site's frozen anchor contract (`content/manifest.yaml`). Content assembly reads anchors
from `manifest.yaml`, never from a filename or a heading. Anchors are the frozen
cross-repo contract with `sparkforensics`.

pages, so every `bottleneck-*` entry's `assembled_from:` points to it.

## Detector → anchor coverage contract (reciprocal, with sparkforensics)

The table above reconciles anchors *inward* (answer file → manifest anchor).
The frozen anchor set also has an *outward* obligation: every anchor
`sparkforensics`'s `src/detectors.ts` deep-links to must resolve to a
real page, and every documented detector anchor should have a detector behind
it. This section defines the machine-readable contract that lets a coverage
check enforce that; the check itself does **not** run here.

**Published contract, `anchors.json`.** This repo
publishes `anchors.json`, a projection of `content/manifest.yaml` carrying one
record per manifest-level anchor:

```json
{ "anchor": "bottleneck-skew", "section": "Detector Catalog",
  "title": "Data Skew", "keywords": ["skew", "partition skew", "SPARK-29544"] }
```

`content/manifest.yaml` stays the single authority for anchor IDs (see
`docs/rules/content.md` #2-#3); `anchors.json` is a derived, faithful mirror of
it, generated by `scripts/build_anchors.py` and asserted current by
`tests/test_anchors_json.py`. Do not hand-edit `anchors.json` or treat it as a
second source of anchor truth; run `uv run scripts/build_anchors.py` after any
`manifest.yaml` change.

**`anchors.json` scope: manifest-level anchors only, not sub-anchors.** Per
`docs/rules/content.md` #3, the frozen contract also covers 12 sub-anchors that
live inside a manifest entry's own page rather than as their own manifest
entries: 4 config-page sub-anchors (`config-shuffle-service`,
`config-autoscale-bounds`, `config-serializer`, `config-memory-overhead`) and
8 detector-facing sub-anchors, each nested inside an existing bottleneck or
chapter page because the detector's `docAnchor` used to point at a page that
never discussed its specific signal: `bottleneck-stage-shape` and
`bottleneck-stage-slowness` (nested inside `bottleneck-skew` and
`bottleneck-slow-host`; `SHAPE` used to link to Task Skew, covering only one
of its three smells, and `SLOW` used to link to Slow Host, a case its own
detector explicitly rules out), `bottleneck-partition-sizing` (nested inside
`bottleneck-shuffle`), `bottleneck-cache-utilization` (nested inside
`memory-model`), `bottleneck-core-locality` and `bottleneck-caching-opportunity`
(both nested inside `bottleneck-utilization`), `bottleneck-speculation-waste`
(nested inside `bottleneck-straggler`), and `bottleneck-autoscaling-churn`
(nested inside `cluster-config`). `anchors.json` does not, and by
design should not, carry a record for any of these 12: `anchors.json` only
projects manifest entries. A detector's doc-anchor coverage check that
intersects against `anchors.json` alone will therefore report these 12 as
dead links even though they resolve to real ids on their own manifest entry's
chapter page. Treat any of these 12 in a coverage report as a known false
positive, not a real dead link; only an anchor outside this list of 43 (31
manifest anchors plus these 12 sub-anchors) is a genuine gap.

**`keywords` is the curatable join key, reserved for future use.** The
`anchor`/`section`/`title` fields are mechanical projections of the manifest;
`keywords` is the one field an author curates. As of 2026-08-30 it is fully
populated (all 31 anchors), but sparkforensics does not read it: its detectors
match by a hardcoded `docAnchor` string per detector, not by intersecting
`finding.type` against these terms. Keep it populated as new anchors are added
so it's ready if/when sparkforensics adopts keyword-based matching, but don't
describe it as an active join key until it actually consumes one.

**The coverage check lives in sparkforensics, not here** (`scripts/doc-anchor-coverage.js`,
shipped as `ELV-042`, PR #74; the companion nonce-handshake work below shipped as `ELV-043`).
sparkforensics owns `src/detectors.ts` and, now that HTML rendering has moved out of this
repo entirely (`docs/architecture.md`'s "HTML generation" section), also owns turning
`content/*.md` into pages, so both sides of the contract coexist in that one repo, with no
cross-repo checkout from spark-tuning-reference CI. `npm run doc-anchor-coverage` intersects
the declared detector doc-anchors against `anchors.json` and reports:

- a detector pointing at an anchor absent from `anchors.json` (dead deep-link), or
- an anchor in `anchors.json` has no detector pointing at it (orphaned page).

It is **warn-only by design, not a CI gate**: `tests/doc-anchor-coverage.test.js` runs under
`npm test` (so it does surface in CI output) but is coded to never fail the suite on drift:
only the manual `npm run doc-anchor-coverage` CLI exit-codes on a real dead link or orphan.
The check also excludes this doc's 6 known sub-anchors (below) from its dead-link count, since
`anchors.json` never carries them by design. The actual hard CI gate against dead deep-links is
a separate, stricter mechanism: sparkforensics's `KNOWN_DOC_ANCHORS` allowlist
(`src/docs-config.ts`), asserted by `tests/docs-config.test.js` to stay a subset of the real
anchors this repo publishes. How a manifest-level anchor resolves in the rendered output (a
vendored file, an `id="..."` attribute, or something else) is entirely sparkforensics' own
rendering choice now; that allowlist, not `anchors.json`, is what actually blocks a dead
"Learn more" link from shipping.

spark-tuning-reference's responsibility ends at emitting a faithful, keyword-populated
`anchors.json`; it runs no detector-coverage check itself, because it has no
access to the detector roster.

## postMessage bridge contract, retired

`src/bridge.js` implemented this contract: a postMessage channel a parent
iframe host used to drive the (now-retired) monolithic `index.html`/`meta.html`
page. `{ type: 'theme' | 'navigate', tok }` went in, `{ type: 'ready', tok }`
came back, and trust was keyed on a per-load nonce rather than origin
(`ELV-043`'s side of this lived in sparkforensics' `src/view/DocsSheet.tsx`).

Per-chapter pages (`site/build-chapters.mjs`) have no such channel: each page
is a full, standalone load, and `site/chapters-client.mjs` (the chapter
site's client script) never posts a `ready` message or listens for
`theme`/`navigate`. `src/bridge.js` and its unit test are deleted; nothing in
this repo inlines it anymore. **sparkforensics' `DocsSheet.tsx` still speaks
the old protocol on its own side** (waits for `ready`, posts `theme`/`navigate`
into the iframe); against a vendored chapter page, that `ready` message never
arrives, so its live theme-sync and in-place navigate silently no-op. That
side needs to drop the handshake and treat the vendored reference the way it
already treats its own docs-site guide pages (`DocsSheet.tsx`'s `'site'`
target kind: reassign the iframe `src` per navigation, read theme once at
load); see the companion sparkforensics adaptation notes this migration
produced.

`site/build-chapters.mjs` and `site/chapters-client.mjs` have since been
removed from this repo along with the rest of the HTML build (`docs/architecture.md`'s
"HTML generation" section): this repo emits no HTML and no client-side script
at all now, so theme sync and in-place navigation are entirely the upstream
renderer's own concern, not something this doc's contract covers.
