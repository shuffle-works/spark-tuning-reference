# Partitioning

## What is the default number of partitions after a shuffle, and what is the guidance for tuning it?

`spark.sql.shuffle.partitions` defaults to 200[^spark-configuration][^learning-spark-2e], applied to every `join()`, `groupBy()`, and aggregation regardless of how much data is actually moving[^spark-configuration]. Learning Spark 2nd Edition notes that this default is usually too high for small or streaming workloads, where you should pull it down toward the executor core count[^learning-spark-2e]. Past that, the tuning guidance stays informal: there's "no magic formula" for the right number. It depends on data set size, core count, and executor memory, and comes down to trial and error[^learning-spark-2e].

Cloudera's tuning guide argues the same from the opposite direction. Because Spark, unlike MapReduce, has low per-task startup overhead, it's safer to over-provision partitions than under-provision them: "when in doubt, it's almost always better to err on the side of a larger number of tasks"[^cloudera-tuning-spark]. Its heuristic for sizing shuffle partitions is to take a stage that already ran, compute the ratio between its Shuffle Spill (Memory) and Shuffle Spill (Disk) metrics, multiply total shuffle write by that ratio to estimate in-memory shuffle size, then round the resulting partition count up rather than down[^cloudera-tuning-spark]. luminousmen's partition-tuning piece backs the same bias and adds an operational catch: once a shuffle stage has run, you can't change its output file count after the fact without inserting a stage barrier (writing to temporary storage, or calling `localCheckpoint()`) between the shuffle and the write[^luminousmen-partition-tuning].

One hard ceiling, not a tuning target: Spark's sort-based shuffle manager caps output partitions in serialized mode at `PackedRecordPointer.MAXIMUM_PARTITION_ID + 1`, roughly 16.8 million. The source code calls this "an extreme defensive programming measure" since no real shuffle comes remotely close to it[^spark-source-shuffle-manager].

## When should repartition be preferred over coalesce, and vice versa?

Reach for `coalesce` first whenever you're only reducing partition count: it merges partitions already sitting on the same node without a shuffle, so it's the cheaper move whenever a shuffle isn't otherwise required[^definitive-guide]. Reach for `repartition` when you actually need the shuffle: increasing partition count, fixing a lopsided partition distribution, or preparing a DataFrame ahead of a join or a `cache()` call, where even parallelism is worth more than the shuffle cost[^definitive-guide].

luminousmen frames the split by what each call is *for* in practice. `repartition()` earns its cost after a heavy filter: Spark doesn't shrink the partition count when rows are filtered out, so 2,000 partitions holding 5% of the original rows just become 2,000 mostly-empty partitions, and `repartition(100)` afterward buys back real parallelism[^luminousmen-partitions]. `coalesce()` belongs at the tail of a pipeline, right before a write, purely to cut down output file count. Push it too far, though (`coalesce(1)`), and it kills parallelism outright, because coalesce doesn't rebalance data, it just stacks existing partitions together, so partitions that were uneven going in are still uneven coming out[^luminousmen-partitions]. There's a middle option, `coalesce(n, shuffle=True)`, which behaves more like repartition: you pay for a shuffle, but get real rebalancing on the way down[^luminousmen-partitions].

High Performance Spark reduces the choice to a readability rule: use `repartition` when you want a shuffle, `coalesce` when you don't, rather than leaning on coalesce's shuffle toggle to blur the line[^high-perf-spark]. At the SQL layer, both directions also have dedicated hints for controlling output partitioning without touching the DataFrame API directly: `/*+ REPARTITION(n) */`, `/*+ REPARTITION(cols) */`, `/*+ REPARTITION_BY_RANGE(cols) */`, and `/*+ COALESCE(n) */`[^spark-sql-perf-tuning].

## Does repartition(n) guarantee exactly n output partitions? What algorithm does it use — does it use a hash shuffle?

Yes. The RDD API docstring is explicit: `repartition(numPartitions)` "return[s] a new RDD that has exactly numPartitions partitions"[^spark-source-rdd]. Under the hood it's just `coalesce(numPartitions, shuffle = true)`[^spark-source-rdd].

The mechanism is a hash shuffle. Spark first spreads records across a temporary key space starting from a randomized position, seeded per-partition via `XORShiftRandom`, so upstream data gets distributed evenly rather than clustered by its original layout[^spark-source-rdd]. That gets fed through a `ShuffledRDD` keyed by a `HashPartitioner(numPartitions)`, then wrapped in a `CoalescedRDD` to land on exactly the requested partition count[^spark-source-rdd]. High Performance Spark puts the same mechanics more plainly: "repartition shuffles the RDD with a hash partitioner and the given number of partitions"[^high-perf-spark]. This holds whether the new count is bigger or smaller than the current one. Repartition always does the full shuffle, unlike coalesce[^definitive-guide].

## Does coalesce(n) ever trigger a shuffle? Under what condition does it promote to a full shuffle?

By default, no. Reducing partition count with `coalesce()` is a narrow transformation: each output partition is the union of a set of parent partitions fixed at plan time, not routed by data values, so there's no shuffle; the stage's task count simply drops to the coalesced number[^high-perf-spark].

The real cost hides one level up: because coalesce is narrow, it forces the *entire* upstream stage to run at the reduced parallelism, not just the coalesce step itself. High Performance Spark flags this as the trade-off. You avoid the shuffle but can lose upstream parallelism, and "you can avoid this behavior at the cost of a shuffle by using the `repartition` function instead"[^high-perf-spark]. The book also notes that coalesce can, at the RDD level, be explicitly made to behave like a full repartition, promoted into a genuine shuffle, though it recommends just calling `repartition` directly in that case for code clarity[^high-perf-spark].

Separate from the DataFrame `.coalesce()` call, Adaptive Query Execution has its own runtime "coalesce" behavior: `spark.sql.adaptive.coalescePartitions.enabled` (default true) merges small, contiguous *post-shuffle* partitions toward a target size at runtime[^spark-sql-perf-tuning]. That's a distinct mechanism. It acts after a shuffle has already happened, rather than being the `.coalesce()` API itself deciding to shuffle.

## In the salting technique for skew, how many salt values should be used? Is there a formula relating salt count to skew ratio or partition count?

No formula turned up in the retrieved sources. What is on record is salting's place in the pre-AQE toolkit. The SPARK-29544 design doc lists "add prefix to the skewed keys to make the same key be different and then adjust the data distribution" as one of three manual approaches used before adaptive execution existed, alongside raising `spark.sql.shuffle.partitions` and raising the broadcast hash join threshold "to change the sort merge join to broadcast hash join as far as possible". It dismisses all three as carrying "lots of limitations" and requiring manual processing, which is exactly the gap AQE's skew-join optimization was built to close[^spark-spip-aqe-skew].

That automatic alternative does carry documented, numeric thresholds, useful for judging when salting would even be warranted: a partition counts as skewed if it's larger than `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (default 5.0) times the median partition size, and also larger than `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default 256 MB)[^spark-configuration][^spark-sql-perf-tuning]. Databricks' skew-hint mechanism is the other documented alternative to hand-rolled salting: a `/*+ SKEW(...) */` hint names the skewed relation and column(s) and, optionally, the specific skewed key values, letting the planner target just those keys instead of relying on automatic detection[^databricks-skew-join].

## When using repartition(col) for join alignment, does Spark guarantee that both DataFrames will use the same partitioner if the same column and count are specified?

No, and the reason is architectural rather than a tuning nuance. High Performance Spark is explicit that `repartition` and `coalesce` "do not assign a known partitioner" to the resulting RDD, in contrast to `partitionBy`, which does[^high-perf-spark]. A "known partitioner" matters because Spark's join planner only skips a shuffle when both sides already carry partitioner objects it can prove equal: for a `HashPartitioner` that means equal partition counts, for a `RangePartitioner` it means equal range bounds[^high-perf-spark]. Since `repartition(n, col)` doesn't leave that trackable partitioner object behind, calling it with the same column and count on two separate DataFrames produces data that's plausibly laid out the same way, but the planner has no recorded partitioner to compare. It has no basis for treating the two as co-partitioned and skipping the shuffle at join time[^high-perf-spark].

The default join execution path makes the same point from the other side: Spark's shuffle hash join partitions the second dataset using the same partitioner as the first specifically so that matching keys land together, which only implies the shuffle can be skipped when a shared, recognized partitioner is already in place beforehand[^high-perf-spark].

The mechanism that does deliver this guarantee is a different one: storage-partitioned joins, where both tables are physically bucketed identically at the catalog level (for example, Iceberg tables created with matching `PARTITIONED BY (bucket(...))` clauses). When Spark recognizes both sides report the same partitioning through `SupportsReportPartitioning`, it can drop the Exchange (shuffle) node entirely, or shuffle only one side. Plain DataFrame-level `repartition(col)` doesn't offer that guarantee, because it isn't backed by catalog-level partitioning metadata[^spark-sql-perf-tuning][^spark-configuration].

## What is the maximum number of partitions Spark supports? Is there a practical upper limit beyond which performance degrades due to scheduling overhead?

None of the sources retrieved for this question state a hard maximum partition count. What they do converge on is the practical, overhead-driven ceiling: every partition maps to exactly one task and one thread, so partitions that are too small flood the cluster with per-task scheduling overhead, while partitions that are too large create memory pressure and straggler tasks[^luminousmen-partitions]. Learning Spark 2nd Edition frames the target from the parallelism side rather than an absolute cap: the goal is at least as many partitions as there are cores across the executors, so no core sits idle. More partitions than cores is fine as long as it doesn't drift into the small-partition overhead regime described above[^learning-spark-2e].

AQE's partition-coalescing behavior exists precisely to correct over-partitioning at runtime, merging small contiguous post-shuffle partitions toward a target size so a stage doesn't end up scheduling far more tasks, and writing far more small files, than the data actually needs[^luminousmen-partitions].

## How do you parallelize a JDBC read in Spark using partitionColumn, lowerBound, upperBound, numPartitions, fetchsize, or predicates, how should the partition column and bounds be chosen, and how do you avoid overloading the source database?

A plain JDBC read runs as one task: by default Spark scans the entire source table through a single `SELECT` query in a single task[^aws-glue-parallelize-tasks]. Parallel reads work by splitting that one `SELECT` into several queries, each with its own `WHERE` predicate[^aws-glue-parallelize-tasks]. Spark gives you two ways to define the split.

**Range partitioning with four options.** `partitionColumn`, `lowerBound`, and `upperBound` must be set together, along with `numPartitions`. They describe how to partition the table when reading in parallel from multiple workers[^spark-jdbc]. `partitionColumn` must be a numeric, date, or timestamp column of the table being read[^spark-jdbc]. `lowerBound` and `upperBound` only decide the partition stride. They do not filter rows, so every row in the table is still partitioned and returned[^spark-jdbc]. `numPartitions` is the maximum number of partitions used for parallelism in table reading, and it also caps the number of concurrent JDBC connections[^spark-jdbc]. The PySpark `DataFrameReader.jdbc()` method exposes the same split through its `column` argument, an alias of `partitionColumn`, and requires `lowerBound`, `upperBound`, and `numPartitions` whenever `column` is given[^pyspark-dataframereader-jdbc].

**Explicit predicates.** `DataFrameReader.jdbc()` also takes `predicates`, a list of expressions suitable for a `WHERE` clause, where each expression defines one partition of the resulting DataFrame[^pyspark-dataframereader-jdbc]. The table is read in parallel if either `column` or `predicates` is set, and when both are set, `column` wins[^pyspark-dataframereader-jdbc]. Since each expression becomes one partition, you pick the ranges yourself[^pyspark-dataframereader-jdbc].

**Choosing the column and bounds.** Databricks' reference example asks for a partition column with a uniformly distributed range of values, with `lowerBound` and `upperBound` set to the lowest and highest values to pull data for with that column[^databricks-jdbc]. It also recommends a column backed by an index in the source database, which speeds up the per-partition queries[^databricks-jdbc].

**Fetch size.** `fetchsize` sets how many rows the JDBC driver fetches per round trip. Its Spark default is `0`, and raising it helps on drivers that default to a low fetch size, such as Oracle with 10 rows[^spark-jdbc].

**Protecting the source database.** Since `numPartitions` also caps concurrent JDBC connections[^spark-jdbc], partition count is load on the database. Databricks warns that too many simultaneous queries might overwhelm the remote database, which is especially troublesome for application databases, and advises caution above 50[^databricks-jdbc]. Its reference example uses `numPartitions` 8 for an eight-core cluster, with a comment not to set it to hundreds[^databricks-jdbc]. The PySpark API docs carry the same warning: too many parallel partitions on a large cluster might crash the external database[^pyspark-dataframereader-jdbc]. When the read itself can't be parallelized further, AWS recommends a `repartition()` right after the initial load, with two or three times the available cores as a rule of thumb[^aws-glue-parallelize-tasks].

**Other connectors.** The same single-task pattern shows up elsewhere, each with its own knob. In AWS Glue, a DynamicFrame JDBC read is split with `hashfield` (or `hashexpression`) and `hashpartitions`[^aws-glue-parallelize-tasks]. A DynamoDB read's partition count comes from `dynamodb.splits`, and a Kinesis Data Streams read gets one partition per shard, so a stream with few shards yields few tasks[^aws-glue-parallelize-tasks].
