# Shuffle

## Q1. What operations trigger a shuffle in Spark SQL / DataFrame API?

At the DataFrame/SQL level, `groupBy()`, `join()`, `agg()`, `sortBy()`, and `reduceByKey()`-style aggregations are the classic wide transformations: they need Spark to exchange, sort, group, and merge data across executors, generically referred to as a shuffle[^learning-spark-2e]. Join implementations that aren't broadcast (shuffle hash join, shuffle sort-merge join, and shuffle-and-replicated nested loop / Cartesian product join) all move a large amount of data across executors[^learning-spark-2e]. At the RDD layer underneath, the operations that can cause a shuffle are repartitioning operations (`repartition`, `coalesce`), `'ByKey` operations other than counting (`groupByKey`, `reduceByKey`), and join-family operations (`cogroup`, `join`)[^spark-rdd-programming].

Spark can skip the shuffle in specific cases where it already knows the data layout. Storage Partition Join (SPJ) avoids the shuffle phase entirely when Spark can use the partitioning already reported by a compatible V2 data source (`spark.sql.sources.v2.bucketing.enabled`, default `true` since 3.3.0), generalizing bucket joins to functions registered in a `FunctionCatalog`[^spark-sql-perf-tuning]. Classic Hive-style bucketing gets the same effect: once both sides of a join are bucketed and sorted the same way, the physical plan shows no `Exchange` operator[^japila-bucketing]. `DataFrameWriter.partitionBy`, on the other hand, does not trigger a shuffle by itself on write, though it can still leave you with a large number of small output files[^luminousmen-partition-tuning].

## Q2. What is the difference between sort-based shuffle (SortShuffleManager) and hash-based shuffle? When does Spark fall back to hash-based?

Modern Spark (3.5 source) only ships `SortShuffleManager`. In sort-based shuffle, incoming records are sorted according to their target partition id and written to a single map output file per task; reducers then fetch contiguous regions of that file for their portion of the map output, spilling sorted subsets to disk and merging them if the data doesn't fit in memory[^spark-source-shuffle-manager]. Internally it has two write paths: a "serialized sorting" path, used when there's no map-side combine, the serializer supports relocation of serialized values (Kryo or Spark SQL's custom serializers), and the shuffle produces at most 16,777,216 output partitions; and a "deserialized sorting" path used for everything else[^spark-source-shuffle-manager].

The Magnet SPIP frames the general hash-based vs. sort-based distinction this way: hash-based shuffle has each map task produce a separate output file per reduce task, while sort-based shuffle sorts the map task's output by the hashed partition key and materializes it as a single file. Sort-based shuffle pays a sorting cost but scales better once the shuffle data is large, which is why Spark and Flink both moved to it and pair it with an external shuffle service[^spark-spip-magnet].

Spark doesn't fall back to a distinct "hash-based shuffle manager" at runtime; the closest thing inside `SortShuffleManager` is the bypass merge path, which is itself hash-style in behavior: it skips the sort and writes one file per reduce partition directly when there's no map-side aggregation and the number of reduce partitions is at most `spark.shuffle.sort.bypassMergeThreshold` (default 200)[^spark-configuration] (see Q3 for that path's trade-offs). Whether Spark historically shipped a separate, selectable `HashShuffleManager` that this bypass path effectively replaced is not something the retrieved chunks document. ## Q3. What is the bypass merge threshold (spark.shuffle.sort.bypassMergeThreshold)? When does Spark use the bypass path and what are the trade-offs?

`spark.shuffle.sort.bypassMergeThreshold` defaults to 200 (added in 1.1.1). In the sort-based shuffle manager, it controls when Spark avoids merge-sorting the shuffle data: the bypass path is used when there is no map-side aggregation and the number of reduce partitions is at most this threshold[^spark-configuration].

The Spark 3.5 source spells out the trade-off directly, in the comment on `SortShuffleManager.registerShuffle`: when there are fewer than `bypassMergeThreshold` partitions and no map-side aggregation is needed, Spark writes `numPartitions` files directly per map task and just concatenates them at the end, rather than merge-sorting spilled files. This avoids serializing and deserializing the data twice, which the normal code path would do to merge spills. The documented downside is having multiple files open at a time, and thus more memory allocated to buffers[^spark-source-shuffle-manager]. So the bypass path trades a doubled serialize/deserialize cost for more open file handles and buffer memory, which stays cheap only while the reduce-side partition count is small.

## Q4. What does spark.shuffle.compress compress — map output, reduce input, or both? What codec is used by default?

`spark.shuffle.compress` (default `true`) controls whether Spark compresses map output files: it's a map-side / write-side setting, not a reduce-input setting[^spark-configuration]. It reuses whatever codec is configured in `spark.io.compression.codec`, which defaults to `lz4`[^spark-configuration]. That same `spark.io.compression.codec` setting is shared by other internal compression toggles (RDD partitions, event log, broadcast variables, shuffle outputs), and Spark also ships `lzf`, `snappy`, and `zstd` as alternative codecs, selectable via fully-qualified class name[^spark-configuration]. Separately, `spark.shuffle.spill.compress` (also default `true`) governs whether *spilled* shuffle data is compressed, and it likewise uses `spark.io.compression.codec`[^spark-configuration].

## Q5. What is spark.reducer.maxSizeInFlight and what happens when a reducer tries to fetch more than this limit?

`spark.reducer.maxSizeInFlight` defaults to 48m (MiB). It caps the maximum size of map outputs a reduce task will fetch simultaneously; because each fetched output needs a buffer to receive it, this value is a fixed memory overhead per reduce task, so the docs recommend keeping it small unless the executor has memory to spare[^spark-configuration]. It's a throttle, not a hard cap that fails the task: it bounds how much data a reducer pulls at once, so when a round of fetches reaches this size, the rest of the map outputs come in later, smaller batches. Raising it moves more data in flight at the cost of per-task memory; lowering it saves memory at the cost of more fetch rounds.

## Q6. What is spark.shuffle.file.buffer — what is it buffering, and when does increasing it help?

`spark.shuffle.file.buffer` defaults to 32k (KiB). It sizes the in-memory buffer for each shuffle file *output* stream (the buffer a map task writes through before the data hits disk), and larger buffers reduce the number of disk seeks and system calls needed to create the intermediate shuffle files[^spark-configuration]. Learning Spark's tuning table recommends bumping it to 1 MB for large jobs, so Spark does more buffering before writing the final map results to disk[^learning-spark-2e]. It helps when map tasks are I/O-bound writing many shuffle files: fewer, larger writes trade some per-task memory for less disk-seek and syscall overhead during the shuffle-write phase[^learning-spark-2e].

## Q7. Does groupBy().agg() always produce a shuffle? Are there cases where Spark can avoid it (e.g., input is already partitioned by the group key)?

No. `groupBy()` on a DataFrame is a wide transformation and normally requires an `Exchange` (shuffle) so all rows for a key land on the same partition[^learning-spark-2e], but Spark can skip that exchange when it already knows the data is co-partitioned by the grouping key. The clearest documented case is Hive-style bucketing plus sorting: once a table is bucketed on the join/group key, the physical plan drops the `Exchange` node because the data was already shuffled at write time[^taboola-bucketing-shuffle]. Storage Partition Join generalizes this for join queries against compatible V2 sources, letting Spark "try to avoid a shuffle if possible" based on the reported partitioning[^spark-sql-perf-tuning].

Note that `DataFrame.repartition(key)` is a one-time, explicit shuffle you can reuse: after repartitioning and caching by a key, subsequent joins on that same key skip their own shuffle because the data is already partitioned that way[^luminousmen-partition-tuning]. The counterexample is `partitionBy` on write: it changes the on-disk directory layout but is "not the equivalent" of an in-memory repartition for aggregations: `df.groupBy('key').sum()` still requires an `Exchange`/shuffle over data written with `partitionBy`[^luminousmen-partition-tuning].

## Q8. What is the shuffle read overhead for distinct() vs dropDuplicates(cols) — do they differ in shuffle volume?

Both require a shuffle: Spark SQL's `dropDuplicates` selects unique rows the same way RDD-level `distinct` does ("this can require a shuffle"), and the source notes it's often much slower than a simple `filter`[^high-perf-spark]. The documented difference between the two is about key flexibility, not shuffle volume: unlike RDD `distinct`, DataFrame `dropDuplicates` can optionally drop rows based on only a subset of columns (e.g., `pandas.dropDuplicates(List("id"))`) rather than requiring uniqueness across the whole row[^high-perf-spark]. The retrieved material doesn't give a quantified, bytes-moved comparison between full-row `distinct()` and a column-subset `dropDuplicates(cols)`; answering that precisely would need a source on how the `Deduplicate`/`Aggregate` planner shapes the shuffle write for each case. ## Q9. What exactly is "external shuffle service" (spark.shuffle.service.enabled) and when is it required vs optional?

The external shuffle service (`spark.shuffle.service.enabled`, default `false`) preserves the shuffle files written by executors so that executors can be safely removed, or so shuffle fetches can continue even after an executor failure; enabling it requires setting the service up separately, since the flag alone isn't enough[^spark-configuration]. Concretely, it's a long-running process on each cluster node, independent of any particular Spark application or its executors; when enabled, Spark executors fetch shuffle files from this service instead of from each other, so shuffle state written by an executor keeps being served after that executor's own lifetime ends[^spark-job-scheduling].

It becomes effectively required, rather than optional, for dynamic allocation: a Spark executor may be decommissioned mid-shuffle (e.g. because of stragglers), and without the external shuffle service its shuffle files would otherwise have to be recomputed from scratch once the executor is removed[^spark-job-scheduling]. Dynamic allocation's own documentation lists the external shuffle service as one of several ways to satisfy this requirement: shuffle tracking (`spark.dynamicAllocation.shuffleTracking.enabled`), shuffle-block decommissioning, or a custom `ShuffleDataIO` plugin backed by reliable storage[^spark-configuration]. Outside of dynamic allocation it's optional: without it, shuffle data on deallocated executors simply remains on local disk until the application ends[^spark-configuration]. It's also currently a hard prerequisite for push-based shuffle, which is only supported for Spark on YARN with the external shuffle service enabled[^spark-configuration].

## Q10. What is push-based shuffle (SPARK-30602 / Magnet) — when available, how is it enabled, and what does it improve vs classic pull shuffle?

Push-based shuffle, designed under SPARK-30602 and based on LinkedIn's "Magnet" shuffle service, changes shuffle from a pull model (reducers requesting many small, randomly-ordered blocks from wherever each mapper wrote them) to a push-and-merge model: mapper-generated shuffle blocks are pushed to remote Magnet shuffle services, which opportunistically merge them into large per-partition chunks before the reduce stage starts[^spark-spip-magnet]. The motivation is that classic Spark shuffle materializes data in sort-based fashion and serves it from an external shuffle service, but as shuffle data volume grows, the number of blocks grows quadratically (mappers × reducers) while individual block sizes shrink to only tens of KB, which is inefficient for HDD-backed random reads[^spark-spip-magnet]. Key properties: the push operation is decoupled from the mappers (it doesn't add to map task runtime or fail map tasks if pushing fails); it's best-effort: Magnet doesn't require every block push to complete, and reducers can fetch a mix of merged and unmerged blocks as input; and it can mitigate stragglers/data skew by halting slow pushes or skipping oversized blocks rather than blocking the whole shuffle[^spark-spip-magnet].

Configuration-wise, push-based shuffle is controlled by paired server- and client-side flags added in Spark 3.2.0: on the server side, `spark.shuffle.push.server.mergedShuffleFileManagerImpl` selects the `MergedShuffleFileManager` implementation and disables/enables push-based shuffle server-side (disabled by default); on the client side, `spark.shuffle.push.enabled` (default `false`) must be set to `true`, and only takes effect together with that server-side flag[^spark-configuration]. LinkedIn's own production rollout, on a cluster running 30K+ Spark applications shuffling roughly 5 PB/day, reported a large reduction in shuffle read wait time and a corresponding drop in total executor runtime after enabling it on complex production flows[^spark-spip-magnet]. Compared with classic pull shuffle, the improvement is specifically in disk I/O efficiency (converting many small random reads into large sequential reads of pre-merged chunks) and in reducer data locality, since merged output can be co-located with the reduce tasks that will consume it[^spark-spip-magnet].
