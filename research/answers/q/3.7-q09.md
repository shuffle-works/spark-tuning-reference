## Q9. Why is Gzip generally discouraged for Spark inputs? Is it solely the non-splittability, or are there other factors (CPU cost, codec availability)?

Non-splittability is the headline factor documented in the corpus, but specifically for large *raw* compressed source files rather than for gzip as a Parquet-internal codec: "do not use large source files in zip/gzip format, they are not splittable. It is not possible to read such files in parallel with Spark. First, Spark needs to download the whole file on one executor, unpack it on just one core, and then redistribute the partitions to the cluster nodes. As you can imagine, this becomes a huge bottleneck in your distributed processing"[^luminousmen-dont-collect]. The recommended workaround for HDFS-resident files is to unpack them before loading into Spark[^luminousmen-dont-collect].

CPU cost is the second documented factor: "uncompressed files are clearly outperforming compressed files. This is because uncompressed files are I/O bound, and compressed files are CPU bound, but I/O is good enough here"[^luminousmen-dont-collect]: once I/O is not the bottleneck, paying gzip's decompression CPU cost is a net loss. The same source draws a comparison to Bzip2, which is splittable but so aggressively compressed that "you get very few partitions and therefore they can be poorly distributed," making it suitable mainly "if there are no limits on compression time and CPU load, for example for one-time packaging of large amounts of data"[^luminousmen-dont-collect].

The non-splittability concern is about gzip as the *container-level* compression of a whole file (a `.csv.gz` or `.json.gz`), not gzip used as Parquet's internal per-page/row-group codec, where Parquet's row-group structure, not the codec, provides splittability (see Q2/Q3). *Spark: The Definitive Guide*'s discussion of splittable file types notes "not all compression schemes are splittable... We recommend Parquet with gzip compression"[^definitive-guide-4]: the same source that warns about raw gzip files elsewhere in the corpus treats gzip as an acceptable choice once it's wrapped inside Parquet's row-group container. The retrieved chunks do not discuss gzip codec-availability issues (e.g., missing native codec libraries) as a separate factor. [UNRESOURCED for codec-availability specifically].
