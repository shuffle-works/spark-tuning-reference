## Is a shuffle the only trigger for a stage boundary, or can other operations (e.g., sortBy on an RDD, checkpointing) also split stages?

The rule is still "shuffle dependency creates the boundary", but several different operations can produce that shuffle dependency, so it isn't just an explicit `.repartition()` or `.groupBy()`. Wide transformations that cause this redistribution include `sort` and `groupByKey`, among others, so `sortByKey`/`sortBy` on an RDD is itself wide, not just `groupByKey`-style aggregations[^high-perf-spark]. The example RDD program `filter → map → groupByKey → map → sortByKey → count` produces three stages, bounded by the `groupByKey` and `sortByKey` operations[^high-perf-spark]. The original Spark paper likewise defines stage boundaries generically as "the shuffle operations required for wide dependencies, or any already-computed partitions that can short-circuit the computation of a parent RDD"[^rdd-nsdi12]. A wide dependency of any kind, not a specific API call, is what matters.

A related practical trigger: reusing shuffle files. Because Spark always writes shuffle output to stable storage regardless of a `persist`/`checkpoint` call, if the driver reuses an RDD that has already been shuffled, Spark can skip recomputing everything up to that shuffle and read the shuffle files directly. The Spark UI shows this as a "skipped stage"[^high-perf-spark]. This doesn't add a boundary, it lets Spark avoid re-running stages that already produced their shuffle output.
