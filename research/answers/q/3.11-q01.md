## Q1. What is the recommended formula for sizing Spark executors (cores × memory)?

The reference material describes a "balanced" approach rather than a single closed-form formula, worked out from three inputs: total cores per node, total memory per node, and a target of 5 cores per executor (justified by HDFS throughput; see Q2). For a 10-node cluster with 16 cores and 64GB RAM per node, the derivation is: assign `--executor-cores = 5`; reserve ~1 core per node for Hadoop/YARN/OS daemons, leaving 15 usable cores/node (150 total); `num-executors = total-usable-cores / cores-per-executor = 150/5 = 30`, minus 1 for the YARN ApplicationMaster (29); executors-per-node `= 30/10 = 3`; `memory-per-executor = mem-per-node / executors-per-node = 64GB/3 ≈ 21GB`; after subtracting ~7% for the YARN memory overhead, the usable `--executor-memory` comes out to about 18GB, yielding a recommended config of 29 executors × 5 cores × 18GB[^spark-notes-executor-sizing].

Cloudera's worked example for a 6-node cluster (16 cores/64GB per node) reaches the same shape: rather than `--num-executors 6 --executor-cores 15 --executor-memory 63G` (one "fat" executor per node), the better option is `--num-executors 17 --executor-cores 5 --executor-memory 19G`[^cloudera-tuning-spark]. Both sources treat the number of tasks (driven by executor-cores × num-executors) as the single most important tuning lever, since Spark cannot compensate for too little parallelism on its own[^cloudera-tuning-spark].

At the config level, `spark.executor.cores` controls how many concurrent tasks an executor runs and defaults to 1 in YARN mode (or all available cores on the worker in standalone mode)[^spark-configuration]; `spark.executor.memory` sets the JVM heap size per executor[^cloudera-tuning-spark]. As a general parallelism target independent of the executor-sizing formula above, the Spark tuning guide recommends 2–3 tasks per CPU core in the cluster[^spark-tuning-guide].
