## Q5. Is pyspark.sql.functions always faster than an equivalent Python UDF? Are there documented edge cases where a UDF is competitive?

The documented comparisons consistently favor built-in/vectorized code over row-at-a-time Python UDFs, but they do not claim built-in functions are unconditionally faster, nor do they document a case where a plain row-at-a-time UDF outperforms `pyspark.sql.functions`. For the "plus one" example, Databricks' post notes that "built-in column operators can perform much faster in this scenario" than a row-at-a-time UDF, and that the vectorized pandas UDF equivalent is "much faster than the row-at-a-time version" because the operation is vectorized over the Series[^databricks-pandas-udf]. That comparison is about row-at-a-time UDFs, not pandas/Arrow-optimized UDFs, which close much of the gap (see Q2's 3x–100x figures)[^databricks-pandas-udf].

No source in the retrieved set documents a case where a plain Python UDF is competitive with or faster than an equivalent built-in function.
