## How do Delta Lake, Apache Iceberg, and Apache Hudi each control target data file size (Delta OPTIMIZE / target file size, Iceberg write.target-file-size-bytes, Hudi hoodie.parquet.max.file.size and small-file handling), and why do many small files hurt query and metadata performance?

Delta Lake, Iceberg, and Hudi treat file sizing very differently: Delta and Iceberg lean on a post-hoc compaction command, while Hudi's headline feature is sizing files correctly at write time.

Delta Lake does not size files during the write itself by default; it improves an already-written table's layout with the `OPTIMIZE` command, which bin-packs small files into larger ones and has been available since Delta Lake 1.2.0[^delta-optimize]. `OPTIMIZE` can run against a whole table (`OPTIMIZE delta_table_name` or the path-based `OPTIMIZE '/path/to/delta/table'`) or against a subset via a partition predicate (`OPTIMIZE delta_table_name WHERE date >= '2017-01-01'`), and the same operation is exposed through the Python/Scala API as `DeltaTable.forName(...).optimize().executeCompaction()`, optionally scoped with `.where(...)`[^delta-optimize]. Bin-packing is idempotent, so re-running `OPTIMIZE` on an already-compacted table is a no-op[^delta-optimize]. Delta Lake 3.1.0 adds a separate "Optimized Write" feature aimed at file sizing[^delta-optimize]; the exact target-size default for either `OPTIMIZE` or Optimized Write is `[UNRESOURCED: Delta Table Properties Reference / spark.databricks.delta.optimize.maxFileSize would carry that default]`.

Apache Iceberg's table spec shows one Iceberg-specific driver of file proliferation: version 2 of the spec "adds delete files to encode rows that are deleted in existing data files," letting a writer "delete or replace individual rows in immutable data files without rewriting the files"[^iceberg-spec]. That is, row-level deletes accumulate as separate small delete files rather than forcing an immediate rewrite of the data file they apply to. The specific `write.target-file-size-bytes` default and how `rewrite_data_files` selects and merges files are `[UNRESOURCED: iceberg-configuration and iceberg-spark-procedures docs would be needed]`.

Apache Hudi is explicit that avoiding small files is "a critical design decision in the Hudi architecture," and it offers two mechanisms: auto-sizing during writes, and clustering after the fact[^hudi-file-sizing]. For auto-sizing, the default targeted size for Parquet base files is 120 MB, set via `hoodie.parquet.max.file.size`[^hudi-file-sizing]. Auto-sizing pairs that with a small-file threshold, `hoodie.parquet.small.file.limit` (default 104,857,600 bytes / 100 MB): any existing file at or below that limit is a candidate to have new records appended to it rather than Hudi writing a brand-new file, and Hudi bin-packs records into such candidates up toward the max-file-size target. For example, with a 100 MB small-file limit and a 120 MB max file size, Hudi picks all files under 100 MB and tries to grow them to 120 MB[^hudi-file-sizing]. Setting `hoodie.parquet.small.file.limit` to 0 disables this small-file lookup and forces every write to a new file[^hudi-file-sizing][^hudi-clustering]. Getting the initial record-size estimate right (`hoodie.copyonwrite.record.size.estimate`, default 1024 bytes) matters for the very first ingestion batch, since Hudi needs it to bin-pack records into a file of the right size before it has commit history to learn the average record size from[^hudi-file-sizing]. Auto-sizing does not apply to `bulk_insert`[^hudi-file-sizing]. Merge-on-Read (MOR) tables add their own knobs: `hoodie.merge.small.file.group.candidates.limit` (default 1) caps how many small-file base-file groups are considered for record appends during upsert, and `hoodie.logfile.max.size` (default 1,073,741,824 bytes / 1 GB) is the rollover size for the row-based delta log files that MOR tables append updates to (append-based rollover only works on storage that supports append, which may not include cloud object stores like S3/GCS)[^hudi-file-sizing]. Hudi's COW/MOR trade-off table also notes that COW base files "need to be smaller to avoid high update (I/O) cost," while MOR base files "can be larger, since update cost is low and amortized" via the delta log[^hudi-table-types].

Hudi's second mechanism, clustering, is a table service that stitches small files into larger ones (optionally re-sorting or applying a space-filling curve like Z-order/Hilbert) without changing ingestion behavior[^hudi-clustering][^hudi-file-sizing]. The `hoodie.parquet.small.file.limit` knob lets you choose the ingestion/query trade-off directly: set it to 0 to force every write into new file groups (fastest ingestion, most small files, relies on clustering to fix later), or raise it to pad more records into existing files at the cost of added ingestion latency[^hudi-clustering]. Clustering's plan strategy groups eligible files so each group targets a size that is a multiple of `targetFileSize`, and size-based clustering strategies specifically exclude files already above the small-file limit from the plan[^hudi-clustering]. Clustering is distinct from compaction: compaction (the default async mode, or synchronous via `hoodie.compact.inline = true`) merges MOR's row-based delta logs into new base-file versions to keep read amplification in check, whereas clustering is a data-layout optimization that can only run on tables/partitions with no concurrent updates[^hudi-compaction][^hudi-clustering].

Many small files hurt performance for a few concrete reasons. On the query side, a query has to scan through many small files to retrieve the same data it would get from fewer larger files, which is an inefficient access pattern; on top of that, cloud storage such as S3 enforces per-prefix request rate limits, and because at least one request is issued per file regardless of its size, more files raise the odds of hitting that rate limit and add fixed per-file open/close overhead[^hudi-file-sizing]. On the pipeline side, more files mean more tasks, which slows down Spark, Flink, or Hive jobs through excessive scheduling overhead and memory requirements[^hudi-file-sizing]. On storage and metadata, many small files compress less efficiently than fewer large ones, raising storage cost, and if the table is indexed, each additional file also adds more metadata (such as column statistics) that has to be stored and, implicitly, scanned by planners[^hudi-file-sizing]. This is why ingestion and query performance pull in opposite directions: ingestion favors small files for parallelism and low latency to availability, but query performance degrades badly as the small-file count grows, which is exactly the tension that table-service features like Hudi's clustering and Delta's `OPTIMIZE` exist to resolve[^hudi-clustering][^delta-optimize].
