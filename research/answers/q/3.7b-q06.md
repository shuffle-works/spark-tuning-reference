## How do the formats handle row-level deletes and updates without rewriting whole files — Delta Lake deletion vectors, Iceberg copy-on-write versus merge-on-read with position and equality deletes, and Hudi Copy-on-Write versus Merge-on-Read table types?

By default, deleting or updating a single row in a Delta table forces a rewrite of the entire Parquet file that contains it[^delta-deletion-vectors]. Deletion vectors avoid that: once enabled, Delta marks the affected rows as removed in a separate file and resolves the table's current state at read time by applying those markers to the most recent version, instead of rewriting the Parquet file immediately[^delta-deletion-vectors]. Support was added incrementally by operation and Delta version: SCAN in 2.3.0, DELETE in 2.4.0, UPDATE in 3.0.0 (on by default since 3.1.0), and MERGE in 3.1.0 (on by default since 3.1.0)[^delta-deletion-vectors]. The feature is turned on per table with `ALTER TABLE <table_name> SET TBLPROPERTIES('delta.enableDeletionVectors' = true)`, which upgrades the table protocol version so older Delta clients that don't understand deletion vectors can no longer read the table[^delta-deletion-vectors]. The soft-deletes recorded in deletion vectors are only applied physically (that is, the Parquet files are actually rewritten) when a DML command runs with deletion vectors disabled, when `OPTIMIZE` runs, or when `REORG TABLE ... APPLY (PURGE)` runs[^delta-deletion-vectors]. Delta's DML surface for this is the standard `UPDATE`, `DELETE`, and `MERGE` commands, callable from SQL, Python, Scala, or Java, each with ACID guarantees[^learning-spark-2e].

Iceberg took a versioned approach to the same problem. Version 1 of the spec manages tables as immutable Parquet, Avro, or ORC files with no row-level delete mechanism[^iceberg-spec]. Version 2 adds delete files that encode which rows in existing data files have been removed, letting a writer delete or replace individual rows in immutable files without rewriting them[^iceberg-spec]. Two delete-file encodings exist under v2: position delete files, which identify a deleted row by its data file path and ordinal row position, and equality delete files, which identify deleted rows by matching one or more column values (for example `id = 5`)[^iceberg-spec]. An equality delete file stores any subset of the table's columns as match predicates, and a row is considered deleted if its values equal all of the delete file's columns for some entry that applies to it, so multiple columns behave as an AND of equality predicates, and a null delete column matches rows whose corresponding value is null[^iceberg-spec]. Delete files, like data files, are tracked by partition and are in general only applied to older data files in the same partition, with equality deletes stored under an unpartitioned spec applied globally instead[^iceberg-spec]. Version 3 replaces position delete files with deletion vectors: a per-data-file bitmap of deleted row positions, stored using the `deletion-vector-v1` Puffin blob format and optimized with 32-bit Roaring bitmaps for positions that fit in 32 bits[^iceberg-spec]. At most one deletion vector is allowed per data file per snapshot, and writing a new one must replace any earlier position delete files for that data file so readers can safely ignore them[^iceberg-spec]. Writers are not allowed to add new position delete files once a table is on v3, though pre-existing v2 position delete files remain valid and must eventually be merged into a deletion vector[^iceberg-spec]. In all versions, this delete-file/deletion-vector mechanism lets Iceberg defer physically rewriting a data file: the deletes are merged with the base file logic at read/scan time, and only compaction-style replace operations combine several files into one that contains the same surviving rows[^iceberg-spec].

Hudi frames the same trade-off explicitly as two table types rather than a spec version progression. Copy-on-Write (CoW) tables are optimized for read-heavy workloads: an update or delete triggers creation of a new base file (file slice) in the affected file group, with no log files written, so every query reads only base files and gets high read performance at the cost of slower writes, since even a small percentage of changed records forces a base-file rewrite[^hudi-table-types]. Merge-on-Read (MoR) tables instead write updates and deletes to lightweight log files (in Avro or a columnar/base-file format), which are merged dynamically with the base file at query time and periodically compacted, trading some query-time overhead (depending on whether logs have been compacted) for lower write latency and near-real-time data availability[^hudi-table-types]. Core transactional features (atomic writes, indexing, incremental queries, automatic file sizing, and scalable metadata tracking) are available on both table types regardless of which one is chosen[^hudi-table-types]. Hudi's own name is an acronym for Hadoop Update Delete and Incremental, reflecting that it was built around incremental upserts and deletes over key/value-style data, storing that data as a combination of columnar base files and row-based log files for recording incremental changes[^learning-spark-2e].
