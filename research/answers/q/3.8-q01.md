## Q1. Under what circumstances does caching a DataFrame improve performance vs have no effect or hurt performance?

Caching pays off when the same DataFrame is scanned or recomputed more than once downstream: repeated queries or transformations on the same base data, iterative ML training loops, or interactive exploration where a dataset is reused across multiple branches[^learning-spark-2e][^definitive-guide]. In one book benchmark, caching a 10M-row DataFrame and materializing it with `count()` cut a subsequent `count()` from 5.11s to 0.44s, a roughly 12x speedup[^learning-spark-2e].

It has no effect, or hurts, in several cases:

- **Single-use data.** If a dataset is processed only once downstream, caching adds serialization/deserialization and storage bookkeeping cost for no reuse benefit: "if you are only going to process a dataset once... caching it will only slow you down"[^definitive-guide].
- **Data too big to fit.** DataFrames too large for available memory are poor candidates[^learning-spark-2e]. Partitions cache whole or not at all (8 partitions with room for 4.5 caches only 4), so the uncached remainder is recomputed on every access, which can make the job slower than not caching[^learning-spark-2e].
- **Partial materialization.** `cache()`/`persist()` are lazy: nothing is cached until an action forces a full pass. An action like `take(1)` materializes only the one partition Catalyst needs, not the whole DataFrame, so a later full scan still recomputes most of the data[^learning-spark-2e]. Likewise, `.take(10)`, `.limit(100)`, or any filtered/partial scan caches only the blocks Spark was forced to touch; the rest stays lazily uncomputed[^luminousmen-caching-mechanics].
- **Plan mismatch.** Caching wraps the *analyzed* (pre-optimization) logical plan in an `InMemoryRelation`. A logically-equivalent but differently-written query produces a different analyzed plan, so Spark can silently skip the cache and recompute from scratch even when the final optimized plan would have been identical[^luminousmen-caching-mechanics].
- **Optimizer limitations.** Caching freezes Catalyst's optimization opportunities at the cached point. For example, it can block predicate pushdown once data is served from the in-memory cache instead of the source[^luminousmen-caching-tips].
