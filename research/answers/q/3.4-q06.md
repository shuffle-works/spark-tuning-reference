## In the salting technique for skew, how many salt values should be used? Is there a formula relating salt count to skew ratio or partition count?

No formula turned up in the retrieved sources. What is on record is salting's place in the pre-AQE toolkit. The SPARK-29544 design doc lists "add prefix to the skewed keys to make the same key be different and then adjust the data distribution" as one of three manual approaches used before adaptive execution existed, alongside raising `spark.sql.shuffle.partitions` and raising the broadcast hash join threshold "to change the sort merge join to broadcast hash join as far as possible". It dismisses all three as carrying "lots of limitations" and requiring manual processing, which is exactly the gap AQE's skew-join optimization was built to close[^spark-spip-aqe-skew].

That automatic alternative does carry documented, numeric thresholds, useful for judging when salting would even be warranted: a partition counts as skewed if it's larger than `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (default 5.0) times the median partition size, and also larger than `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default 256 MB)[^spark-configuration][^spark-sql-perf-tuning]. Databricks' skew-hint mechanism is the other documented alternative to hand-rolled salting: a `/*+ SKEW(...) */` hint names the skewed relation and column(s) and, optionally, the specific skewed key values, letting the planner target just those keys instead of relying on automatic detection[^databricks-skew-join].

[UNRESOURCED]: the specific salt-count formula (salt count as a function of skew ratio or target partition count) isn't in the corpus. It would need a dedicated skew-handling walkthrough that works a numeric salting example, rather than the AQE and skew-hint reference docs retrieved here.
