## How does each format expire old snapshots/versions and reclaim storage, and what are the default retention windows — Delta Lake VACUUM and log retention, Iceberg expire_snapshots and orphan-file removal, and the Hudi cleaner?

Delta Lake reclaims storage with the `VACUUM` command, which removes data files no longer referenced by the table and older than a retention threshold; VACUUM is not triggered automatically and must be run explicitly[^delta-utility]. The default retention threshold is 7 days[^delta-utility]. VACUUM deletes only data files, not transaction log files. Log files are removed automatically and asynchronously after checkpoint operations, with a default log retention of 30 days configurable through the `delta.logRetentionDuration` table property[^delta-utility]. Once VACUUM runs, the ability to time-travel to a version older than the retention period is lost[^delta-utility]. Retention can be overridden per run, e.g. `VACUUM table RETAIN 100 HOURS` or `deltaTable.vacuum(100)`[^delta-utility]. Delta recommends never dropping the retention interval below 7 days, since older snapshots and uncommitted files can still be in use by concurrent readers or writers; a safety check blocks shorter intervals unless `spark.databricks.delta.retentionDurationCheck.enabled` is explicitly set to `false`[^delta-utility]. Delta 3.3+ also offers a `VACUUM ... LITE` mode, which uses the transaction log to find files to remove within the retention duration instead of listing the whole table directory[^delta-utility].

Iceberg expires old snapshots with the `expire_snapshots` stored procedure. Each write/update/delete/upsert/compaction produces a new snapshot while retaining old data and metadata for snapshot isolation and time travel; `expire_snapshots` removes older snapshots and only the data/delete/manifest files uniquely required by those expired snapshots, never touching files still needed by a non-expired snapshot[^iceberg-spark-procedures]. Its default `older_than` is 5 days ago, and `retain_last` (ancestor snapshots always preserved regardless of age) defaults to 1[^iceberg-spark-procedures]. Snapshots referenced by branches or tags are not removed: branches and tags never expire by default, though the policy can be changed with the `history.expire.max-ref-age-ms` table property, and the main branch never expires[^iceberg-spark-procedures]. More generally, Iceberg's snapshot retention policy is governed by the table/branch properties `min-snapshots-to-keep`, `max-snapshot-age-ms`, and `max-ref-age-ms`[^iceberg-spec]. Separately, the `remove_orphan_files` action cleans up files under the table location that are not referenced by any table metadata (for example, left behind by failed jobs[^iceberg-maintenance]); its default `older_than` is 3 days ago[^iceberg-spark-procedures]. Iceberg warns that running orphan-file removal with a retention interval shorter than the time expected for in-flight writes to complete is dangerous, since it can delete in-progress files and corrupt the table[^iceberg-maintenance]. Old metadata JSON files are also kept by default; the number tracked is controlled by `write.metadata.previous-versions-max` (default 100), and setting `write.metadata.delete-after-commit.enabled` (default `false`) to `true` makes the writer delete the oldest tracked metadata file on each new commit; untracked/orphaned metadata files fall outside this mechanism and can only be removed by orphan-file deletion[^iceberg-maintenance].

Hudi's cleaner is a table service that reclaims space from older file versions kept for MVCC-based snapshot isolation between writers and readers[^hudi-cleaning]. Automatic cleaning is enabled by default and runs inline immediately after each commit to delete older file slices; it can instead be scheduled after every few commits via `hoodie.clean.max.commits`[^hudi-cleaning]. The default cleaning policy is `hoodie.clean.policy = KEEP_LATEST_COMMITS`[^hudi-cleaning]. Under `KEEP_LATEST_COMMITS`, the cleaner retains a configurable number of recent commits before cleaning older file versions, via `hoodie.clean.commits.retained`, which defaults to 10[^hudi-cleaning]. Two other Spark-based cleaning policies exist: `KEEP_LATEST_FILE_VERSIONS`, which keeps a fixed number of file versions per file group regardless of time (`hoodie.clean.fileversions.retained`), and `KEEP_LATEST_BY_HOURS`, which cleans commits older than a configured number of hours (`hoodie.clean.hours.retained`)[^hudi-cleaning]. Automatic cleaning itself is controlled by `hoodie.clean.automatic`, which defaults to `true`[^hudi-cleaning]; cleaning can also be run asynchronously alongside writing by setting `hoodie.clean.async=true`[^hudi-cleaning].
