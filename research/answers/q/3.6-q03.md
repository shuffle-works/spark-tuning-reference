## Q3. What is the bypass merge threshold (spark.shuffle.sort.bypassMergeThreshold)? When does Spark use the bypass path and what are the trade-offs?

`spark.shuffle.sort.bypassMergeThreshold` defaults to 200 (added in 1.1.1). In the sort-based shuffle manager, it controls when Spark avoids merge-sorting the shuffle data: the bypass path is used when there is no map-side aggregation and the number of reduce partitions is at most this threshold[^spark-configuration].

The Spark 3.5 source spells out the trade-off directly, in the comment on `SortShuffleManager.registerShuffle`: when there are fewer than `bypassMergeThreshold` partitions and no map-side aggregation is needed, Spark writes `numPartitions` files directly per map task and just concatenates them at the end, rather than merge-sorting spilled files. This avoids serializing and deserializing the data twice, which the normal code path would do to merge spills. The documented downside is having multiple files open at a time, and thus more memory allocated to buffers[^spark-source-shuffle-manager]. So the bypass path trades a doubled serialize/deserialize cost for more open file handles and buffer memory, which stays cheap only while the reduce-side partition count is small.
