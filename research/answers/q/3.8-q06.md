## Q6. What is the CPU/memory trade-off of MEMORY_AND_DISK_SER vs MEMORY_AND_DISK? At what data size does serialization save enough memory to be worth the CPU cost?

`MEMORY_AND_DISK_SER` behaves like `MEMORY_AND_DISK` except that data kept in memory is also serialized (data on disk is always serialized under either level)[^learning-spark-2e]. Serializing what would otherwise be full JVM objects "can save substantial space at the cost of some extra CPU time"[^spark-configuration]. Serialized byte streams use less memory than deserialized Java objects, which carry structural overhead, but reading them back requires deserialization, which costs more CPU than reading deserialized objects directly[^high-perf-spark].

The corpus gives no concrete data-size threshold or rule of thumb for when serialization's memory savings outweigh its CPU cost. That would need a benchmarking source with measured break-even points, which isn't in this reference set. This claim is [UNRESOURCED].
