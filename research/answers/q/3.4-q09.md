## How do you parallelize a JDBC read in Spark using partitionColumn, lowerBound, upperBound, numPartitions, fetchsize, or predicates, how should the partition column and bounds be chosen, and how do you avoid overloading the source database?

A plain JDBC read runs as one task: by default Spark scans the entire source table through a single `SELECT` query in a single task[^aws-glue-parallelize-tasks]. Parallel reads work by splitting that one `SELECT` into several queries, each with its own `WHERE` predicate[^aws-glue-parallelize-tasks]. Spark gives you two ways to define the split.

**Range partitioning with four options.** `partitionColumn`, `lowerBound`, and `upperBound` must be set together, along with `numPartitions`. They describe how to partition the table when reading in parallel from multiple workers[^spark-jdbc]. `partitionColumn` must be a numeric, date, or timestamp column of the table being read[^spark-jdbc]. `lowerBound` and `upperBound` only decide the partition stride. They do not filter rows, so every row in the table is still partitioned and returned[^spark-jdbc]. `numPartitions` is the maximum number of partitions used for parallelism in table reading, and it also caps the number of concurrent JDBC connections[^spark-jdbc]. The PySpark `DataFrameReader.jdbc()` method exposes the same split through its `column` argument, an alias of `partitionColumn`, and requires `lowerBound`, `upperBound`, and `numPartitions` whenever `column` is given[^pyspark-dataframereader-jdbc].

**Explicit predicates.** `DataFrameReader.jdbc()` also takes `predicates`, a list of expressions suitable for a `WHERE` clause, where each expression defines one partition of the resulting DataFrame[^pyspark-dataframereader-jdbc]. The table is read in parallel if either `column` or `predicates` is set, and when both are set, `column` wins[^pyspark-dataframereader-jdbc]. Since each expression becomes one partition, you pick the ranges yourself[^pyspark-dataframereader-jdbc].

**Choosing the column and bounds.** Databricks' reference example asks for a partition column with a uniformly distributed range of values, with `lowerBound` and `upperBound` set to the lowest and highest values to pull data for with that column[^databricks-jdbc]. It also recommends a column backed by an index in the source database, which speeds up the per-partition queries[^databricks-jdbc].

**Fetch size.** `fetchsize` sets how many rows the JDBC driver fetches per round trip. Its Spark default is `0`, and raising it helps on drivers that default to a low fetch size, such as Oracle with 10 rows[^spark-jdbc].

**Protecting the source database.** Since `numPartitions` also caps concurrent JDBC connections[^spark-jdbc], partition count is load on the database. Databricks warns that too many simultaneous queries might overwhelm the remote database, which is especially troublesome for application databases, and advises caution above 50[^databricks-jdbc]. Its reference example uses `numPartitions` 8 for an eight-core cluster, with a comment not to set it to hundreds[^databricks-jdbc]. The PySpark API docs carry the same warning: too many parallel partitions on a large cluster might crash the external database[^pyspark-dataframereader-jdbc]. When the read itself can't be parallelized further, AWS recommends a `repartition()` right after the initial load, with two or three times the available cores as a rule of thumb[^aws-glue-parallelize-tasks].

**Other connectors.** The same single-task pattern shows up elsewhere, each with its own knob. In AWS Glue, a DynamicFrame JDBC read is split with `hashfield` (or `hashexpression`) and `hashpartitions`[^aws-glue-parallelize-tasks]. A DynamoDB read's partition count comes from `dynamodb.splits`, and a Kinesis Data Streams read gets one partition per shard, so a stream with few shards yields few tasks[^aws-glue-parallelize-tasks].
