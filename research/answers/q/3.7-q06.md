## Q6. At what file size does the "too many small files" problem become measurable? Is there a task count threshold where scheduling overhead dominates?

The retrieved corpus does not give a specific file-size number at which the small-file problem becomes measurable. [UNRESOURCED for a quantified byte threshold; would need a benchmark isolating file-count/size vs. job wall-clock time]. What it does establish qualitatively: "when you're writing lots of small files, there's a significant metadata overhead that you incur managing all of those files. Spark especially does not do well with small files, although many file systems (like HDFS) don't handle lots of small files well, either"[^definitive-guide-3]. Spark 2.2 introduced `maxRecordsPerFile` specifically to let users target an optimum output file size by capping the number of records written per file (e.g., `df.write.option("maxRecordsPerFile", 5000)`)[^definitive-guide-3].

On the task-count/scheduling-overhead side, the closest documented threshold is a task-duration one rather than a task-count one: Spark's tuning guide notes that "Spark can efficiently support tasks as short as 200 ms, because it reuses one executor JVM across many tasks and it has a low task launching cost, so you can safely increase the level of parallelism to more than the number of cores in your clusters"[^spark-tuning-guide-1], and separately recommends "2-3 tasks per CPU core in your cluster" as a general parallelism target[^spark-tuning-guide-1]. This implies scheduling/launch overhead becomes proportionally significant only below roughly that 200ms-per-task floor, but the corpus does not state an explicit task-count threshold at which scheduling overhead dominates total runtime.
