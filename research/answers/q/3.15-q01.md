## Q1. What is the exact default of spark.sql.shuffle.partitions in Spark 3.0+ with AQE enabled — is the effective default different when coalescing is on?

The config default itself does not change: `spark.sql.shuffle.partitions` is 200, unchanged since version 1.1.0, and AQE does not override that number[^spark-sql-perf-tuning][^definitive-guide][^learning-spark-2e].

What AQE changes is the *effective* number of shuffle partitions used at runtime. `spark.sql.adaptive.enabled` defaults to true[^spark-configuration], and when it is on together with `spark.sql.adaptive.coalescePartitions.enabled` (also default true, since 3.0.0), Spark merges contiguous small post-shuffle partitions instead of running one task per configured partition[^spark-sql-perf-tuning]. The initial partition count going into that coalescing step is set by `spark.sql.adaptive.coalescePartitions.initialPartitionNum`; if unset, it equals `spark.sql.shuffle.partitions` (still 200)[^spark-sql-perf-tuning].

The coalescing target isn't simply "64MB" out of the box. `spark.sql.adaptive.coalescePartitions.parallelismFirst` defaults to true (since 3.2.0), and when true Spark *ignores* the target size set by `spark.sql.adaptive.advisoryPartitionSizeInBytes` (default 64MB) and computes an adaptive target from the cluster's default parallelism, respecting only the floor set by `spark.sql.adaptive.coalescePartitions.minPartitionSize` (default 1MB)[^spark-sql-perf-tuning][^spark-source-sql-conf]. Spark's docs recommend setting `parallelismFirst=false` on busy clusters to get stricter, size-based coalescing[^spark-sql-perf-tuning].

So with AQE and coalescing on (the 3.0+ default), 200 is just the starting point for the shuffle stage; the actual number of reduce tasks is reduced based on measured data volume, as databricks' AQE writeup shows[^databricks-aqe]. This is also why Learning Spark notes the static 200 default is "too high for smaller or streaming workloads"[^learning-spark-2e].
