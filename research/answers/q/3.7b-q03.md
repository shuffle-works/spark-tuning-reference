## How does data clustering to co-locate related rows compare across the formats: Delta Lake Z-order versus liquid clustering, Iceberg sort orders and rewrite_data_files sort/zorder strategies, and Hudi clustering?

Delta Lake's Z-Ordering (multi-dimensional clustering) is a technique to colocate related information in the same set of files; this co-locality is automatically used by Delta Lake's data-skipping algorithms, dramatically reducing how much data Spark needs to read[^delta-optimize]. It runs via `OPTIMIZE table ZORDER BY (col1, col2, ...)` (or `deltaTable.optimize().executeZOrderBy(col)`), and works best on high-cardinality columns that are commonly used in query predicates; the effectiveness of the co-locality drops with each additional ZORDER column, and Z-Ordering is not idempotent, since each run creates a new clustering of all files in a partition, both new files and ones from a previous Z-Ordering[^delta-optimize]. Delta's documentation set also lists liquid clustering as its own, separately documented table-layout feature alongside Z-Ordering[^delta-optimize]. Iceberg exposes clustering through the `rewrite_data_files` procedure's `strategy` argument, which is `binpack` (the default) or `sort`, combined with a `sort_order` argument: for Z-order, a comma-separated list of columns inside `zorder(...)` (e.g. `zorder(c1,c2,c3)`); otherwise a comma-separated list of `ColumnName SortDirection NullOrder` clauses, defaulting to the table's existing sort order when omitted[^iceberg-spark-procedures]. For example, `CALL catalog_name.system.rewrite_data_files(table => 'db.sample', strategy => 'sort', sort_order => 'id DESC NULLS LAST,name ASC NULLS FIRST')` sorts explicitly on named columns, while `CALL catalog_name.system.rewrite_data_files(table => 'db.sample', strategy => 'sort', sort_order => 'zorder(c1,c2)')` Z-orders on `c1` and `c2`[^iceberg-spark-procedures]. The plain sort strategy has its own tuning options: `compression-factor` adjusts the on-disk-size estimate used to size the Spark sort's shuffle partitions, and `shuffle-partitions-per-file` sets how many shuffle partitions Iceberg's custom coalesce operation stitches back into one sorted output file; the zorder variant adds `var-length-contribution` (bytes considered from a variable-length column) and `max-output-size` (bytes interleaved by the ZOrder algorithm)[^iceberg-spark-procedures]. At the table-spec level, each data or delete file is associated with a sort order by that order's id within its manifest, order id 0 is reserved for the unsorted order, and a table declares all its sort orders for lookup, optionally naming a default sort order id that new writes should follow, though writers aren't required to honor it when doing so would be prohibitively expensive, as for streaming writes[^iceberg-spec].

Hudi's clustering is a table service, distinct from compaction, that reorganizes data without slowing ingestion: compaction merges Merge-on-Read delta logs into base files, while clustering rewrites file groups purely to improve layout, either by stitching small files into larger ones or by sorting rows on a chosen key so that data frequently queried together ends up co-located[^hudi-clustering]. Clustering runs as a two-phase "REPLACE" action: a plan phase picks eligible file groups using a pluggable plan strategy (size-based strategies such as `SparkSizeBasedClusteringPlanStrategy`, which groups files under a size cap and excludes files already above the small-file limit; `SparkSingleFileSortPlanStrategy`, which keeps a single output group per partition and preserves the file group ID; `SparkConsistentBucketClusteringPlanStrategy` for expanding consistent-bucket-index tables; and `CommitBasedClusteringPlanStrategy`, which groups file slices by the commits that produced them rather than by size), and an execution phase applies an execution strategy class to rewrite each group[^hudi-clustering]. The default execution strategy, `SparkSortAndSizeExecutionStrategy`, uses `bulk_insert` to rewrite the input file groups, sorting by the columns named in `hoodie.clustering.plan.strategy.sort.columns` while meeting the configured target file size; this sort-column config is exactly the "cluster by sort key" mechanism Hudi uses to co-locate rows matching common query predicates instead of leaving them ordered by arrival time[^hudi-clustering]. A separate `SparkStreamCopyClusteringExecutionStrategy` (available since Hudi 1.2.0) instead performs binary file stitching, a byte-level copy with no re-read/re-write of records, which is faster but skips sorting, so it only applies when the goal is pure small-file consolidation and no sort order is required[^hudi-clustering]. Since Hudi 1.2.0, the order in which file slices themselves get packed into clustering groups is also configurable via `hoodie.clustering.plan.strategy.file.slices.sort.by` (`SIZE`, largest-first, by default, or `INSTANT_TIME`, oldest-first)[^hudi-clustering]. Clustering builds on Hudi's MVCC design so writers can keep inserting while clustering runs in the background, and it produces a new file-group version while readers keep snapshot isolation; it can only be scheduled for tables or partitions not currently receiving concurrent updates[^hudi-clustering][^hudi-file-sizing]. Practically, Hudi also uses clustering to fix file sizes after workloads like `BULK_INSERT` without sort modes, governed by `hoodie.clustering.plan.strategy.small.file.limit` (default 314572800 bytes on Spark) and `hoodie.clustering.plan.strategy.target.file.max.bytes` (default 1073741824 bytes)[^hudi-file-sizing].
