## Q1. What are the most commonly cited Spark anti-patterns in practitioner literature?

Practitioner checklists converge on a recurring set of mistakes rather than exotic ones. The most frequently cited:

- **Staying on the RDD API instead of DataFrame/Dataset.** RDDs are "lambda-driven": Spark cannot see inside the closures, so it cannot apply predicate pushdown, filter reordering, Adaptive Query Execution, or cost-based join reordering. The RDD-based MLlib API is called out as being in maintenance mode for the same reason[^luminousmen-optimization-checklist].
- **Wrong file format / schema handling.** Reading raw CSV or JSON without an explicit schema forces a full data scan just to infer types; Parquet is recommended for analytical workloads because column pruning, predicate pushdown, and stats-based file skipping work out of the box[^luminousmen-optimization-checklist].
- **Non-splittable compression.** A large GZIP file can't be split across executors, so one node must decompress the whole file alone; Snappy, LZ4, or ZSTD are recommended instead because they're splittable[^luminousmen-optimization-checklist].
- **Storing data as JSON instead of a binary columnar/row format.** JSON has to be re-parsed on every read; Avro, Parquet, Thrift, or Protobuf structs stored in a sequence file avoid the repeated parsing cost[^cloudera-tuning-spark].
- **Not registering custom Kryo classes**, which increases serialized-record size and hurts serialized cache storage levels (e.g., `MEMORY_SER`)[^cloudera-tuning-spark].
