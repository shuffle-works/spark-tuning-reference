## Is spark.python.worker.memory a hard limit enforced by the JVM, or just a hint? What happens when a Python worker exceeds it?

It's a soft threshold, not a hard limit, and it cannot be JVM-enforced in the first place, because a PySpark worker is a separate OS process outside the JVM heap[^luminousmen-memory-management]. Per its documented behavior, `spark.python.worker.memory` (default `512m`) is "the amount of memory to use per python worker process during aggregation... If the memory used during aggregation goes above this amount, it will spill the data into disks"[^spark-configuration]. It's a spill trigger for the worker's own aggregation buffering, not a cap the JVM polices.

If a Python worker's actual memory footprint keeps growing beyond that point (for example due to code paths that don't spill, oversized single records, or native library allocations), nothing in the JVM stops it. The only related guardrail is `spark.executor.pyspark.memory`, which if set will actually try to bound PySpark's memory per executor, but that limiting depends on Python's `resource` module and inherits its platform limitations: it isn't supported on Windows, and "actual resource is not limited on MacOS" even when set[^spark-configuration]. Absent that config, PySpark memory usage is folded into `spark.executor.memoryOverhead` by default[^spark-configuration], so the practical backstop is the container limit: once the executor's combined footprint (heap + overhead, which includes PySpark memory when `spark.executor.pyspark.memory` is unset) exceeds what YARN or Kubernetes granted, the whole container/pod gets killed rather than the Python worker being throttled[^spark-configuration][^luminousmen-memory-management].
