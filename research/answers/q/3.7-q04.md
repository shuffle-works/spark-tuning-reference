## Q4. What statistics does Parquet collect per row group (min/max, null count, bloom filters)? Which are used for predicate pushdown in Spark?

Parquet records column statistics (including min/max values) per column chunk within each row group, and additionally supports an optional `ColumnIndex` structure that stores page-level min/max values (with writers permitted to truncate large values to bound index size) so that "for ordered columns, this allows a reader to find matching pages by performing a binary search in min_values and max_values. For unordered columns, a reader can find matching pages by sequentially reading min_values and max_values"[^parquet-format-spec-4]. Parquet also supports optional Bloom filters per column, motivated specifically by cases where a dictionary would be too large: "when there are too many distinct values, writers sometimes choose not to add dictionaries because of the extra space they occupy. This leaves columns with large cardinalities and widely separated min and max without support for predicate pushdown," which a compact Bloom filter (no false negatives, configurable false-positive rate) resolves[^parquet-bloom-filters].

On the Spark side, these statistics feed query planning: "Statistics that Spark reads directly from the underlying data source, like the counts and min/max values in the metadata of Parquet files. These statistics are maintained by the underlying data source"[^spark-sql-perf-tuning-2]. The mechanism is gated by `spark.sql.parquet.filterPushdown` (default `true`, since Spark 1.2.0), which "enables Parquet filter push-down optimization"[^spark-configuration-1]. A related, more aggressive feature, `spark.sql.parquet.aggregatePushdown` (default `false`, since 3.3.0), pushes `MIN`, `MAX`, and `COUNT` aggregate expressions down to Parquet's footer statistics directly, throwing an exception if the required statistics are missing from any file's footer[^spark-configuration-1].
