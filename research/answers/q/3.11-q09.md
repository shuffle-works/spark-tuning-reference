## Q9. Is there a documented maximum number of executors beyond which Spark scheduling overhead degrades performance?

[UNRESOURCED for a specific documented maximum executor count — none of the retrieved chunks state a numeric ceiling beyond which Spark's own task-scheduling overhead degrades performance; this would need a source explicitly benchmarking or documenting scheduler behavior at very high executor counts.]

The corpus does document a related but distinct overhead: with dynamic allocation, requesting more executors than a workload's task count can use wastes resources. `spark.dynamicAllocation.executorAllocationRatio` (default `1.0`, added in 2.4.0) addresses this: "By default, the dynamic allocation will request enough executors to maximize the parallelism according to the number of tasks to process. While this minimizes the latency of the job, with small tasks this setting can waste a lot of resources due to executor allocation overhead, as some executor might not even do any work. This setting allows to set a ratio that will be used to reduce the number of executors w.r.t. full parallelism"[^spark-configuration]; e.g. `0.5` halves the target executor count computed by dynamic allocation[^spark-configuration]. This addresses per-task/per-executor allocation overhead with small tasks, not a scheduler-scaling ceiling on total executor count.
