## Q7. Does groupBy().agg() always produce a shuffle? Are there cases where Spark can avoid it (e.g., input is already partitioned by the group key)?

No. `groupBy()` on a DataFrame is a wide transformation and normally requires an `Exchange` (shuffle) so all rows for a key land on the same partition[^learning-spark-2e], but Spark can skip that exchange when it already knows the data is co-partitioned by the grouping key. The clearest documented case is Hive-style bucketing plus sorting: once a table is bucketed on the join/group key, the physical plan drops the `Exchange` node because the data was already shuffled at write time[^taboola-bucketing-shuffle]. Storage Partition Join generalizes this for join queries against compatible V2 sources, letting Spark "try to avoid a shuffle if possible" based on the reported partitioning[^spark-sql-perf-tuning].

Note that `DataFrame.repartition(key)` is a one-time, explicit shuffle you can reuse: after repartitioning and caching by a key, subsequent joins on that same key skip their own shuffle because the data is already partitioned that way[^luminousmen-partition-tuning]. The counterexample is `partitionBy` on write: it changes the on-disk directory layout but is "not the equivalent" of an in-memory repartition for aggregations: `df.groupBy('key').sum()` still requires an `Exchange`/shuffle over data written with `partitionBy`[^luminousmen-partition-tuning].
