## Q7. Does mergeSchema in spark.read.parquet handle type widening (e.g., int -> long)? What happens on a type conflict it cannot resolve?

`spark.sql.parquet.mergeSchema` (default `false`, since 1.5.0) does merge schemas collected across all data files rather than picking one arbitrarily: "when true, the Parquet data source merges schemas collected from all data files, otherwise the schema is picked from the summary file or a random data file if no summary file is available"[^spark-source-sql-conf]. The retrieved documentation for this option describes only that merging behavior at a high level and a usage example (`session.read.option("mergeSchema", "true").format("parquet").load(path)`)[^high-perf-spark-1]; it does not document the specific type-promotion rules Parquet's schema merger applies (e.g., whether an `int` column in one file and a `long` column in another are silently widened to `long`), nor what error Spark raises when it encounters a genuinely unresolvable type conflict between files. [UNRESOURCED for the exact type-widening/conflict-resolution behavior; would need Spark's `ParquetSchemaConverter`/schema-merging source, or a Spark JIRA describing `mergeSchema` type-promotion semantics.]

A related but distinct schema-evolution behavior is documented for Delta Lake's own `mergeSchema` option (not plain Parquet): adding a new column via `.option("mergeSchema", "true")` on write causes existing rows, when read back, to have the new column's value treated as `NULL`[^learning-spark-2e-2]. This is column addition, not numeric type widening, and does not directly answer the int→long question, but it's the nearest documented mergeSchema conflict-handling behavior in the retrieved corpus.
