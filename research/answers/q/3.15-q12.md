## Q12. What does `spark.executor.memoryOverhead` cover (off-heap / non-JVM memory), what is its default floor, and how does setting it too low cause the container to be OOM-killed by the resource manager?

`spark.executor.memoryOverhead` covers everything an executor needs outside the JVM heap specified by `spark.executor.memory`: thread stacks, JIT buffers, metaspace, JNI, native libraries, and, if `spark.executor.pyspark.memory` isn't set separately, the memory used by PySpark's per-task Python worker processes as well[^luminousmen-memory-management]. If left unset, Spark defaults this to the greater of 10% of executor memory or 384 MB[^luminousmen-memory-management]. In the configuration reference's terms, this floor is formalized as `spark.executor.minMemoryOverhead` (default `384m`, since Spark 4.0), which is the minimum non-heap allocation applied when `spark.executor.memoryOverhead` isn't set directly, while `spark.executor.memoryOverheadFactor` (since 3.3.0) controls the percentage, defaulting to 0.10, or 0.40 for non-JVM jobs on Kubernetes, since such jobs need more non-JVM heap space and commonly fail with "Memory Overhead Exceeded" errors otherwise[^spark-configuration].

The container-killing failure mode arises because the resource manager (YARN's NodeManager, or the Kubernetes kubelet) allocates a container/pod sized to the sum of executor memory, memory overhead, off-heap size, and PySpark memory: the configuration reference states the maximum container memory for a running executor "is determined by the sum of `spark.executor.memoryOverhead`, `spark.executor.memory`, `spark.memory.offHeap.size` and `spark.executor.pyspark.memory`"[^spark-configuration]. If a workload turns on off-heap memory (`spark.memory.offHeap.size`) or relies on PySpark worker processes without correspondingly increasing `memoryOverhead`, that extra memory isn't counted in the container's requested size. It's still consumed at the process level, though: the resource manager tracks actual RSS usage, not just JVM heap. Once real usage exceeds the allocated container size, the executor gets killed by YARN or OOMKilled by the Kubernetes kubelet, with no Spark-level error, just an abrupt process death[^luminousmen-memory-management].
