## Q2. Does Snappy compression support block-level splitting in Parquet? If not, how does Parquet achieve parallelism despite non-splittable Snappy?

No. Snappy itself has no split points. Google's format description says the Snappy stream format has "no entropy encoder backend nor framing layer -- the latter is assumed to be handled by other parts of the system"[^snappy-format]. Splittability is not a property of the raw Snappy byte stream; any container using Snappy has to provide its own way to locate independent, separately-decodable chunks.

Parquet provides exactly that mechanism at the container level, independent of which codec compresses the bytes. A Parquet file's `FileMetaData` footer records the offset and size of every row group and column chunk, and "readers are expected to first read the file metadata to find all the column chunks they are interested in. The column chunks should then be read sequentially"[^parquet-format-spec-2]. Because compression and encoding are applied within each column chunk/page rather than as one continuous stream across the whole file, a reader (or a Spark task) can seek directly to a row group's recorded offset via the footer and decode from there; it does not need to decompress the file from byte zero the way a single monolithic `.snappy` stream would require. This is why Parquet files compressed with Snappy remain splittable across row groups even though the Snappy format itself has no internal split points[^snappy-format][^parquet-format-spec-2].
