## What join strategies does Spark SQL support, and how does the optimizer choose between them?

Spark SQL's Catalyst optimizer has five concrete physical join operators to choose from: broadcast hash join, broadcast nested loop join, shuffle hash join, shuffle sort-merge join (SMJ), and shuffle-and-replicate nested loop (cartesian) join[^high-perf-spark]. Broadcast hash avoids a shuffle entirely and is used whenever one side is small enough; it supports every join type except full outer and requires an equi-join condition[^high-perf-spark]. Broadcast nested loop join is similar but drops the equi-join restriction, supporting non-equi conditions and every join type, at the cost of scanning one side repeatedly, so it's normally a last resort because it can be slow or run out of memory[^high-perf-spark]. Shuffle-and-replicate (cartesian) joins compute every partition against every other partition and are the most likely to blow up in data size[^high-perf-spark]. Unlike hand-tuned RDD joins, where you control the partitioner directly, Spark SQL's optimizer can also push down or reorder other operations automatically to make the eventual join cheaper[^high-perf-spark].

Spark's communication strategy for a join is binary: either an all-to-all shuffle join or a broadcast join that replicates the small side once and then lets every node join locally without further communication[^definitive-guide]. The primary signal the optimizer uses to pick between broadcast and a shuffle-based join is relation size relative to `spark.sql.autoBroadcastJoinThreshold`, informed by table/column statistics (inspectable via `DESCRIBE EXTENDED`) and the cost estimates shown in `EXPLAIN COST` / `.explain(mode="cost")`[^spark-sql-perf-tuning]. Since Spark 3.2, Adaptive Query Execution (AQE, on by default) re-optimizes the plan mid-execution using accurate runtime statistics rather than only the pre-execution estimates, which is why the physical join operator can change after the shuffle stage actually runs[^spark-sql-perf-tuning].
