## How does each table format compact small files into larger ones — Delta Lake OPTIMIZE bin-packing, Iceberg rewrite_data_files, and Hudi compaction/clustering — and how is each triggered (manual command, procedure, or automatic/inline)?

**Delta Lake.** The `OPTIMIZE` command coalesces small files into larger ones ("bin-packing"), available since Delta Lake 1.2.0[^delta-optimize]. It is run manually, via `OPTIMIZE delta_table_name;` or, with an optional partition predicate, `OPTIMIZE delta_table_name WHERE date >= '2017-01-01'`, or from the Python/Scala API (`deltaTable.optimize().executeCompaction()`, with an optional `.where(...)` predicate), available from Delta Lake 2.0 and above[^delta-optimize]. Bin-packing is idempotent (a second run on the same data has no effect) and targets evenly-balanced file sizes on disk rather than an even tuple count per file, though the two are usually correlated; setting `spark.databricks.delta.optimize.repartition.enabled=true` makes OPTIMIZE use `repartition(1)` instead of `coalesce(1)` for better performance when compacting many small files[^delta-optimize]. Beyond the manual command, Delta Lake 3.1.0+ adds **auto compaction**: it runs automatically and synchronously on the same cluster right after a write succeeds, compacts only files not already compacted, and is gated by a configurable minimum number of small files per partition before it triggers; output file size is controlled via `spark.databricks.delta.autoCompact.maxFileSize`[^delta-optimize]. A related manual command, `REORG TABLE ... APPLY (PURGE)`, rewrites files containing rows marked deleted by deletion vectors; if the resulting rewritten files come out small, REORG TABLE also coalesces them into larger ones, and the operation is idempotent[^delta-deletion-vectors].

**Iceberg.** The retrieved Iceberg reference documents the `rewrite_position_delete_files` procedure in detail: it performs minor compaction of small position delete files into larger ones (reducing manifest metadata size and the overhead of opening many small delete files) and removes dangling deletes, meaning position delete records that reference data files no longer live, which can persist after a `rewrite_data_files` run[^iceberg-spark-procedures]. It is invoked as a table procedure with a `table` argument, an optional `where` filter predicate, and options such as `max-concurrent-file-group-rewrites` (default 5)[^iceberg-spark-procedures]. **Hudi.** Hudi splits small-file handling into two distinct table services. **Compaction** applies only to Merge-on-Read (MOR) tables: MOR stores inserts in a base (columnar) file and appends updates to row-based log files, and compaction periodically merges the log files into the base file to produce a new base file version, bounding log growth and read latency; it does not apply to Copy-on-Write (COW) tables[^hudi-compaction]. Compaction runs in two steps: scheduling (scanning partitions and selecting file slices to compact, writing a compaction plan to the Hudi timeline) and execution (reading the plan and compacting the file slices)[^hudi-compaction]. Scheduling is governed by a **trigger strategy** (`hoodie.compact.inline.trigger.strategy`, default `NUM_COMMITS`, with options `NUM_COMMITS_AFTER_LAST_REQUEST`, `TIME_ELAPSED`, `NUM_AND_TIME`, `NUM_OR_TIME`) and a separate **compaction strategy** that picks which file groups to compact (`hoodie.compaction.strategy`, default `LogFileSizeBasedCompactionStrategy`, with alternatives such as `LogFileNumBasedCompactionStrategy`, `BoundedIOCompactionStrategy`, `BoundedPartitionAwareCompactionStrategy`, `DayBasedCompactionStrategy`, and `UnBoundedCompactionStrategy`)[^hudi-compaction]. By default compaction runs **async**, alongside ingestion without blocking it (the default for streaming models like Hudi Streamer continuous mode, Flink, and Spark Structured Streaming)[^hudi-compaction]. It can instead run **inline** (synchronously, as part of the same write job) by setting `hoodie.compact.inline = true` for Spark Datasource/Spark SQL writers, or via the `--disable-compaction` flag in Hudi Streamer sync-once mode[^hudi-compaction]. It can also be triggered **manually/offline**: through the Hudi CLI (`compaction run --tableName <table_name> --parallelism <parallelism> --compactionInstant <InstantTime>`) or, for Flink, by submitting `org.apache.hudi.sink.compact.HoodieFlinkCompactor` as a standalone command-line job with options like `--schedule` and `--service` (continuous monitoring mode)[^hudi-compaction].

**Clustering** is Hudi's separate data-layout service: unlike compaction (which merges log files into base files for MOR read performance), clustering stitches small files into larger ones and can additionally sort data by a key so co-located, frequently-queried data lands together[^hudi-clustering]. Users tune the ingestion-time trade-off between file size and write latency via `hoodie.parquet.small.file.limit`, which sets the smallest allowable file size that new writes get "padded" toward; clustering then rewrites the resulting layout asynchronously or synchronously[^hudi-clustering]. Clustering is one path to fixing file sizing after ingestion has already produced small files, complementing write-time auto-sizing, which uses `hoodie.parquet.small.file.limit` together with `hoodie.parquet.max.file.size` to bin-pack records into a target file size as they are written (Hudi picks files under the small-file limit and adds records until they reach the max size)[^hudi-file-sizing].
