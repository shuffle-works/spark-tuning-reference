## What is the intended mental model a practitioner should have before reading an optimization guide?

Spark code is declarative before it is anything else: transformations and actions get compiled through a logical plan, an optimized logical plan, and finally a physical plan before a single task runs[^definitive-guide]. The Catalyst optimizer does this compilation itself, constructing candidate plans and assigning costs to them, with predicate pushdown to the data source as one of the physical-plan optimizations[^high-perf-spark]. A practitioner tuning configs without this picture is turning knobs on a black box.

Underneath that plan, Spark's execution unit is the task, and tasks are grouped into stages, and stages into jobs. A new stage starts after each wide transformation, and because stages on the same RDD lineage generally run in sequence, a single slow task can hold up the whole job[^high-perf-spark]. Partitions are the atomic unit of parallelism here: one task per partition, one thread per core, so the practical target is at least as many partitions as cores per executor[^learning-spark-2e]. A commonly cited rule of thumb is roughly 4x partitions to available cores, with each task ideally running 100ms or longer. Below that, the overhead of scheduling and distributing tasks starts to dominate the actual work[^luminousmen-partition-tuning].

With that model in place, the specific levers a guide will walk through (caching, partition tuning, join strategy, statistics, adaptive query execution) sit on top of the same few things: how much data moves, how evenly it's split, and how well the optimizer's plan matches reality[^spark-sql-perf-tuning]. Configs themselves can be set three ways: cluster-wide in `conf/spark-defaults.conf`, per submission via `spark-submit --conf`, or programmatically on the `SparkSession` builder[^learning-spark-2e].
