## In a skew join with manual salting, what is the correct way to handle the NULL key case so salted and non-salted rows join correctly?

The retrieved sources describe the general salting mechanism: adding a random "salt" column to the join key on both sides so a single hot key is spread across many partitions, e.g. exploding the dimension side into one row per salt value and assigning a random salt to the fact side, then joining on the composite `(key, salt)` pair[^luminousmen-partition-tuning], and Spark's own automated alternatives to doing this by hand: AQE's skew-join handling, which splits (and replicates if needed) oversized shuffle partitions detected at runtime[^spark-spip-aqe-skew], controlled by `spark.sql.adaptive.skewJoin.enabled`[^spark-configuration], and Databricks' declarative `SKEW` hint that lets the engine construct a skew-aware plan without manual salting at all[^databricks-skew-join].

None of the retrieved chunks specifically address how a manually salted join should treat `NULL` join keys (the standard pitfall being that if both sides independently randomize a salt suffix for `NULL` keys, those `NULL` rows will carry different salts and silently fail to match, effectively dropping them from an inner join).
