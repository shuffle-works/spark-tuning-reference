## Q9. With dynamic allocation, why is an executor's shuffle output lost when the executor is reclaimed, and how does `spark.shuffle.service.enabled` (the external shuffle service) prevent the resulting `FetchFailed` and stage recompute?

During a shuffle, an executor first writes its map output to local disk and then acts as the file server for that data, serving fetch requests from other executors that need it[^spark-job-scheduling]. Before dynamic allocation existed, this was fine: an executor's on-disk state only had to survive until the whole application exited, and could be discarded the moment the executor itself exited. With dynamic allocation, the application keeps running after an individual executor is explicitly removed, so if a later stage tries to fetch shuffle blocks from an executor that's already gone, it has to recompute that state instead[^spark-job-scheduling]. This is especially likely with stragglers, tasks that run much longer than their peers, because dynamic allocation may reclaim an idle executor before a shuffle depending on it has fully completed, forcing an unnecessary recompute of the shuffle files that executor held[^spark-job-scheduling].

The external shuffle service fixes this by decoupling the shuffle data's lifetime from the executor's lifetime. It's a long-running process on each cluster node, independent of any particular Spark application's executors. When `spark.shuffle.service.enabled` is true, executors fetch shuffle blocks from this service rather than from each other. Shuffle output written by an executor can then continue being served after that executor is reclaimed, avoiding the `FetchFailed` error and the stage recompute it would otherwise trigger[^spark-job-scheduling][^spark-configuration]. The Spark configuration reference describes this directly: the service "preserves the shuffle files written by executors e.g. so that executors can be safely removed, or so that shuffle fetches can continue in the event of executor failure," and the service itself must be set up on the cluster before enabling it[^spark-configuration]. Setting up dynamic allocation requires enabling this external shuffle service on every worker node in addition to `spark.dynamicAllocation.enabled`[^definitive-guide].

As of Spark 3.0, `spark.dynamicAllocation.enabled` can alternatively rely on `spark.dynamicAllocation.shuffleTracking.enabled` (shuffle file tracking) instead of the external shuffle service to allow safe executor removal, though the underlying problem (shuffle output going unreachable when an executor is reclaimed) is the same one the external shuffle service was originally built to solve[^spark-configuration].
