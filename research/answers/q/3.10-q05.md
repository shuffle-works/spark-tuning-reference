## Q5. When AQE promotes a sort-merge join to broadcast, does it re-materialize the build side, or does it reuse the shuffle files already written?

The corpus indicates AQE reuses the already-materialized shuffle output rather than re-running the map side from scratch. The Spark SQL performance-tuning guide states the conversion happens "when the runtime statistics of any join side are smaller than the adaptive broadcast hash join threshold," and explicitly frames the benefit as avoiding re-sorting both join sides and instead reading the shuffle files locally to save network traffic, conditional on `spark.sql.adaptive.localShuffleReader.enabled` being true[^spark-sql-perf-tuning]. The same guide calls this conversion "not as efficient as planning a broadcast hash join in the first place," which is consistent with reusing existing shuffle output rather than re-materializing an equivalent-to-fresh broadcast build side[^spark-sql-perf-tuning]. The Databricks AQE post similarly describes that once the sort-merge join is converted to broadcast hash join at runtime, "we may further optimize the regular shuffle to a localized shuffle (i.e., shuffle that reads on a per mapper basis instead of a per reducer basis) to reduce the network traffic"[^databricks-aqe], again pointing at reading the existing per-mapper shuffle output locally, not recomputing it.
