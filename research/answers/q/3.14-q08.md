## Does taskMetrics.shuffleWriteMetrics.bytesWritten count bytes before or after compression, and does it include bytes spilled to disk during the shuffle write, or only the final merged output?

Spark's own metric table just calls it "Number of bytes written in shuffle operations"[^spark-history-server], without stating compression state. The `SortShuffleManager` source fills in the mechanics for the sort-based (serialized) shuffle write path: incoming records are serialized "as soon as they are passed to the shuffle writer and are buffered in a serialized form during sorting"[^spark-source-shuffle-manager]. Critically, "when the spill compression codec supports concatenation of compressed data, the spill merge simply concatenates the serialized and compressed spill partitions to produce the final output partition. This allows efficient data copying methods, like NIO's transferTo, to be used and avoids the need to allocate decompression or copying buffers during the merge."[^spark-source-shuffle-manager]

That tells us two things. First, the bytes physically written to the final shuffle data file are the serialized-and-compressed bytes (post-compression), not raw record bytes. Second, because the fast merge path concatenates the already-spilled compressed partitions directly into the final output file (via `transferTo`, without decompressing/recompressing), the final on-disk output *is* built from what was spilled to disk during sorting; there's no separate "spill bytes" pool that gets discarded before the final write. So `shuffleWriteMetrics.bytesWritten`, measuring the size of that final written shuffle output, counts compressed bytes, and in this common fast-merge path it corresponds to data that originated as on-disk spill segments during the sort rather than being written fresh at merge time.
