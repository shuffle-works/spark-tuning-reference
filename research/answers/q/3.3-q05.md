## What happens step-by-step when execution memory is exhausted during a sort or hash aggregation — what is the exact spill trigger and spill path?

Each task gets its own `TaskMemoryManager`, which arbitrates access to the shared execution pool across all tasks concurrently running on an executor. It enforces a soft per-task cap: with `n` tasks running concurrently, each task is allowed to allocate somewhere between `1/(2n)` and `1/n` of total execution memory, and the first task to arrive on an idle executor typically grabs more than its later-arriving neighbors[^luminousmen-memory-management]. This is a soft limit rather than a hard stop. When a task's sort or hash-aggregation operator keeps requesting execution-memory pages and can't get more, Spark doesn't fail immediately. It blocks the requesting task, triggers a spill of that task's in-memory data structure to disk, or, in the worst case, throws an `OutOfMemoryError`[^luminousmen-memory-management].

The spill path itself runs through Spark's map/shuffle I/O machinery: during map and shuffle operations Spark writes to and reads from local disk shuffle files, and shuffle partitions created by wide transformations like `groupBy()` or `join()` spill to the executors' local disks at the location set by `spark.local.directory`[^learning-spark-2e]. [NEEDS-REVIEW: the Q5-citable sources confirm that execution-memory exhaustion during sort/hash-aggregation causes the task to block, spill to local disk, or in the worst case throw an OOM (see the `TaskMemoryManager` behavior above), and that shuffle spill/merge I/O lands on `spark.local.dir`/`spark.local.directory`, but none of them describe the specific internal spill mechanics — e.g., the serialized ("Tungsten") sort path's `ShuffleExternalSorter` and its 8-byte record pointers, the `spark.shuffle.spill.compress`/`spark.shuffle.spill.diskWriteBufferSize` settings, how spilled runs are merged/concatenated at the end of the map task, or whether the legacy `spark.shuffle.spill` flag is still honored. Confirming those details would require Spark's shuffle source (`org.apache.spark.shuffle.sort.SortShuffleManager`/`ShuffleExternalSorter`) or the configuration reference, neither of which is citable for this question.]

SQL physical operators apply the same idea with their own row-count guardrails: `sortMergeJoinExec`'s in-memory buffer and the cartesian-product operator's buffer both spill once they cross a configured row threshold, which by default is set to the value of `spark.shuffle.spill.numElementsForceSpillThreshold`[^spark-source-sql-conf]. Whatever the trigger, the resulting spilled bytes are exposed on the task metrics as `memoryBytesSpilled`, visible in the Spark UI and event log[^spark-history-server].
