## Q1. What are the main structural differences between Parquet and ORC, and when should each be preferred?

ORC is a self-describing, type-aware columnar file format designed for Hadoop workloads[^definitive-guide-1]. Parquet is likewise a columnar format, differing from ORC mainly by optimization target rather than by fundamental structure[^definitive-guide-1]; its internal row-group and footer layout, and its row-group-size guidance, are documented under Q2 and Q3, whose queries surface the Parquet format-spec chunks that state them.

*Spark: The Definitive Guide* puts the practical difference plainly: "for the most part, they're quite similar; the fundamental difference is that Parquet is further optimized for use with Spark, whereas ORC is further optimized for Hive"[^definitive-guide-1]. ORC "has no options for reading in data because Spark understands the file format quite well"[^definitive-guide-1]: Spark treats it as a native source rather than one it has extra configuration knobs for.

On the read-path side, the chunks retrieved for this question do not document Spark's ORC/Parquet vectorized-reader configuration (e.g., `spark.sql.orc.impl`, `spark.sql.orc.enableVectorizedReader`, or the Hive-SerDe-specific `spark.sql.hive.convertMetastoreOrc` gating). [UNRESOURCED within Q1's own retrieval; this vectorized-reader behavior exists elsewhere in the corpus but not among the sources Q1's query surfaces].

Guidance from the retrieved sources: default to Parquet, the format Spark's own optimizations target[^definitive-guide-1], and use ORC when the data also has to serve Hive consumers or existing Hive ORC tables, where ORC is the better-optimized target[^definitive-guide-1].
