## Q5. spark.sql.shuffle.partitions=200 fixed: observable symptom of too few partitions (spill) vs too many (scheduling overhead) in the Spark UI?

`spark.sql.shuffle.partitions` controls how many partitions Spark creates for wide transformations (`join`, `groupBy`, aggregations) and defaults to 200 regardless of data size: "it doesn't matter if you're joining 5MB or 5TB"[^luminousmen-partitions][^spark-configuration].

**Too few partitions relative to data size** (large per-partition working set): each of the 200 partitions ends up holding more data than fits comfortably in an executor's memory, which "causes fewer tasks at a time to be processed in executors, but it increases the load on each individual executor and often leads to memory errors," and once partition size exceeds available executor memory you get disk spills[^luminousmen-partitions]. In the Spark UI this shows up on the Stages tab as "Spill (Memory)" or "Spill (Disk)" entries against a stage, a direct signal that data didn't fit and Spark had to write intermediate results to disk[^luminousmen-partitions].

**Too many partitions relative to data size** (tiny per-partition working set): with a small dataset, 200 shuffle partitions can mean each task gets on the order of ten rows: "tasks become microscopic. Most of your CPUs will just be sitting there doing nothing"[^luminousmen-partitions]. The Spark UI signature here is the inverse of the spill case: a large task/stage count where each task's duration is dominated by scheduling and bookkeeping rather than actual compute, and (if that stage also writes output) a correspondingly large number of small output files, since Spark writes one file per output partition regardless of how little data it holds[^luminousmen-partitions].

The rule of thumb given for picking a number: if tasks are processing multiple GB each and spilling, increase `spark.sql.shuffle.partitions`; if tasks finish in a couple of seconds and write tiny files, decrease it; a target of roughly 100–200 MB of data per task is offered as a starting point, tuned per dataset[^luminousmen-partitions].
