# Cluster Tuning

## Q1. What is the recommended formula for sizing Spark executors (cores × memory)?

The reference material describes a "balanced" approach rather than a single closed-form formula, worked out from three inputs: total cores per node, total memory per node, and a target of 5 cores per executor (justified by HDFS throughput; see Q2). For a 10-node cluster with 16 cores and 64GB RAM per node, the derivation is: assign `--executor-cores = 5`; reserve ~1 core per node for Hadoop/YARN/OS daemons, leaving 15 usable cores/node (150 total); `num-executors = total-usable-cores / cores-per-executor = 150/5 = 30`, minus 1 for the YARN ApplicationMaster (29); executors-per-node `= 30/10 = 3`; `memory-per-executor = mem-per-node / executors-per-node = 64GB/3 ≈ 21GB`; after subtracting ~7% for the YARN memory overhead, the usable `--executor-memory` comes out to about 18GB, yielding a recommended config of 29 executors × 5 cores × 18GB[^spark-notes-executor-sizing].

Cloudera's worked example for a 6-node cluster (16 cores/64GB per node) reaches the same shape: rather than `--num-executors 6 --executor-cores 15 --executor-memory 63G` (one "fat" executor per node), the better option is `--num-executors 17 --executor-cores 5 --executor-memory 19G`[^cloudera-tuning-spark]. Both sources treat the number of tasks (driven by executor-cores × num-executors) as the single most important tuning lever, since Spark cannot compensate for too little parallelism on its own[^cloudera-tuning-spark].

At the config level, `spark.executor.cores` controls how many concurrent tasks an executor runs and defaults to 1 in YARN mode (or all available cores on the worker in standalone mode)[^spark-configuration]; `spark.executor.memory` sets the JVM heap size per executor[^cloudera-tuning-spark]. As a general parallelism target independent of the executor-sizing formula above, the Spark tuning guide recommends 2–3 tasks per CPU core in the cluster[^spark-tuning-guide].

## Q2. Why is ≤5 cores per executor the common recommendation — what is the connection to NUMA, OS jitter, and HDFS throughput?

The retrieved material grounds the ≤5-cores rule in HDFS client behavior, not in NUMA or OS-jitter effects: "HDFS client has trouble with tons of concurrent threads. It was observed that HDFS achieves full write throughput with ~5 tasks per executor. So it's good to keep the number of cores per executor below that number"[^spark-notes-executor-sizing]. The "fat executor" case (one executor per node, using all 16 cores) shows the failure mode: "with all 16 cores per executor... HDFS throughput will hurt and it'll result in excessive garbage [collection]"[^spark-notes-executor-sizing].

## Q3. What is the exact container memory formula for YARN: spark.executor.memory + spark.executor.memoryOverhead + spark.memory.offHeap.size? Is there an additional overhead on top?

The formula, as implemented by Spark, is: `totalMemMiB = executorMemoryMiB + memoryOverheadMiB + memoryOffHeapMiB + pysparkMemToUseMiB`; on YARN this is the amount YARN allocates for the container, and on Kubernetes it becomes the pod memory limit[^luminousmen-memory-management]. So yes: there is a term beyond the three named in the question: PySpark memory (`spark.executor.pyspark.memory`) is added on top when it's explicitly configured; when it isn't, PySpark's memory use is folded into the overhead budget rather than tracked separately[^luminousmen-memory-management]. The Spark configuration reference states the same thing: "the maximum memory size of container to running executor is determined by the sum of spark.executor.memoryOverhead, spark.executor.memory, spark.memory.offHeap.size and spark.executor.pyspark.memory"[^spark-configuration].

`spark.executor.memoryOverhead` itself defaults to `max(0.1 * executorMemory, 384MB)` (10%, or 384MB, whichever is larger)[^luminousmen-memory-management][^spark-configuration]. Critically, off-heap memory is not automatically included in that overhead calculation: enabling `spark.memory.offHeap.enabled=true` with `spark.memory.offHeap.size=1g` on top of an 8G executor with default overhead (819MB) means real usage is 8192+819+1024 = 10,035MB, while the container was only granted 8192+819 = 9,011MB. The executor gets killed by YARN or OOMKilled by the Kubernetes kubelet, with no Spark-level error[^luminousmen-memory-management]. The deprecated `spark.yarn.executor.memoryOverhead` config (an older name for the same value) was removed in Spark 3.0[^luminousmen-memory-management].

## Q4. For Kubernetes, what is the difference between spark.kubernetes.executor.request.cores and spark.executor.cores? Can they be set independently, and what happens if they differ?

The retrieved material establishes a priority relationship, not a full mechanical breakdown: "Spark on K8s offers higher priority versions of spark.kubernetes.executor.limit.cores and spark.kubernetes.executor.request.cores than spark.executor.cores"[^spark-job-scheduling]. When set, the Kubernetes-specific request/limit configs take precedence over `spark.executor.cores` for the pod's resource request/limit to the Kubernetes scheduler, while `spark.executor.cores` stays the config Spark itself uses to size the number of concurrent task slots (`spark.executor.cores`, "the number of cores to use on each executor")[^spark-configuration].

## Q5. What does spark.locality.wait control exactly — is it a timeout per level (process-local → node-local → rack-local → any)? What are spark.locality.wait.node, spark.locality.wait.rack, spark.locality.wait.process?

Yes, `spark.locality.wait` (default `3s`) is documented as "How long to wait to launch a data-local task before giving up and launching it on a less-local node. The same wait will be used to step through multiple locality levels (process-local, node-local, rack-local and then any)"[^spark-configuration]. Each level can be overridden independently: `spark.locality.wait.node` "customize[s] the locality wait for node locality. For example, you can set this to 0 to skip node locality and search immediately for rack locality (if your cluster has rack information)"[^spark-configuration]; `spark.locality.wait.process` "customize[s] the locality wait for process locality. This affects tasks that attempt to access cached data in a particular executor process"[^spark-configuration]; `spark.locality.wait.rack` "customize[s] the locality wait for rack locality"[^spark-configuration]. All three default to the value of `spark.locality.wait` when not explicitly set[^spark-configuration]. The guidance is to increase the base wait if tasks are long-running and locality is poor, since the default is tuned to work well for most workloads[^spark-configuration].

## Q6. What is the interaction between dynamic allocation and shuffle tracking (spark.dynamicAllocation.shuffleTracking.enabled)? What can go wrong if shuffle tracking is disabled?

Enabling dynamic allocation (`spark.dynamicAllocation.enabled`) requires one of several supporting mechanisms to be turned on, and shuffle tracking is one of them: "This requires one of the following conditions: 1) enabling external shuffle service through spark.shuffle.service.enabled, or 2) enabling shuffle tracking through spark.dynamicAllocation.shuffleTracking.enabled, or 3) enabling shuffle blocks decommission..., or 4) (Experimental) configuring spark.shuffle.sort.io.plugin.class..."[^spark-configuration]. `spark.dynamicAllocation.shuffleTracking.enabled` itself (default `true` since Spark 3.0) "enables shuffle file tracking for executors, which allows dynamic allocation without the need for an external shuffle service. This option will try to keep alive executors that are storing shuffle data for active jobs"[^spark-configuration]. A companion `spark.dynamicAllocation.shuffleTracking.timeout` (default infinity) controls how long tracked executors are held if garbage collection of the shuffle state doesn't naturally free them[^spark-configuration].

All of these options (external shuffle service, shuffle tracking, or shuffle-block decommission) serve the same purpose: "to allow executors to be removed without deleting shuffle files written by them"[^spark-job-scheduling]. If none is enabled (shuffle tracking off and no external shuffle service configured), Spark either cannot enable dynamic allocation at all per the requirement above[^spark-configuration], or, if dynamic allocation is otherwise active and an executor holding shuffle output is removed mid-shuffle, the shuffle files it wrote are lost and must be recomputed, since nothing preserved that state beyond the executor's lifetime[^spark-job-scheduling] (see Q7 for the mechanism).

## Q7. When dynamic allocation removes an executor, are its shuffle files lost? What does the external shuffle service solve here?

Potentially yes, if nothing preserves them. During a shuffle, "the Spark executor first writes its own map outputs locally to disk, and then acts as the server for those files when other executors attempt to fetch them. In the event of stragglers, which are tasks that run for much longer than their peers, dynamic allocation may remove an executor before the shuffle completes, in which case the shuffle files written by that executor must be recomputed unnecessarily"[^spark-job-scheduling]. More generally, before dynamic allocation, an executor exiting alongside its application meant that all its state could be safely discarded; with dynamic allocation, the application keeps running after an executor is explicitly removed, so if the application later needs state written by that executor, it "will have to perform a recompute of the state"[^spark-job-scheduling]; hence Spark needing "a mechanism to decommission an executor gracefully by preserving its state before removing it"[^spark-job-scheduling].

The external shuffle service (introduced in Spark 1.2) is exactly that mechanism: "a long-running process that runs on each node of your cluster independently of your Spark applications and their executors. If the service is enabled, Spark executors will fetch shuffle files from the service instead of from each other. This means any shuffle state written by an executor may continue to be served beyond the executor's lifetime"[^spark-job-scheduling]. The same idea extends to cached data: by default, executors holding cached blocks are never removed by dynamic allocation (tunable via `spark.dynamicAllocation.cachedExecutorIdleTimeout`), and if `spark.shuffle.service.fetch.rdd.enabled` is set, the external shuffle service can also serve disk-persisted RDD blocks after their executor is gone[^spark-job-scheduling].

## Q8. What is the driver memory impact of a wide physical plan (many columns, deeply nested)? What is spark.driver.maxResultSize and how is it different from driver heap?

`spark.driver.maxResultSize` (default `1g`) is "Limit of total size of serialized results of all partitions for each Spark action (e.g. collect) in bytes. Should be at least 1M, or 0 for unlimited. Jobs will be aborted if the total size is above this limit. Having a high limit may cause out-of-memory errors in driver (depends on spark.driver.memory and memory overhead of objects in JVM). Setting a proper limit can protect the driver from out-of-memory errors"[^spark-configuration]. That is distinct from driver heap: `spark.driver.memory` (default `1g`) is "the amount of memory to use for the driver process, i.e. where SparkContext is initialized"[^spark-configuration]: the overall JVM heap available to the driver for everything it does, not just collected action results. `maxResultSize` is a guardrail specifically on the size of serialized data pulled back from executors by an action; `spark.driver.memory` is the total heap budget the driver process has to work with, and the config docs explicitly note the interaction: whether a high `maxResultSize` actually causes an OOM "depends on spark.driver.memory and memory overhead of objects in JVM"[^spark-configuration].

## Q9. Is there a documented maximum number of executors beyond which Spark scheduling overhead degrades performance?

[UNRESOURCED for a specific documented maximum executor count — none of the retrieved chunks state a numeric ceiling beyond which Spark's own task-scheduling overhead degrades performance; this would need a source explicitly benchmarking or documenting scheduler behavior at very high executor counts.]

The corpus does document a related but distinct overhead: with dynamic allocation, requesting more executors than a workload's task count can use wastes resources. `spark.dynamicAllocation.executorAllocationRatio` (default `1.0`, added in 2.4.0) addresses this: "By default, the dynamic allocation will request enough executors to maximize the parallelism according to the number of tasks to process. While this minimizes the latency of the job, with small tasks this setting can waste a lot of resources due to executor allocation overhead, as some executor might not even do any work. This setting allows to set a ratio that will be used to reduce the number of executors w.r.t. full parallelism"[^spark-configuration]; e.g. `0.5` halves the target executor count computed by dynamic allocation[^spark-configuration]. This addresses per-task/per-executor allocation overhead with small tasks, not a scheduler-scaling ceiling on total executor count.

## Q10. What is spark.task.cpus and when must it be set greater than 1? What is the interaction with spark.executor.cores for resource allocation?

`spark.task.cpus` defaults to `1` and is documented simply as "Number of cores to allocate for each task"[^spark-configuration]. The number of concurrent task slots on an executor is derived jointly from it and `spark.executor.cores`: the Spark configuration reference notes, in the context of speculative-execution slot counting, that "the number of slots is computed based on the conf values of spark.executor.cores and spark.task.cpus minimum 1"[^spark-configuration]; i.e., slots per executor ≈ `spark.executor.cores / spark.task.cpus`. Raising `spark.task.cpus` above 1 therefore reduces the number of tasks an executor runs concurrently, reserving more cores per individual task.
