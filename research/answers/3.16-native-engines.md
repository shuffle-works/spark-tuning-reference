# Native Engines

## How does Databricks Photon change Spark execution and tuning, when does it fall back to the Spark runtime, and how can you see where it ran?

Photon is the Databricks-native vectorized query engine. It accelerates SQL workloads, DataFrame API calls, ETL pipelines and stateless streaming, and it works with existing Spark APIs without code changes[^databricks-photon]. It is available only on Databricks.

### How it executes

For supported operations, Photon replaces the JVM-based Spark SQL execution engine with a native C++ runtime. The Spark query optimizer (Catalyst) still plans the query, and Photon takes over at the execution layer, processing data in columnar batches rather than row by row[^databricks-photon]. Databricks describes the effect of native C++ execution as eliminating garbage collection pauses, JIT warm-up delays and memory overhead for the work Photon runs[^databricks-photon]. The [GC pressure](#bottleneck-gc) measured on a stage therefore reflects only the work still running on the JVM.

When Photon meets an unsupported operation during execution, it transparently falls back to the Spark runtime for the remainder of that operation, and the query still returns correct results[^databricks-photon].

### Turning it on

Photon is enabled on serverless compute, SQL warehouses and serverless Lakeflow pipelines. On classic all-purpose compute, jobs compute and classic Lakeflow pipelines Databricks enables it by default, and the **Use Photon Acceleration** checkbox under **Performance** turns it on or off. Compute created through the Clusters API or Jobs API must set `runtime_engine` to `PHOTON`, and the Pipelines API uses `photon` set to `true`[^databricks-photon]. Photon instance types consume DBUs at a different rate than the same instance type running the non-Photon runtime[^databricks-photon].

### What changes for tuning

- **Joins and shuffle.** Photon replaces sort-merge joins with hash joins and uses a redesigned columnar shuffle[^databricks-photon]. The Spark-side strategy choices on the [Join Optimization](#joins) and [Shuffle](#shuffle) pages describe the JVM engine that Photon replaces for supported operators.
- **Scans and writes.** Its scan implements filter pushdown, dictionary pruning and row-group skipping, and its native Parquet writer accelerates Delta Lake, Apache Iceberg and Parquet writes, including `UPDATE`, `DELETE`, `MERGE INTO`, `INSERT` and `CREATE TABLE AS SELECT`[^databricks-photon].
- **UDFs.** Photon doesn't support UDFs, RDD APIs or Dataset APIs[^databricks-photon]. A stage built around a [Python UDF](#pyspark) runs on the Spark runtime.
- **Streaming.** Photon supports stateless streaming only. Stateful streaming is not supported[^databricks-photon].
- **Short queries.** Queries that normally finish in under two seconds see no meaningful improvement, because planning and scheduling overhead dominates their execution time[^databricks-photon].
- **Features that need it.** Predictive I/O for reads and writes, and dynamic file pruning in `MERGE`, `UPDATE` and `DELETE`, require Photon to be enabled[^databricks-photon].

### Supported operators

Photon covers scans (Parquet, Delta, CSV, JSON), filter and project, hash aggregate, hash join and shuffle, nested-loop join, null-aware anti join, union, expand, scalar subquery, the Delta and Parquet write sink, sort, top-K, limit and window functions. Databricks marks its expression and data-type categories as representative, not exhaustive, and notes that individual functions within a category may have limitations[^databricks-photon].

### Seeing where Photon ran

On classic all-purpose and jobs compute, the SQL/DataFrame tab of the Spark UI draws Photon operators in orange in the query DAG and standard Spark operators in blue. On SQL warehouses and serverless compute, the query profile's Execution Details view shows the percentage of task time spent in Photon, and the query plan marks Photon operators purple and standard operators grey. If a query isn't using Photon as expected, Databricks says to check for unsupported operations, UDFs or data formats that cause a fallback to the Spark runtime[^databricks-photon].

## Confidence

The behavior described here is documented by Databricks on its Photon page[^databricks-photon]. That page is the only source for this section, and it lists operators and expressions as representative rather than exhaustive, so a specific function can still fall back even when its category is supported. Treat the plan colors and the Photon share of task time as the check for any one query.

## Limitations / false-positive risk

Photon exists only on Databricks. Fallback happens per operation: one unsupported expression moves the remainder of that operation to the Spark runtime[^databricks-photon], so a partly accelerated stage still shows JVM-side GC, spill and serialization costs. A short query's runtime is dominated by planning and scheduling rather than data processing[^databricks-photon], which makes a missing speedup there expected, not a misconfiguration.

## How does Apache Gluten change Spark execution and tuning, when does it fall back to vanilla Spark, and how do engines built on it (Microsoft Fabric's native execution engine, Google Cloud's native query execution) differ?

Gluten is a middle layer that offloads the execution of JVM-based SQL engines to native engines[^gluten-index]. This page covers its Velox backend. Spark keeps the control flow: Gluten transforms Spark's whole-stage physical plan into a Substrait plan, sends it to the native engine, and reuses Spark's distributed control flow[^gluten-index]. The notes here follow Gluten's documentation on its main branch, which is not versioned, so check them against the release you run.

### Turning it on

The Velox backend needs four static settings: `spark.plugins` set to `org.apache.gluten.GlutenPlugin`, `spark.shuffle.manager` set to `org.apache.spark.shuffle.sort.ColumnarShuffleManager`, `spark.memory.offHeap.enabled` set to `true`, and a `spark.memory.offHeap.size`[^gluten-configuration]. Static means they are fixed when the application starts.

```properties
spark.plugins=org.apache.gluten.GlutenPlugin
spark.shuffle.manager=org.apache.spark.shuffle.sort.ColumnarShuffleManager
spark.memory.offHeap.enabled=true
spark.memory.offHeap.size=20g
```

The officially supported Spark versions are 3.4.4, 3.5.5, 4.0.2 and 4.1.1, and Spark 4.0 and 4.1 require JDK 17 or later and Scala 2.13[^gluten-velox]. On an unofficially supported Spark version, `NoSuchMethodError` can be thrown at runtime[^gluten-velox-limitations].

### Memory

Gluten allocates native memory from `spark.memory.offHeap.size` even when off-heap memory is otherwise disabled, and its configuration reference recommends a larger value if the plugin runs out of memory[^gluten-configuration]. The Velox example in its getting-started guide uses `--executor-memory 25g`, `spark.memory.offHeap.size=20g` and `spark.executor.memoryOverhead=5g`, and says to adjust executor cores, memory and off-heap size to your environment[^gluten-velox]. Two further settings shape how that memory is shared:

- `spark.gluten.memory.isolation` (default `false`) caps the off-heap memory each task can use at executor memory divided by the maximum task slots. It is recommended when Gluten serves concurrent queries in one session, because not all memory Gluten allocates is guaranteed to be spillable[^gluten-configuration].
- `spark.gluten.memory.overAcquiredMemoryRatio` (default `0.3`) lets the Velox backend over-acquire that ratio of the allocated memory as a backup against out-of-memory errors[^gluten-configuration].

The Velox backend supports spill-to-disk, and `spillStrategy` set to `auto` (the default) lets the Spark memory manager manage Velox's spilling, while `none` disables it[^gluten-velox]. Gluten's documentation warns that `OutOfMemoryException` can still occur with spill-to-disk when the shuffle partition count is large, and advises reducing it[^gluten-velox-limitations]. See [Memory Management](#memory-model) and [spill](#bottleneck-spill) for the Spark side. The experimental `spark.gluten.velox.offHeapBroadcastBuildRelation.enabled` (default `false`) stores broadcast build relations off-heap instead of on-heap[^gluten-velox].

### Joins and shuffle

The columnar shuffle is on by default (`spark.gluten.sql.columnar.shuffle`, `true`) and its codec, set with `spark.gluten.sql.columnar.shuffle.codec`, supports lz4 and zstd[^gluten-configuration]. For joins, `spark.gluten.sql.columnar.forceShuffledHashJoin` defaults to `true`, and separate switches control the columnar sort-merge join (`spark.gluten.sql.columnar.sortMergeJoin`, which "should be set with preferSortMergeJoin=false"), the broadcast join and the broadcast exchange[^gluten-configuration]. The strategy-selection rules on the [Join Optimization](#joins) page describe vanilla Spark's choices, so verify the physical plan of a Gluten job rather than assuming them.

### Fallback

Gluten falls back to vanilla Spark in several documented cases:

- ANSI mode: "If ANSI is enabled, Spark plan's execution will always fall back to vanilla Spark."[^gluten-velox-limitations]
- File formats: Gluten fully supports Parquet and partially supports ORC, and the scan falls back for other formats[^gluten-velox-limitations].
- Partitioned table scans need the partition information in the file path, and without it the scan falls back[^gluten-velox-limitations].
- Bucket writes are not supported and fall back[^gluten-velox-limitations].
- Parquet scans of the Byte type fall back[^gluten-velox-limitations].

Two settings tune fallback. `spark.gluten.sql.columnar.query.fallback.threshold` (default `-1`) is the threshold for whether a query falls back, counted from the number of `ColumnarToRow` and vanilla leaf nodes. `spark.gluten.sql.columnar.fallback.expressions.threshold` (default `50`) falls back a filter or project when the number of nested expressions reaches it, because Spark codegen can be faster in that case[^gluten-configuration].

### Seeing where it ran

To see what can be offloaded and why a part fell back, the getting-started guide says to disable AQE (`spark.sql.adaptive.enabled=false`) so that plan validation runs in Gluten, then read the physical plan with `explain()`[^gluten-velox]. In that plan, the symbol `^` marks a plan offloaded to Velox in a stage, and `VeloxColumnarToRowExec` or `GlutenRowToArrowColumnar` indicates a fallback operator before or after it[^gluten-velox]. A helper, `df.fallbackSummary` from `org.apache.spark.sql.execution.GlutenImplicits`, returns the fallback summary of a Dataset[^gluten-velox].

### Known incompatibilities

Gluten supports only Spark's default case-insensitive mode, and enabling case-sensitive mode can give incorrect results. Velox does not support NaN, so comparisons involving NaN can give unexpected results, and it handles only double-quoted strings in JSON data. Gluten ignores `spark.sql.parquet.datetimeRebaseModeInRead`, and "not all parquet configurations are honored"[^gluten-velox-limitations].

### Engines built on Gluten

**Microsoft Fabric native execution engine.** Fabric's engine is based on two open-source components, Velox and Apache Gluten. Supported operators are offloaded from the JVM to a vectorized C++ execution path, and Fabric keeps its Spark query optimizations, including AQE[^fabric-native-execution-engine]. When a query can't run natively the operation falls back to the traditional Spark engine automatically, and plan nodes with a `Transformer` suffix, `*NativeFileScan` or `VeloxColumnarToRowExec` show native execution[^fabric-native-execution-engine]. It is enabled through the environment's acceleration setting or `spark.native.enabled`, it doesn't support structured streaming, doesn't accelerate queries against JSON and XML, and on Runtime 1.3 falls back to vanilla Spark when ANSI SQL mode is on[^fabric-native-execution-engine]. Fabric describes it as suited to computationally intensive queries rather than simple or I/O-bound ones[^fabric-native-execution-engine].

**Google Cloud native query execution.** Google's native query execution is a native engine based on Apache Gluten and Velox that runs parts of a Spark query outside the JVM. It is enabled by setting `spark.dataproc.lightningEngine.runtime` to `native`[^dataproc-native-query-execution][^dataproc-spark-properties]. It falls back to standard Spark when ANSI mode is enabled, when case-sensitive mode is enabled, or when partitioned table scans lack partition information in the path[^dataproc-native-query-execution].

## Confidence

The settings, defaults and fallback cases above are taken from Gluten's own configuration reference, getting-started guide and limitations page on its main branch, and from the Fabric and Google Cloud documentation for the managed engines. Defaults in the configuration reference can change between Gluten releases, so confirm a setting against the release you run. The plan-reading guidance is documented for the Velox backend only.

## Limitations / false-positive risk

Fallback is per operator: a mostly native plan can still contain fallback operators, each marked by a transition operator in the plan[^gluten-velox]. Diagnosing fallbacks means disabling AQE[^gluten-velox], so the plan you inspect is a diagnostic view, not the AQE-enabled plan your production runs use (see [Adaptive Query Execution](#aqe)). Fabric and Google Cloud document their own limits separately, and those differ from Gluten's.

## How does Apache DataFusion Comet change Spark execution and tuning, when does it fall back to Spark, and how do you size its memory and read its plans?

Apache DataFusion Comet is a high-performance accelerator for Apache Spark. It keeps Spark queries Arrow-native end to end: operators, expressions, shuffle and broadcast all stay in Apache Arrow columnar format[^comet-readme]. Consecutive Rust-implemented operators are combined into a single block that is serialized as protobuf and executed by DataFusion on the executor[^comet-understanding-plans]. The notes here follow Comet's documentation on its main branch, which is not versioned, so check them against the release you run.

### Turning it on

The installation guide's quick start sets `spark.plugins` to `org.apache.spark.CometPlugin`, `spark.shuffle.manager` to `org.apache.spark.sql.comet.execution.shuffle.CometShuffleManager`, `spark.memory.offHeap.enabled` to `true` with a `spark.memory.offHeap.size`, and `spark.executor.memoryOverhead`, and it turns on `spark.comet.explain.fallback.enabled` to log fallback reasons[^comet-installation].

```properties
spark.plugins=org.apache.spark.CometPlugin
spark.shuffle.manager=org.apache.spark.sql.comet.execution.shuffle.CometShuffleManager
spark.comet.explain.fallback.enabled=true
spark.memory.offHeap.enabled=true
spark.memory.offHeap.size=4g
spark.executor.memoryOverhead=2g
```

Comet requires JDK 17 or later, and the installation guide recommends using it only with Spark versions where both Comet and Spark tests run in CI[^comet-installation].

### Memory

Comet shares an off-heap memory pool with Spark, sized by `spark.memory.offHeap.size`. The pool is a shared budget rather than a shared allocator: Comet's native operators allocate from the Rust heap, but every reservation they make is charged against the same pool as Spark's own off-heap consumers. An operator that cannot spill fails the task when it cannot reserve the memory it needs[^comet-tuning-memory].

Memory that Comet's accounting does not track has to fit in `spark.executor.memoryOverhead`, so enabling off-heap memory is not sufficient on its own. Setting `spark.executor.memoryOverhead` replaces the derived value (`max(spark.executor.memoryOverheadFactor * spark.executor.memory, 384 MiB)`, factor `0.1`) instead of adding to it, so a value below the derived one shrinks the container. The guide gives `2g` as a reasonable start for a small executor, says to raise `spark.executor.memoryOverheadFactor` instead for large ones, and says to raise the overhead further if the cluster manager kills executors (on Kubernetes, `ExecutorLostFailure` with exit code 137)[^comet-tuning-memory]. See [Memory Management](#memory-model) for how Spark sizes overhead.

### Shuffle

Comet tries native shuffle first, then columnar shuffle, and falls back to Spark's shuffle if neither applies. `spark.shuffle.manager` is a static setting that cannot change at runtime, so Comet shuffle is toggled at runtime with `spark.comet.shuffle.enabled`. By default Comet converts a Spark `ShuffleExchangeExec` to columnar shuffle even when its child is a non-Comet plan, at the cost of a row-to-columnar conversion at the shuffle boundary, and `spark.comet.shuffle.convertFromSparkPlan.enabled=false` opts out. The codec is set with `spark.comet.shuffle.compression.codec` (`lz4` by default, `zstd` and `snappy` also supported)[^comet-tuning-shuffle]. The tuning rules on the [Shuffle](#shuffle) page describe Spark's own shuffle.

### Joins

Vectorized engines tend to perform better with `ShuffledHashJoin`, so Comet's tuning guide suggests converting `SortMergeJoin` to it with `spark.comet.exec.forceShuffledHashJoin=true`. Comet does not yet provide spill-to-disk for `ShuffledHashJoin`, so this can run out of memory[^comet-tuning-operators]. `BroadcastHashJoinExec` is supported, and `BroadcastNestedLoopJoinExec` falls back to Spark when the preserved side is broadcast[^comet-tuning-operators]. See [Join Optimization](#joins) for the strategy rules on the Spark side.

### UDFs

The presence of a Scala or Java UDF does not force the enclosing operator out of the Comet pipeline. Python `@udf`, pandas `@pandas_udf`, aggregate and Hive UDFs are out of scope and continue to fall back to Spark[^comet-scala-java-udfs]. Comet can accelerate Python UDFs that use PyArrow-backed batch processing, such as `mapInArrow` and `mapInPandas`[^comet-pyarrow-udfs]. See [PySpark Specifics](#pyspark) for the UDF cost on the Spark side.

### Scans

Comet falls back to Spark for Parquet scans it cannot convert. The documented cases include `ShortType` columns by default, `ignoreMissingFiles` or `ignoreCorruptFiles` set to `true`, and `spark.sql.parquet.enableVectorizedReader=false`[^comet-compatibility-scans]. Pushing filter evaluation into the Parquet decode step with `spark.comet.parquet.rowFilterPushdown.enabled=true` is disabled by default because it can hurt when the filter is not selective, and the scan tuning guide's workaround for scan tasks left with no row groups is a lower `spark.sql.files.maxPartitionBytes`[^comet-tuning-scans]. See [Data Formats](#data-formats) for the Spark scan.

### Reading the plan

Operators that Comet does not support remain in their original Spark form. Fallback can be partial (a subtree falls back to Spark while the rest stays in the Comet pipeline) or full (no Comet nodes appear). Wherever data crosses between columnar and row-based execution, Comet inserts a transition node such as `CometColumnarToRow` or `CometSparkRowToColumnar`, and frequent transitions usually indicate fallback inside the plan[^comet-understanding-plans]. `spark.comet.explain.fallback.enabled` logs a warning with the reasons each query stage could not run in Comet[^comet-understanding-plans]. Under AQE the report describes the plan before any adaptive re-planning, so coverage of the plan that finally executes can differ[^comet-understanding-plans], which affects how you read it next to [Adaptive Query Execution](#aqe).

Repeated columnar-to-row and row-to-columnar conversions can dominate stage runtime. `spark.comet.exec.transitionRevert.enabled=true` reverts the whole stage to Spark row execution once the number of columnar-to-row transitions exceeds `spark.comet.exec.transitionRevert.maxTransitions` (default `2`)[^comet-tuning-transitions].

### Compatibility

Comet aims for results consistent with the Spark version in use and documents the areas where its behavior differs. Some expressions also have a native implementation that can differ from Spark for certain inputs, and these are not used unless you opt in with the relevant `spark.comet.expression.<Name>.allowIncompatible=true` setting[^comet-compatibility-index].

## Confidence

The settings, defaults and fallback cases above come from Comet's own installation guide, tuning guides and compatibility pages. Settings and their defaults can change between Comet releases, so confirm one against the release you run. The memory-sizing guidance is specific to Comet's off-heap accounting and does not replace sizing from your own executor metrics.

## Limitations / false-positive risk

Fallback is per operator or subtree, so a plan with some Comet nodes can still run stages on the Spark engine. Because the fallback report under AQE describes the plan before adaptive re-planning[^comet-understanding-plans], coverage in the final plan can differ from what the log lists.
