## Is taskMetrics.executorRunTime available for tasks that failed, or only for successful task ends?

Spark's monitoring docs only describe what `executorRunTime` measures, "elapsed time the executor spent running this task ... expressed in milliseconds"[^spark-history-server], without stating whether it's populated on failure. The `JsonProtocol` source is more informative: `taskEndToJson` serializes the `Task Metrics` field conditionally, via `Option(taskEnd.taskMetrics).foreach { m => ... taskMetricsToJson(m, g) }`[^spark-source-json-protocol]. That means `TaskMetrics` (and therefore `executorRunTime`) is an optional part of the `SparkListenerTaskEnd` payload, not guaranteed on every task end.

The same source's `taskEndReasonFromJson` / `TASK_END_REASON_FORMATTED_CLASS_NAMES` enumerates the failure reasons that can accompany a task end (`FetchFailed`, `ExceptionFailure`, `TaskResultLost`, `TaskKilled`, `TaskCommitDenied`, `ExecutorLostFailure`, `Resubmitted`, `UnknownReason`) alongside `Success`[^spark-source-json-protocol]. Its `ExceptionFailure` deserialization branch even falls back to pulling accumulator updates out of the embedded `TaskMetrics` object for old event logs ("Fallback on getting accumulator updates from TaskMetrics, which was logged in Spark 1.x")[^spark-source-json-protocol], which only makes sense if `TaskMetrics`, and thus `executorRunTime`, is normally populated for that failure type. So `executorRunTime` is available for failed tasks that got far enough to actually run (e.g. `ExceptionFailure`, `TaskKilled`), but the metrics object is optional in the schema overall and can be absent for reasons like `Resubmitted`, where the task attempt never completed on that executor.

## What is the unit of taskMetrics.jvmGCTime — milliseconds? Is it cumulative across all GC events in the task?

Yes, milliseconds. Spark's own metric description: "jvmGCTime | Elapsed time the JVM spent in garbage collection while executing this task. The value is expressed in milliseconds."[^spark-history-server] The phrasing "while executing this task" indicates the value accumulates over the task's full execution window: the sum of every GC pause that occurred during that task's run, not just the most recent pause. The `JsonProtocol` source confirms it's serialized as a single scalar long (`g.writeNumberField("JVM GC Time", taskMetrics.jvmGCTime)`)[^spark-source-json-protocol], consistent with an accumulator rather than a per-GC-event log entry.

## What exactly is taskMetrics.peakExecutionMemory tracking — Tungsten off-heap, on-heap execution pool, or both?

Q5's own retrieved chunks (spark-history-server, spark-monitoring) surface only the **executor**-level `peakMemoryMetrics.OnHeapExecutionMemory` ("Peak on heap execution memory in use, in bytes") and `.OffHeapExecutionMemory` ("Peak off heap execution memory in use, in bytes") gauges[^spark-history-server], not a description of the **task**-level `peakExecutionMemory` accumulator itself. [UNRESOURCED: Spark's monitoring docs do describe `peakExecutionMemory` as "peak memory used by internal data structures created during shuffles, aggregations and joins ... For SQL jobs, this only tracks all unsafe operators and ExternalSort," and the Tungsten/`UnsafeRow`/`sun.misc.Unsafe` background behind "unsafe operators" is accurate — but both passages surfaced under a different question's retrieval, not Q5's own top-k, so neither is citable here.]

`peakExecutionMemory` is a task-level accumulator, distinct from the separate executor-level `peakMemoryMetrics.OnHeapExecutionMemory` / `.OffHeapExecutionMemory` gauges, which report the on-heap and off-heap execution pools as two separate numbers at the executor level rather than as a single per-task figure[^spark-history-server]. Whether the task-level figure itself covers on-heap use, off-heap use, or both isn't resolvable from Q5's own retrieved chunks; that would require the [UNRESOURCED] passage above.

## What is the reason field format in SparkListenerTaskEnd for different failure types — what are the canonical reason strings?

The `JsonProtocol` source is authoritative here. The `Reason` field of a serialized `TaskEndReason` holds `Utils.getFormattedClassName(taskEndReason)`[^spark-source-json-protocol], the formatted class name of whichever `TaskEndReason` instance was assigned to that task end. Q7's own retrieved chunks show deserialization cases for `FetchFailed`, `ExceptionFailure`, `TaskResultLost`, `TaskKilled`, `TaskCommitDenied`, `ExecutorLostFailure`, and `UnknownReason`[^spark-source-json-protocol]. [UNRESOURCED: the full canonical set also includes `Success` and `Resubmitted`, per the `TASK_END_REASON_FORMATTED_CLASS_NAMES` lookup table — this is accurate, but that object and those two values only appear under a different question's retrieval (Q3), not Q7's own top-15, so they aren't citable here.]

Each reason carries type-specific extra fields on deserialization[^spark-source-json-protocol]:
- `FetchFailed`: Reduce ID, Message. [UNRESOURCED: the full field set also includes Block Manager Address, Shuffle ID, Map ID, and Map Index (the latter backfilled to `Int.MinValue` for logs written before Spark 3.0) — accurate, but those field names only appear under a different question's retrieval (Q3), not Q7's own chunks, so they aren't citable here.]
- `ExceptionFailure`: Class Name, Description, Stack Trace, Full Stack Trace, and accumulator updates (falling back to reading them out of embedded `TaskMetrics` for Spark 1.x-era logs).
- `TaskKilled`: a Kill Reason (added in Spark 2.2.0) plus optional Accumulator Updates (added in Spark 2.4.0).
- `TaskCommitDenied`: Job ID, Partition ID, Attempt Number.
- `ExecutorLostFailure`: Exit Caused By App (boolean), Executor ID, Loss Reason.
- `UnknownReason` carries no extra fields. [UNRESOURCED: `Resubmitted` also carries no extra fields, but the `Resubmitted` case doesn't appear in Q7's own retrieved chunks — only under a different question's retrieval.]

## Does taskMetrics.shuffleWriteMetrics.bytesWritten count bytes before or after compression, and does it include bytes spilled to disk during the shuffle write, or only the final merged output?

Spark's own metric table just calls it "Number of bytes written in shuffle operations"[^spark-history-server], without stating compression state. The `SortShuffleManager` source fills in the mechanics for the sort-based (serialized) shuffle write path: incoming records are serialized "as soon as they are passed to the shuffle writer and are buffered in a serialized form during sorting"[^spark-source-shuffle-manager]. Critically, "when the spill compression codec supports concatenation of compressed data, the spill merge simply concatenates the serialized and compressed spill partitions to produce the final output partition. This allows efficient data copying methods, like NIO's transferTo, to be used and avoids the need to allocate decompression or copying buffers during the merge."[^spark-source-shuffle-manager]

That tells us two things. First, the bytes physically written to the final shuffle data file are the serialized-and-compressed bytes (post-compression), not raw record bytes. Second, because the fast merge path concatenates the already-spilled compressed partitions directly into the final output file (via `transferTo`, without decompressing/recompressing), the final on-disk output *is* built from what was spilled to disk during sorting; there's no separate "spill bytes" pool that gets discarded before the final write. So `shuffleWriteMetrics.bytesWritten`, measuring the size of that final written shuffle output, counts compressed bytes, and in this common fast-merge path it corresponds to data that originated as on-disk spill segments during the sort rather than being written fresh at merge time.
