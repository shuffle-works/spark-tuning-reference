# Introduction

## What is the intended mental model a practitioner should have before reading an optimization guide?

Spark code is declarative before it is anything else: transformations and actions get compiled through a logical plan, an optimized logical plan, and finally a physical plan before a single task runs[^definitive-guide]. The Catalyst optimizer does this compilation itself, constructing candidate plans and assigning costs to them, with predicate pushdown to the data source as one of the physical-plan optimizations[^high-perf-spark]. A practitioner tuning configs without this picture is turning knobs on a black box.

Underneath that plan, Spark's execution unit is the task, and tasks are grouped into stages, and stages into jobs. A new stage starts after each wide transformation, and because stages on the same RDD lineage generally run in sequence, a single slow task can hold up the whole job[^high-perf-spark]. Partitions are the atomic unit of parallelism here: one task per partition, one thread per core, so the practical target is at least as many partitions as cores per executor[^learning-spark-2e]. A commonly cited rule of thumb is roughly 4x partitions to available cores, with each task ideally running 100ms or longer. Below that, the overhead of scheduling and distributing tasks starts to dominate the actual work[^luminousmen-partition-tuning].

With that model in place, the specific levers a guide will walk through (caching, partition tuning, join strategy, statistics, adaptive query execution) sit on top of the same few things: how much data moves, how evenly it's split, and how well the optimizer's plan matches reality[^spark-sql-perf-tuning]. Configs themselves can be set three ways: cluster-wide in `conf/spark-defaults.conf`, per submission via `spark-submit --conf`, or programmatically on the `SparkSession` builder[^learning-spark-2e].

## What is the canonical definition of a "straggler task" in Spark documentation vs in the research literature? Are they the same concept?

The most direct definition in the retrieved corpus comes from a Spark performance book, not from Spark's own reference docs: "Stragglers are those tasks within a stage that take much longer to execute than the other tasks in that stage." The same source ties stragglers directly to partitioning: they show up when Spark hasn't allocated resources correctly and, in particular, when data isn't partitioned evenly. Skewed keys produce a skewed task-duration distribution, and because stages run in sequence, a straggler in one stage can hold up the whole job[^high-perf-spark].

A second, narrower framing shows up in discussions of task memory management: a straggler is described there as "the last remaining task" in a stage, the one still running after every other task in that stage has finished. That framing matters operationally because Spark's memory manager treats a lone running task differently: with only one active task on an executor, dynamic memory allocation lets it claim the full execution memory pool, which is called out as one advantage of dynamic over static memory assignment for handling stragglers[^spark-notes-task-memory-management].

The two descriptions are the same concept from two angles: a task that is far behind its peers in the same parallel stage, for whatever reason (skew, an overloaded executor, a slow node), and that lag delays the stage's completion. Nothing in the retrieved corpus points to a separate, formally distinct academic definition to contrast against the Spark-community one; the practitioner-book definition already matches the general distributed-systems usage of the term.

## What exactly is a "speculative task" — what conditions trigger speculative execution, and what config controls it (spark.speculation.*)?

A task in Spark is the smallest unit of execution: each stage is split into tasks, one per partition of the RDD being processed, and each task runs on a single executor core[^high-perf-spark]. A "speculative task" is a duplicate run of one of these tasks. If a task in a running stage is running abnormally slowly compared to its peers, Spark starts a second copy of that same task on a different executor. If the original slowness was caused by a faulty node, the copy can finish first[^definitive-guide].

Speculative execution is off by default and is enabled with `spark.speculation=true`[^spark-configuration]. When enabled, several configs govern when a slow task actually gets speculated:

- `spark.speculation.interval` (default `100ms`) sets how often Spark checks for tasks that qualify for speculation[^spark-configuration].
- `spark.speculation.quantile` (default `0.9`) is the fraction of tasks in a stage that must have already completed before speculation is turned on for that stage. It only kicks in once most of the stage's tasks are done, so it targets stragglers instead of firing on every early task[^spark-configuration].
- `spark.speculation.multiplier` (default `3`) is the slowness threshold: a task must be running at least this many times slower than the median duration of already-completed tasks in the stage to be considered for speculation[^spark-configuration].
- `spark.speculation.minTaskRuntime` (default `100ms`, added in 3.2.0) is a floor on task runtime below which a task is never speculated, so very short tasks aren't needlessly duplicated[^spark-configuration].
- `spark.speculation.task.duration.threshold` (added in 3.0.0, no default) is a separate trigger meant for stages with very few tasks: if a stage has fewer (or equal) tasks than the number of executor slots available (computed from `spark.executor.cores` and `spark.task.cpus`), Spark will speculatively rerun any task whose duration exceeds this threshold, since the quantile-based mechanism above doesn't work well when there aren't many completed tasks yet to form a meaningful median. The regular speculation configs can still apply on top of this when slots are large enough[^spark-configuration].

Spark 3.4.0 added an "efficiency" layer on top of the classic multiplier/quantile logic, controlled by `spark.speculation.efficiency.enabled` (default `true`). With it on, crossing the multiplier/quantile bar is not enough on its own; Spark first checks whether the task is actually inefficient. That's true if its data-processing rate is below the average of successful tasks in the stage times `spark.speculation.efficiency.processRateMultiplier` (default `0.75`), or if its duration has exceeded `spark.speculation.efficiency.longRunTaskFactor` (default `2`) multiplied by the same time threshold used above (the multiplier-times-median or the min task runtime, whichever applies). A task that is merely slow but still processing data at a reasonable rate can be skipped. One that is genuinely stalled or inefficient gets caught regardless of raw duration[^spark-configuration].
