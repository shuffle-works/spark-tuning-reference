# PySpark Specifics

## Q1. How does PySpark execute Python UDFs — what is the serialization path between the JVM and the Python worker?

A standard (non-Arrow) PySpark UDF is a row-at-a-time function. Historically this was slow because "PySpark UDFs required data movement between the JVM and Python, which was quite expensive"[^learning-spark-2e], and the mechanism for that movement is pickle-based row serialization (the surrounding text is indexed under "pickle serialization library (Python)")[^learning-spark-2e]. Spark: The Definitive Guide breaks down the cost: starting the separate Python process is expensive, but "the real cost is in serializing the data to Python." Once data has crossed into the Python process, the JVM can no longer manage that worker's memory, so the two compete for memory on the same machine, which can cause the worker to fail under memory pressure[^definitive-guide]. This is why the same source recommends writing UDFs in Scala/Java when possible and calling them from Python[^definitive-guide].

Since Spark 3.4, this row-by-row path can itself be Arrow-optimized. Setting `useArrow=True` on `udf()`, or the session-wide `spark.sql.execution.pythonUDF.arrow.enabled` (default `false`, added in 3.4.0), makes a regular Python UDF an "Arrow Python UDF", still executed row-by-row semantically, but using Arrow for the batch data transfer and serialization instead of Python's pickle format[^pyspark-pandas-udfs][^spark-configuration]. The session config only takes effect when `useArrow` is unset or `None` on the UDF itself[^pyspark-pandas-udfs].

The pandas UDF (vectorized UDF), introduced in Spark 2.3, avoids the per-row JVM↔Python movement altogether. It uses Apache Arrow to transfer whole batches of data to the Python worker and pandas Series/DataFrame to operate on them, so there is no need to serialize/pickle data row by row: the data already arrives in a format the Python process can consume directly[^learning-spark-2e].

## Q2. What is the exact per-row overhead of Pickle serialization in a Python UDF vs Arrow batch serialization in a pandas UDF? Are there published benchmarks?

The corpus has no published exact per-row (microsecond or nanosecond) overhead figure for pickle vs. Arrow serialization. What it does have is a relative, workload-level benchmark. Databricks' introductory blog post benchmarked three operations (Plus One, Cumulative Probability, Subtract Mean) on a 10M-row DataFrame with an Int and a Double column, on a single-node 6.0 GB / 0.88-core Databricks Community Edition cluster, and found that "Pandas UDFs perform much better than row-at-a-time UDFs across the board, ranging from 3x to over 100x"[^databricks-pandas-udf]. Learning Spark, 2nd Edition explains the gap qualitatively: pickled row-at-a-time UDFs require expensive JVM↔Python data movement, whereas Arrow-backed pandas UDFs skip serialization/pickling because the data already arrives in Arrow's columnar, Python-consumable format[^learning-spark-2e]. No source in the corpus decomposes this into a fixed per-row cost. ## Q3. What is the difference between a pandas_udf of type SCALAR (Series -> Series), SCALAR_ITER (Iterator[Series] -> Iterator[Series]), and MAP_ITER (mapInPandas)? When should each be used?

**SCALAR** (`Series -> Series`, or via type hints `pandas.Series, ... -> pandas.Series`): the function takes one or more pandas Series and returns a Series of the same length. PySpark calls the function once per Arrow batch and concatenates the batch results back together as a Column output[^databricks-pandas-udf][^learning-spark-2e]. It is the direct vectorized replacement for a row-at-a-time scalar UDF (e.g., computing `v + 1`, or `cubed(x)`)[^databricks-pandas-udf][^learning-spark-2e].

**SCALAR_ITER** (`Iterator[Series] -> Iterator[Series]`): the function takes and yields an iterator of pandas Series rather than a single Series, and the total output length must equal the total input length. Internally it works the same as the Series-to-Series case, but the iterator form lets the function prefetch data across batches[^pyspark-pandas-udfs]. Use it when the UDF needs expensive one-time initialization (e.g., `state = very_expensive_initialization()`) and reuses that state for every batch pulled from the iterator, instead of re-initializing per batch as a plain SCALAR UDF would[^pyspark-pandas-udfs]. A variant, `Iterator[Tuple] -> Iterator`, exists when multiple input columns are needed[^pyspark-pandas-udfs].

**MAP_ITER / `mapInPandas`**: this is not a `pandas_udf` type but a separate Pandas Function API: `DataFrame.mapInPandas()`. It maps an iterator of `pandas.DataFrame` (representing the whole PySpark DataFrame) to another iterator of `pandas.DataFrame`. Unlike the pandas UDF variants, it can return output of arbitrary length rather than matching the input length, while internally working like the Series-to-Series pandas UDF[^pyspark-pandas-udfs]. Use it to transform or filter a DataFrame partition-by-partition when the output row count need not match the input (e.g., row filtering, expansion, deduplication).

A related API is the grouped-map `DataFrame.groupby().applyInPandas()`: it splits the DataFrame into groups, applies a `pandas.DataFrame -> pandas.DataFrame` function per group (split-apply-combine), and combines results, useful for per-group transformations such as subtracting the group mean or fitting a per-group regression[^databricks-pandas-udf][^pyspark-pandas-udfs]. A full group's data is loaded into memory before the function runs, and `maxRecordsPerBatch` does not apply to groups, so skewed groups risk OOM[^pyspark-pandas-udfs].

## Q4. Does enabling spark.sql.execution.arrow.pyspark.enabled affect operations other than pandas UDFs (e.g., toPandas(), createDataFrame() from a pandas DataFrame)?

Yes. The Spark configuration reference states that `spark.sql.execution.arrow.pyspark.enabled` (default: the value of `spark.sql.execution.arrow.enabled`, since 3.0.0) "make[s] use of Apache Arrow for columnar data transfers in PySpark" and "applies to: 1. `pyspark.sql.DataFrame.toPandas`. 2. `pyspark.sql.SparkSession.createDataFrame` when its input is a Pandas DataFrame or a NumPy ndarray"[^spark-configuration]. The PySpark Arrow user guide confirms the same two entry points and shows the pattern: set the conf to `"true"`, then use `spark.createDataFrame(pdf)` to build a Spark DataFrame from a pandas DataFrame via Arrow, and `df.select("*").toPandas()` to convert back, with results identical to running without Arrow[^pyspark-pandas-udfs]. A related fallback config, `spark.sql.execution.arrow.pyspark.fallback.enabled`, silently falls back to the non-Arrow implementation if an error occurs before computation starts[^pyspark-pandas-udfs][^spark-configuration]. So this config is not pandas-UDF-specific. It is the general on/off switch for Arrow-based conversion between Spark DataFrames and pandas/NumPy on the driver side, on top of gating pandas UDF execution.

The documented comparisons consistently favor built-in/vectorized code over row-at-a-time Python UDFs, but they do not claim built-in functions are unconditionally faster, nor do they document a case where a plain row-at-a-time UDF outperforms `pyspark.sql.functions`. That comparison is about row-at-a-time UDFs, not pandas/Arrow-optimized UDFs, which close much of the gap (see Q2's 3x–100x figures)[^databricks-pandas-udf].

## Q6. What is spark.python.worker.reuse — what does it reuse, and what are the correctness risks of enabling it?

`spark.python.worker.reuse` (default `true`, since 1.2.0) controls whether Spark reuses Python worker processes: "If yes, it will use a fixed number of Python workers, does not need to fork() a Python process for every task. It will be very useful if there is a large broadcast, then the broadcast will not need to be transferred from JVM to Python worker for every task"[^spark-configuration]. What is reused is the Python worker *process* itself, along with anything already resident in it such as a previously-received broadcast variable, across successive tasks, rather than spawning and tearing down a fresh interpreter per task.

The retrieved corpus does not document specific correctness risks of enabling worker reuse (e.g., module-level/global state leaking between tasks that land on the same reused worker). ## Q7. What does spark.python.worker.memory control exactly — is it a per-worker limit, and what happens at the OS level when it is exceeded?

`spark.python.worker.memory` (default `512m`, since 1.1.0) is documented as "Amount of memory to use per python worker process during aggregation... If the memory used during aggregation goes above this amount, it will spill the data into disks"[^spark-configuration]. So it is per-Python-worker-process, but it is a Spark-managed, application-level accounting threshold for in-worker aggregation buffering, not an OS-enforced cap. When it is exceeded, Spark spills the aggregation data to disk[^spark-configuration]; nothing in the retrieved chunk says the OS terminates the process at that point.

The OS/cgroup-enforced mechanisms are separate. `spark.executor.pyspark.memory` is an executor-scoped config that, if set, limits total PySpark memory for an executor using Python's `resource` module, so it inherits that module's limitations: it does not limit actual memory on macOS, and Windows lacks the `resource` module entirely[^spark-configuration]. The Python worker's memory comes from the executor's overhead memory space; if total container memory (heap + off-heap + Python + native) exceeds what YARN or Kubernetes allocated, "Kubernetes won't hesitate"; the process is "OOMKilled," i.e., the OS/container runtime kills it at that boundary[^luminousmen-memory-management]. So `spark.python.worker.memory` triggers a disk spill inside Spark's own accounting, while a container-level overage (governed by overhead/pyspark.memory settings, not by `worker.memory`) is what gets OS/cgroup-level enforcement.

## Q8. What is the correct way to handle stateful operations in PySpark without row-at-a-time Python UDFs?

Two documented, vectorized patterns cover common "needs state" cases:

1. **SCALAR_ITER pandas UDF** (`Iterator[Series] -> Iterator[Series]`): when a computation needs one-time, expensive initialization (loading a model, opening a connection, precomputing a lookup table) that should be reused across all rows a worker processes, the iterator form of `pandas_udf` lets you initialize state once and then loop over the iterator of batches reusing it. The documented pattern is `state = very_expensive_initialization()` followed by a loop over the iterator applying `calculate_with_state(x, state)`[^pyspark-pandas-udfs]. This gives per-worker (not per-row) state initialization while still processing data as vectorized pandas Series.

2. **Grouped-map Pandas Function API** (`DataFrame.groupBy().applyInPandas()`, the modern form of the old "grouped map" pandas UDF): this implements split-apply-combine. Spark splits the DataFrame into groups, hands each group to your Python function as a whole `pandas.DataFrame`, and your function can compute anything that needs the full group's data as state (subtracting a group mean, fitting an OLS regression per group), returning another `pandas.DataFrame`[^databricks-pandas-udf][^pyspark-pandas-udfs]. This avoids row-at-a-time UDFs for per-group stateful logic, at the cost that an entire group must fit in memory (the `maxRecordsPerBatch` limit does not apply to groups)[^pyspark-pandas-udfs].

Neither of these is streaming state management (e.g., state carried across micro-batches in Structured Streaming).
