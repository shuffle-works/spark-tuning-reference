# Table Formats

## How do Delta Lake, Apache Iceberg, and Apache Hudi each control target data file size (Delta OPTIMIZE / target file size, Iceberg write.target-file-size-bytes, Hudi hoodie.parquet.max.file.size and small-file handling), and why do many small files hurt query and metadata performance?

Delta Lake, Iceberg, and Hudi treat file sizing very differently: Delta and Iceberg lean on a post-hoc compaction command, while Hudi's headline feature is sizing files correctly at write time.

Delta Lake does not size files during the write itself by default; it improves an already-written table's layout with the `OPTIMIZE` command, which bin-packs small files into larger ones and has been available since Delta Lake 1.2.0[^delta-optimize]. `OPTIMIZE` can run against a whole table (`OPTIMIZE delta_table_name` or the path-based `OPTIMIZE '/path/to/delta/table'`) or against a subset via a partition predicate (`OPTIMIZE delta_table_name WHERE date >= '2017-01-01'`), and the same operation is exposed through the Python/Scala API as `DeltaTable.forName(...).optimize().executeCompaction()`, optionally scoped with `.where(...)`[^delta-optimize]. Bin-packing is idempotent, so re-running `OPTIMIZE` on an already-compacted table is a no-op[^delta-optimize]. Delta Lake 3.1.0 adds a separate "Optimized Write" feature aimed at file sizing[^delta-optimize]; the exact target-size default for either `OPTIMIZE` or Optimized Write is `[UNRESOURCED: Delta Table Properties Reference / spark.databricks.delta.optimize.maxFileSize would carry that default]`.

Apache Iceberg's table spec shows one Iceberg-specific driver of file proliferation: version 2 of the spec "adds delete files to encode rows that are deleted in existing data files," letting a writer "delete or replace individual rows in immutable data files without rewriting the files"[^iceberg-spec]. That is, row-level deletes accumulate as separate small delete files rather than forcing an immediate rewrite of the data file they apply to. The specific `write.target-file-size-bytes` default and how `rewrite_data_files` selects and merges files are `[UNRESOURCED: iceberg-configuration and iceberg-spark-procedures docs would be needed]`.

Apache Hudi is explicit that avoiding small files is "a critical design decision in the Hudi architecture," and it offers two mechanisms: auto-sizing during writes, and clustering after the fact[^hudi-file-sizing]. For auto-sizing, the default targeted size for Parquet base files is 120 MB, set via `hoodie.parquet.max.file.size`[^hudi-file-sizing]. Auto-sizing pairs that with a small-file threshold, `hoodie.parquet.small.file.limit` (default 104,857,600 bytes / 100 MB): any existing file at or below that limit is a candidate to have new records appended to it rather than Hudi writing a brand-new file, and Hudi bin-packs records into such candidates up toward the max-file-size target. For example, with a 100 MB small-file limit and a 120 MB max file size, Hudi picks all files under 100 MB and tries to grow them to 120 MB[^hudi-file-sizing]. Setting `hoodie.parquet.small.file.limit` to 0 disables this small-file lookup and forces every write to a new file[^hudi-file-sizing][^hudi-clustering]. Getting the initial record-size estimate right (`hoodie.copyonwrite.record.size.estimate`, default 1024 bytes) matters for the very first ingestion batch, since Hudi needs it to bin-pack records into a file of the right size before it has commit history to learn the average record size from[^hudi-file-sizing]. Auto-sizing does not apply to `bulk_insert`[^hudi-file-sizing]. Merge-on-Read (MOR) tables add their own knobs: `hoodie.merge.small.file.group.candidates.limit` (default 1) caps how many small-file base-file groups are considered for record appends during upsert, and `hoodie.logfile.max.size` (default 1,073,741,824 bytes / 1 GB) is the rollover size for the row-based delta log files that MOR tables append updates to (append-based rollover only works on storage that supports append, which may not include cloud object stores like S3/GCS)[^hudi-file-sizing]. Hudi's COW/MOR trade-off table also notes that COW base files "need to be smaller to avoid high update (I/O) cost," while MOR base files "can be larger, since update cost is low and amortized" via the delta log[^hudi-table-types].

Hudi's second mechanism, clustering, is a table service that stitches small files into larger ones (optionally re-sorting or applying a space-filling curve like Z-order/Hilbert) without changing ingestion behavior[^hudi-clustering][^hudi-file-sizing]. The `hoodie.parquet.small.file.limit` knob lets you choose the ingestion/query trade-off directly: set it to 0 to force every write into new file groups (fastest ingestion, most small files, relies on clustering to fix later), or raise it to pad more records into existing files at the cost of added ingestion latency[^hudi-clustering]. Clustering's plan strategy groups eligible files so each group targets a size that is a multiple of `targetFileSize`, and size-based clustering strategies specifically exclude files already above the small-file limit from the plan[^hudi-clustering]. Clustering is distinct from compaction: compaction (the default async mode, or synchronous via `hoodie.compact.inline = true`) merges MOR's row-based delta logs into new base-file versions to keep read amplification in check, whereas clustering is a data-layout optimization that can only run on tables/partitions with no concurrent updates[^hudi-compaction][^hudi-clustering].

Many small files hurt performance for a few concrete reasons. On the query side, a query has to scan through many small files to retrieve the same data it would get from fewer larger files, which is an inefficient access pattern; on top of that, cloud storage such as S3 enforces per-prefix request rate limits, and because at least one request is issued per file regardless of its size, more files raise the odds of hitting that rate limit and add fixed per-file open/close overhead[^hudi-file-sizing]. On the pipeline side, more files mean more tasks, which slows down Spark, Flink, or Hive jobs through excessive scheduling overhead and memory requirements[^hudi-file-sizing]. On storage and metadata, many small files compress less efficiently than fewer large ones, raising storage cost, and if the table is indexed, each additional file also adds more metadata (such as column statistics) that has to be stored and, implicitly, scanned by planners[^hudi-file-sizing]. This is why ingestion and query performance pull in opposite directions: ingestion favors small files for parallelism and low latency to availability, but query performance degrades badly as the small-file count grows, which is exactly the tension that table-service features like Hudi's clustering and Delta's `OPTIMIZE` exist to resolve[^hudi-clustering][^delta-optimize].

## How does each table format compact small files into larger ones — Delta Lake OPTIMIZE bin-packing, Iceberg rewrite_data_files, and Hudi compaction/clustering — and how is each triggered (manual command, procedure, or automatic/inline)?

**Delta Lake.** The `OPTIMIZE` command coalesces small files into larger ones ("bin-packing"), available since Delta Lake 1.2.0[^delta-optimize]. It is run manually, via `OPTIMIZE delta_table_name;` or, with an optional partition predicate, `OPTIMIZE delta_table_name WHERE date >= '2017-01-01'`, or from the Python/Scala API (`deltaTable.optimize().executeCompaction()`, with an optional `.where(...)` predicate), available from Delta Lake 2.0 and above[^delta-optimize]. Bin-packing is idempotent (a second run on the same data has no effect) and targets evenly-balanced file sizes on disk rather than an even tuple count per file, though the two are usually correlated; setting `spark.databricks.delta.optimize.repartition.enabled=true` makes OPTIMIZE use `repartition(1)` instead of `coalesce(1)` for better performance when compacting many small files[^delta-optimize]. Beyond the manual command, Delta Lake 3.1.0+ adds **auto compaction**: it runs automatically and synchronously on the same cluster right after a write succeeds, compacts only files not already compacted, and is gated by a configurable minimum number of small files per partition before it triggers; output file size is controlled via `spark.databricks.delta.autoCompact.maxFileSize`[^delta-optimize]. A related manual command, `REORG TABLE ... APPLY (PURGE)`, rewrites files containing rows marked deleted by deletion vectors; if the resulting rewritten files come out small, REORG TABLE also coalesces them into larger ones, and the operation is idempotent[^delta-deletion-vectors].

**Iceberg.** The retrieved Iceberg reference documents the `rewrite_position_delete_files` procedure in detail: it performs minor compaction of small position delete files into larger ones (reducing manifest metadata size and the overhead of opening many small delete files) and removes dangling deletes, meaning position delete records that reference data files no longer live, which can persist after a `rewrite_data_files` run[^iceberg-spark-procedures]. It is invoked as a table procedure with a `table` argument, an optional `where` filter predicate, and options such as `max-concurrent-file-group-rewrites` (default 5)[^iceberg-spark-procedures]. [UNRESOURCED: `rewrite_data_files` bin-packing mechanics and manual trigger syntax; would need Iceberg's maintenance/procedures documentation for that specific procedure.]

**Hudi.** Hudi splits small-file handling into two distinct table services. **Compaction** applies only to Merge-on-Read (MOR) tables: MOR stores inserts in a base (columnar) file and appends updates to row-based log files, and compaction periodically merges the log files into the base file to produce a new base file version, bounding log growth and read latency; it does not apply to Copy-on-Write (COW) tables[^hudi-compaction]. Compaction runs in two steps: scheduling (scanning partitions and selecting file slices to compact, writing a compaction plan to the Hudi timeline) and execution (reading the plan and compacting the file slices)[^hudi-compaction]. Scheduling is governed by a **trigger strategy** (`hoodie.compact.inline.trigger.strategy`, default `NUM_COMMITS`, with options `NUM_COMMITS_AFTER_LAST_REQUEST`, `TIME_ELAPSED`, `NUM_AND_TIME`, `NUM_OR_TIME`) and a separate **compaction strategy** that picks which file groups to compact (`hoodie.compaction.strategy`, default `LogFileSizeBasedCompactionStrategy`, with alternatives such as `LogFileNumBasedCompactionStrategy`, `BoundedIOCompactionStrategy`, `BoundedPartitionAwareCompactionStrategy`, `DayBasedCompactionStrategy`, and `UnBoundedCompactionStrategy`)[^hudi-compaction]. By default compaction runs **async**, alongside ingestion without blocking it (the default for streaming models like Hudi Streamer continuous mode, Flink, and Spark Structured Streaming)[^hudi-compaction]. It can instead run **inline** (synchronously, as part of the same write job) by setting `hoodie.compact.inline = true` for Spark Datasource/Spark SQL writers, or via the `--disable-compaction` flag in Hudi Streamer sync-once mode[^hudi-compaction]. It can also be triggered **manually/offline**: through the Hudi CLI (`compaction run --tableName <table_name> --parallelism <parallelism> --compactionInstant <InstantTime>`) or, for Flink, by submitting `org.apache.hudi.sink.compact.HoodieFlinkCompactor` as a standalone command-line job with options like `--schedule` and `--service` (continuous monitoring mode)[^hudi-compaction].

**Clustering** is Hudi's separate data-layout service: unlike compaction (which merges log files into base files for MOR read performance), clustering stitches small files into larger ones and can additionally sort data by a key so co-located, frequently-queried data lands together[^hudi-clustering]. Users tune the ingestion-time trade-off between file size and write latency via `hoodie.parquet.small.file.limit`, which sets the smallest allowable file size that new writes get "padded" toward; clustering then rewrites the resulting layout asynchronously or synchronously[^hudi-clustering]. Clustering is one path to fixing file sizing after ingestion has already produced small files, complementing write-time auto-sizing, which uses `hoodie.parquet.small.file.limit` together with `hoodie.parquet.max.file.size` to bin-pack records into a target file size as they are written (Hudi picks files under the small-file limit and adds records until they reach the max size)[^hudi-file-sizing].

## How does data clustering to co-locate related rows compare across the formats: Delta Lake Z-order versus liquid clustering, Iceberg sort orders and rewrite_data_files sort/zorder strategies, and Hudi clustering?

Delta Lake's Z-Ordering (multi-dimensional clustering) is a technique to colocate related information in the same set of files; this co-locality is automatically used by Delta Lake's data-skipping algorithms, dramatically reducing how much data Spark needs to read[^delta-optimize]. It runs via `OPTIMIZE table ZORDER BY (col1, col2, ...)` (or `deltaTable.optimize().executeZOrderBy(col)`), and works best on high-cardinality columns that are commonly used in query predicates; the effectiveness of the co-locality drops with each additional ZORDER column, and Z-Ordering is not idempotent, since each run creates a new clustering of all files in a partition, both new files and ones from a previous Z-Ordering[^delta-optimize]. Delta's documentation set also lists liquid clustering as its own, separately documented table-layout feature alongside Z-Ordering[^delta-optimize]. [UNRESOURCED: liquid clustering's own mechanism, e.g. how its incremental approach differs operationally from a Z-order rewrite, would need Delta's "Use liquid clustering for Delta tables" page, which wasn't retrieved for this question.]

Iceberg exposes clustering through the `rewrite_data_files` procedure's `strategy` argument, which is `binpack` (the default) or `sort`, combined with a `sort_order` argument: for Z-order, a comma-separated list of columns inside `zorder(...)` (e.g. `zorder(c1,c2,c3)`); otherwise a comma-separated list of `ColumnName SortDirection NullOrder` clauses, defaulting to the table's existing sort order when omitted[^iceberg-spark-procedures]. For example, `CALL catalog_name.system.rewrite_data_files(table => 'db.sample', strategy => 'sort', sort_order => 'id DESC NULLS LAST,name ASC NULLS FIRST')` sorts explicitly on named columns, while `CALL catalog_name.system.rewrite_data_files(table => 'db.sample', strategy => 'sort', sort_order => 'zorder(c1,c2)')` Z-orders on `c1` and `c2`[^iceberg-spark-procedures]. The plain sort strategy has its own tuning options: `compression-factor` adjusts the on-disk-size estimate used to size the Spark sort's shuffle partitions, and `shuffle-partitions-per-file` sets how many shuffle partitions Iceberg's custom coalesce operation stitches back into one sorted output file; the zorder variant adds `var-length-contribution` (bytes considered from a variable-length column) and `max-output-size` (bytes interleaved by the ZOrder algorithm)[^iceberg-spark-procedures]. At the table-spec level, each data or delete file is associated with a sort order by that order's id within its manifest, order id 0 is reserved for the unsorted order, and a table declares all its sort orders for lookup, optionally naming a default sort order id that new writes should follow, though writers aren't required to honor it when doing so would be prohibitively expensive, as for streaming writes[^iceberg-spec].

Hudi's clustering is a table service, distinct from compaction, that reorganizes data without slowing ingestion: compaction merges Merge-on-Read delta logs into base files, while clustering rewrites file groups purely to improve layout, either by stitching small files into larger ones or by sorting rows on a chosen key so that data frequently queried together ends up co-located[^hudi-clustering]. Clustering runs as a two-phase "REPLACE" action: a plan phase picks eligible file groups using a pluggable plan strategy (size-based strategies such as `SparkSizeBasedClusteringPlanStrategy`, which groups files under a size cap and excludes files already above the small-file limit; `SparkSingleFileSortPlanStrategy`, which keeps a single output group per partition and preserves the file group ID; `SparkConsistentBucketClusteringPlanStrategy` for expanding consistent-bucket-index tables; and `CommitBasedClusteringPlanStrategy`, which groups file slices by the commits that produced them rather than by size), and an execution phase applies an execution strategy class to rewrite each group[^hudi-clustering]. The default execution strategy, `SparkSortAndSizeExecutionStrategy`, uses `bulk_insert` to rewrite the input file groups, sorting by the columns named in `hoodie.clustering.plan.strategy.sort.columns` while meeting the configured target file size; this sort-column config is exactly the "cluster by sort key" mechanism Hudi uses to co-locate rows matching common query predicates instead of leaving them ordered by arrival time[^hudi-clustering]. A separate `SparkStreamCopyClusteringExecutionStrategy` (available since Hudi 1.2.0) instead performs binary file stitching, a byte-level copy with no re-read/re-write of records, which is faster but skips sorting, so it only applies when the goal is pure small-file consolidation and no sort order is required[^hudi-clustering]. Since Hudi 1.2.0, the order in which file slices themselves get packed into clustering groups is also configurable via `hoodie.clustering.plan.strategy.file.slices.sort.by` (`SIZE`, largest-first, by default, or `INSTANT_TIME`, oldest-first)[^hudi-clustering]. Clustering builds on Hudi's MVCC design so writers can keep inserting while clustering runs in the background, and it produces a new file-group version while readers keep snapshot isolation; it can only be scheduled for tables or partitions not currently receiving concurrent updates[^hudi-clustering][^hudi-file-sizing]. Practically, Hudi also uses clustering to fix file sizes after workloads like `BULK_INSERT` without sort modes, governed by `hoodie.clustering.plan.strategy.small.file.limit` (default 314572800 bytes on Spark) and `hoodie.clustering.plan.strategy.target.file.max.bytes` (default 1073741824 bytes)[^hudi-file-sizing].

## How does each format track table metadata and what is the resulting overhead — the Delta transaction log (JSON commits plus Parquet checkpoints), Iceberg metadata files with manifest lists and manifest files, and the Hudi timeline and metadata table?

Delta Lake records every table change as a commit in the transaction log, with each operation automatically versioned; `deltaTable.history()` exposes the version, timestamp, operation, and operationParameters for each commit[^learning-spark-2e]. Delta periodically and automatically compacts the incremental updates in that log into a checkpoint Parquet file, so reads can reconstruct current table state (which files to process, what the current schema is) without processing every file with incremental updates[^delta-optimize]. Checkpoints can be split across multiple Parquet files ("multi-part checkpointing"); for V2 checkpoints the default part size is 50,000 actions, tunable via `spark.databricks.delta.checkpoint.partSize`[^delta-optimize]. Since Delta Lake 3.0, log compaction files (named `<x>.<y>.compact.json`) aggregate the actions across a commit range into a single JSON file, reducing how often checkpoints are needed and minimizing the latency spikes they otherwise cause; read support for these files is on by default and can be disabled via `spark.databricks.delta.deltaLog.minorCompaction.useForReads`[^delta-optimize]. On the overhead side, `vacuum` removes stale data files older than a retention threshold (default 7 days) but never removes log files; log files are instead deleted automatically and asynchronously after checkpoint operations, with a default log retention of 30 days configured through the `delta.logRetentionDuration` table property[^delta-utility].

Iceberg tracks table metadata using JSON files: each change to the table produces a new metadata file, providing atomicity[^iceberg-maintenance]. Each metadata file also carries a `metadata-log` field listing prior metadata file locations[^iceberg-maintenance]. The set of manifests for a snapshot is tracked separately in a manifest list file, written fresh on every commit attempt because the manifest set always changes to produce a new snapshot[^iceberg-spec]. The manifest list carries summary metadata (counts of added/existing/deleted files, and per-partition-field value summaries) so query planning can avoid scanning every manifest, and large tables split their data files across multiple manifests to parallelize planning and avoid rewriting one large manifest on every change[^iceberg-spec]. This layered design adds cleanup overhead of its own: metadata JSON files accumulate as tracked history and are only pruned automatically if `write.metadata.delete-after-commit.enabled` is turned on, so otherwise old metadata files build up and can only be removed by an orphan-file-deletion pass[^iceberg-maintenance]. Snapshots accumulate until `expireSnapshots` is run, which is recommended specifically to keep table metadata size small in addition to freeing unreferenced data files[^iceberg-maintenance]. More data files translate into more manifest entries, and small data files inflate this metadata disproportionately and slow query planning; `rewriteDataFiles` compacts small data files to cut that metadata overhead and file-open cost, while `rewriteManifests` re-groups data files into manifests to speed up planning when a table's write pattern no longer aligns with its query pattern[^iceberg-maintenance]. A full metadata rewrite (the `rewrite_table_path` procedure) has to touch every reachable metadata.json file, manifest list, manifest, and position-delete file, underscoring how much of a table's metadata footprint lives in that manifest/manifest-list layer[^iceberg-spark-procedures]. Iceberg also tracks partition evolution as metadata: a table's partition spec can change over time, and because each manifest uses a single partition spec, partition filters for queries are derived from data predicates so queries do not need to change when the spec changes[^iceberg-spec].

Hudi records every write and table-service action as an instant on a timeline, alongside background cleaning and compaction actions[^hudi-table-types]. A commit's instant on the timeline captures its arrival time, and combined with record-level metadata it lets an incremental query pull only the records changed since a given instant instead of scanning every time-range partition[^hudi-table-types]. Table services record their own plans on that same timeline: a clustering operation adds a `REPLACE` action type and saves its clustering plan to the timeline in avro metadata format[^hudi-clustering], and a compaction similarly writes its plan to the timeline before its execution step reads that plan and compacts the file slices[^hudi-compaction]. The timeline's history rests on Hudi's MVCC design, which keeps multiple versioned files per file group; those versions give writers and readers snapshot isolation and let older versions serve time travel and rollback queries[^hudi-cleaning].

This timeline is also the source of ongoing overhead. Because commits, cleans, clusterings, and compactions all leave entries and plans on it, Hudi runs a cleaning service automatically after every commit by default to reclaim space from older file versions, with retention governed by policies such as `KEEP_LATEST_COMMITS` (the default, tunable via `hoodie.clean.commits.retained`) or `KEEP_LATEST_FILE_VERSIONS`; cleaning can instead be scheduled every few commits via `hoodie.clean.max.commits`[^hudi-cleaning]. Without incremental cleaning (`hoodie.clean.incremental.enabled=false`), the cleaner scans every partition on every run, which can cause out-of-memory failures during planning on very large tables; Hudi 1.2.0 added `hoodie.clean.partition.filter.regex` and `hoodie.clean.partition.filter.selected` to bound that scan[^hudi-cleaning]. Clustering and compaction scheduling face the same scaling problem and use the same fix: incremental scheduling analyzes only the commit metadata in the window since the last completed operation instead of rescanning all partitions, enabled by default via `hoodie.table.services.incremental.enabled`[^hudi-clustering][^hudi-compaction].

## How does each format expire old snapshots/versions and reclaim storage, and what are the default retention windows — Delta Lake VACUUM and log retention, Iceberg expire_snapshots and orphan-file removal, and the Hudi cleaner?

Delta Lake reclaims storage with the `VACUUM` command, which removes data files no longer referenced by the table and older than a retention threshold; VACUUM is not triggered automatically and must be run explicitly[^delta-utility]. The default retention threshold is 7 days[^delta-utility]. VACUUM deletes only data files, not transaction log files. Log files are removed automatically and asynchronously after checkpoint operations, with a default log retention of 30 days configurable through the `delta.logRetentionDuration` table property[^delta-utility]. Once VACUUM runs, the ability to time-travel to a version older than the retention period is lost[^delta-utility]. Retention can be overridden per run, e.g. `VACUUM table RETAIN 100 HOURS` or `deltaTable.vacuum(100)`[^delta-utility]. Delta recommends never dropping the retention interval below 7 days, since older snapshots and uncommitted files can still be in use by concurrent readers or writers; a safety check blocks shorter intervals unless `spark.databricks.delta.retentionDurationCheck.enabled` is explicitly set to `false`[^delta-utility]. Delta 3.3+ also offers a `VACUUM ... LITE` mode, which uses the transaction log to find files to remove within the retention duration instead of listing the whole table directory[^delta-utility].

Iceberg expires old snapshots with the `expire_snapshots` stored procedure. Each write/update/delete/upsert/compaction produces a new snapshot while retaining old data and metadata for snapshot isolation and time travel; `expire_snapshots` removes older snapshots and only the data/delete/manifest files uniquely required by those expired snapshots, never touching files still needed by a non-expired snapshot[^iceberg-spark-procedures]. Its default `older_than` is 5 days ago, and `retain_last` (ancestor snapshots always preserved regardless of age) defaults to 1[^iceberg-spark-procedures]. Snapshots referenced by branches or tags are not removed: branches and tags never expire by default, though the policy can be changed with the `history.expire.max-ref-age-ms` table property, and the main branch never expires[^iceberg-spark-procedures]. More generally, Iceberg's snapshot retention policy is governed by the table/branch properties `min-snapshots-to-keep`, `max-snapshot-age-ms`, and `max-ref-age-ms`[^iceberg-spec]. Separately, the `remove_orphan_files` action cleans up files under the table location that are not referenced by any table metadata (for example, left behind by failed jobs[^iceberg-maintenance]); its default `older_than` is 3 days ago[^iceberg-spark-procedures]. Iceberg warns that running orphan-file removal with a retention interval shorter than the time expected for in-flight writes to complete is dangerous, since it can delete in-progress files and corrupt the table[^iceberg-maintenance]. Old metadata JSON files are also kept by default; the number tracked is controlled by `write.metadata.previous-versions-max` (default 100), and setting `write.metadata.delete-after-commit.enabled` (default `false`) to `true` makes the writer delete the oldest tracked metadata file on each new commit; untracked/orphaned metadata files fall outside this mechanism and can only be removed by orphan-file deletion[^iceberg-maintenance].

Hudi's cleaner is a table service that reclaims space from older file versions kept for MVCC-based snapshot isolation between writers and readers[^hudi-cleaning]. Automatic cleaning is enabled by default and runs inline immediately after each commit to delete older file slices; it can instead be scheduled after every few commits via `hoodie.clean.max.commits`[^hudi-cleaning]. The default cleaning policy is `hoodie.clean.policy = KEEP_LATEST_COMMITS`[^hudi-cleaning]. Under `KEEP_LATEST_COMMITS`, the cleaner retains a configurable number of recent commits before cleaning older file versions, via `hoodie.clean.commits.retained`, which defaults to 10[^hudi-cleaning]. Two other Spark-based cleaning policies exist: `KEEP_LATEST_FILE_VERSIONS`, which keeps a fixed number of file versions per file group regardless of time (`hoodie.clean.fileversions.retained`), and `KEEP_LATEST_BY_HOURS`, which cleans commits older than a configured number of hours (`hoodie.clean.hours.retained`)[^hudi-cleaning]. Automatic cleaning itself is controlled by `hoodie.clean.automatic`, which defaults to `true`[^hudi-cleaning]; cleaning can also be run asynchronously alongside writing by setting `hoodie.clean.async=true`[^hudi-cleaning].

## How do the formats handle row-level deletes and updates without rewriting whole files — Delta Lake deletion vectors, Iceberg copy-on-write versus merge-on-read with position and equality deletes, and Hudi Copy-on-Write versus Merge-on-Read table types?

By default, deleting or updating a single row in a Delta table forces a rewrite of the entire Parquet file that contains it[^delta-deletion-vectors]. Deletion vectors avoid that: once enabled, Delta marks the affected rows as removed in a separate file and resolves the table's current state at read time by applying those markers to the most recent version, instead of rewriting the Parquet file immediately[^delta-deletion-vectors]. Support was added incrementally by operation and Delta version: SCAN in 2.3.0, DELETE in 2.4.0, UPDATE in 3.0.0 (on by default since 3.1.0), and MERGE in 3.1.0 (on by default since 3.1.0)[^delta-deletion-vectors]. The feature is turned on per table with `ALTER TABLE <table_name> SET TBLPROPERTIES('delta.enableDeletionVectors' = true)`, which upgrades the table protocol version so older Delta clients that don't understand deletion vectors can no longer read the table[^delta-deletion-vectors]. The soft-deletes recorded in deletion vectors are only applied physically (that is, the Parquet files are actually rewritten) when a DML command runs with deletion vectors disabled, when `OPTIMIZE` runs, or when `REORG TABLE ... APPLY (PURGE)` runs[^delta-deletion-vectors]. Delta's DML surface for this is the standard `UPDATE`, `DELETE`, and `MERGE` commands, callable from SQL, Python, Scala, or Java, each with ACID guarantees[^learning-spark-2e].

Iceberg took a versioned approach to the same problem. Version 1 of the spec manages tables as immutable Parquet, Avro, or ORC files with no row-level delete mechanism[^iceberg-spec]. Version 2 adds delete files that encode which rows in existing data files have been removed, letting a writer delete or replace individual rows in immutable files without rewriting them[^iceberg-spec]. Two delete-file encodings exist under v2: position delete files, which identify a deleted row by its data file path and ordinal row position, and equality delete files, which identify deleted rows by matching one or more column values (for example `id = 5`)[^iceberg-spec]. An equality delete file stores any subset of the table's columns as match predicates, and a row is considered deleted if its values equal all of the delete file's columns for some entry that applies to it, so multiple columns behave as an AND of equality predicates, and a null delete column matches rows whose corresponding value is null[^iceberg-spec]. Delete files, like data files, are tracked by partition and are in general only applied to older data files in the same partition, with equality deletes stored under an unpartitioned spec applied globally instead[^iceberg-spec]. Version 3 replaces position delete files with deletion vectors: a per-data-file bitmap of deleted row positions, stored using the `deletion-vector-v1` Puffin blob format and optimized with 32-bit Roaring bitmaps for positions that fit in 32 bits[^iceberg-spec]. At most one deletion vector is allowed per data file per snapshot, and writing a new one must replace any earlier position delete files for that data file so readers can safely ignore them[^iceberg-spec]. Writers are not allowed to add new position delete files once a table is on v3, though pre-existing v2 position delete files remain valid and must eventually be merged into a deletion vector[^iceberg-spec]. In all versions, this delete-file/deletion-vector mechanism lets Iceberg defer physically rewriting a data file: the deletes are merged with the base file logic at read/scan time, and only compaction-style replace operations combine several files into one that contains the same surviving rows[^iceberg-spec].

Hudi frames the same trade-off explicitly as two table types rather than a spec version progression. Copy-on-Write (CoW) tables are optimized for read-heavy workloads: an update or delete triggers creation of a new base file (file slice) in the affected file group, with no log files written, so every query reads only base files and gets high read performance at the cost of slower writes, since even a small percentage of changed records forces a base-file rewrite[^hudi-table-types]. Merge-on-Read (MoR) tables instead write updates and deletes to lightweight log files (in Avro or a columnar/base-file format), which are merged dynamically with the base file at query time and periodically compacted, trading some query-time overhead (depending on whether logs have been compacted) for lower write latency and near-real-time data availability[^hudi-table-types]. Core transactional features (atomic writes, indexing, incremental queries, automatic file sizing, and scalable metadata tracking) are available on both table types regardless of which one is chosen[^hudi-table-types]. Hudi's own name is an acronym for Hadoop Update Delete and Incremental, reflecting that it was built around incremental upserts and deletes over key/value-style data, storing that data as a combination of columnar base files and row-based log files for recording incremental changes[^learning-spark-2e].
