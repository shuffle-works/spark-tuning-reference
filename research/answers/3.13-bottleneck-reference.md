# Bottleneck Reference

## Q1. Is executorRunTime (as recorded in taskMetrics) wall-clock time or CPU time? Does it include time the task is blocked on I/O?

`executorRunTime` is elapsed (wall-clock) time, not CPU time. The Spark monitoring docs define it as "elapsed time the executor spent running this task," measured in milliseconds, and explicitly contrast it with `executorCpuTime`, "CPU time the executor spent running this task," measured in nanoseconds: two fields, one for wall-clock duration and one for CPU consumption[^spark-history-server]. Both descriptions carry the same qualifier, "this includes time fetching shuffle data," so shuffle-fetch blocking time counts toward `executorRunTime` (and even `executorCpuTime`)[^spark-history-server]. The docs don't say whether other blocking I/O (e.g., an HDFS/S3 read outside of shuffle) counts the same way. The retrieved text doesn't address it, so treat that as `[UNRESOURCED]` beyond the shuffle-fetch case.

## Q2. Is jvmGCTime included in executorRunTime, or is it additive? — i.e., does executorRunTime + jvmGCTime > wall-clock task time?

`jvmGCTime` is a subset of `executorRunTime`, not additive on top of it. The docs define it as "elapsed time the JVM spent in garbage collection while executing this task"[^spark-history-server]. The phrase "while executing this task" puts GC pauses inside the task's execution window, not outside it. Since `executorRunTime` is itself the wall-clock time the executor spent running the task[^spark-history-server], summing `executorRunTime + jvmGCTime` double-counts the GC pauses and overstates the wall-clock duration.

## Q3. What is peakExecutionMemory exactly — is it measured per-task or per-executor? Does it include storage memory?

`peakExecutionMemory` is a per-task metric, not a per-executor one. It sits in the Task Metrics table alongside `executorRunTime`, `jvmGCTime`, etc., and is defined as "peak memory used by internal data structures created during shuffles, aggregations and joins," where "the value of this accumulator should be approximately the sum of the peak sizes across all such data structures created in this task"; for SQL jobs it "only tracks all unsafe operators and ExternalSort"[^spark-history-server]. That scope (shuffles, aggregations, joins, unsafe operators, `ExternalSort`) is execution memory, not storage/cache memory. It does not include memory for cached RDDs or broadcast variables, which the same docs track separately under executor-level storage-memory fields (`memoryUsed`, `.usedOnHeapStorageMemory`, etc.)[^spark-history-server]. Those storage-memory and `peakMemoryMetrics.*` fields are executor-level, not task-level, and are reported via the executor heartbeat[^spark-history-server].

## Q4. Does shuffleReadMetrics.remoteBytesRead include local reads (same host shuffle), or only cross-node reads?

Only cross-node reads. The shuffle read metrics table keeps the two counted separately: `.remoteBytesRead` is "number of remote bytes read in shuffle operations," while `.localBytesRead` is "number of bytes read in shuffle operations from local disk (as opposed to read from a remote executor)"[^spark-history-server]. The same split exists one level up for block counts (`.remoteBlocksFetched` vs. `.localBlocksFetched`, "number of local (as opposed to read from a remote executor) blocks fetched"), with `.totalBlocksFetched`/`.totalBytesRead` provided as the explicit sum of "both local and remote"[^spark-history-server]. So same-host shuffle reads land in `localBytesRead`, and `remoteBytesRead` reflects cross-node traffic only.

## Q5. What is the exact condition Spark uses to fire a speculative task — is it based on a fraction of median task duration, a percentile, or an absolute threshold? What config controls it?

It's a combination of a stage-completion quantile gate and a multiplier-of-median threshold, with an additional absolute-floor and (as of 3.4) an efficiency check layered on top. `spark.speculation` (default `false`) turns speculative execution on; when enabled, `spark.speculation.quantile` (default `0.9`) is "fraction of tasks which must be complete before speculation is enabled for a particular stage," and `spark.speculation.multiplier` (default `3`) is "how many times slower a task is than the median to be considered for speculation"[^spark-configuration]. `spark.speculation.minTaskRuntime` (default `100ms`, since 3.2.0) sets a floor so very short tasks aren't speculated just for being slower-than-median, and `spark.speculation.task.duration.threshold` (since 3.0.0) is an alternative absolute-duration trigger usable for stages with very few tasks[^spark-configuration]. Since 3.4.0, `spark.speculation.efficiency.enabled` (default `true`) adds an efficiency filter: a task is only "inefficient" (and thus a speculation candidate) if its data-process rate is below the stage average times `spark.speculation.efficiency.processRateMultiplier` (default `0.75`), or if its duration exceeds `spark.speculation.efficiency.longRunTaskFactor` (default `2`) multiplied by the same time threshold (`spark.speculation.multiplier * successfulTaskDurations.median` or `spark.speculation.minTaskRuntime`), regardless of process rate[^spark-configuration]. `spark.speculation.interval` (default `100ms`) controls how often Spark checks for speculation candidates[^spark-configuration].

## Q9. What is fetchWaitTime in task metrics — what exactly is the executor waiting for, and does it include deserialization time?

`shuffleReadMetrics.fetchWaitTime` is "time the task spent waiting for remote shuffle blocks. This only includes the time blocking on shuffle input data. For instance, if block B is being fetched while the task is still not finished processing block A, it is not considered to be blocking on block B"[^spark-history-server]. So it's narrow: only time the task is stalled waiting on a shuffle block it needs next, not time spent prefetching blocks in the background while busy with something else. It does not include deserialization time; that's tracked as its own separate metric, `executorDeserializeTime`, "elapsed time spent to deserialize this task"[^spark-history-server], distinct from the shuffle-fetch-wait accounting.

## Q11. When a task attempt is superseded by a later retry after executor loss (`ExecutorLostFailure`) or a shuffle `FetchFailed`, what executor time is wasted on the abandoned attempt, and how is the dominant cause (lost executor vs. fetch failure) identified from the event log?

Every task attempt, successful or not, carries the standard task metrics: `executorRunTime` ("Elapsed time the executor spent running this task. This includes time fetching shuffle data") and `executorCpuTime`[^spark-monitoring]. These are recorded for the abandoned attempt exactly as for any other. Because only the winning attempt's output is kept, all of the `executorRunTime`/`executorCpuTime` accrued by the superseded attempt is pure loss: none of that compute contributes to the job's result once the TaskScheduler resubmits the task elsewhere. The TaskScheduler performs this resubmission: "If an executor dies or a task throws an exception, the TaskScheduler resubmits the task to another executor, respecting Spark's task locality preferences"[^luminousmen-anatomy]. The previous attempt's runtime is discarded work, not carried forward.

The two causes are handled differently by Spark's own machinery, which is how they can be told apart after the fact. A lost executor removes the executor (and any shuffle map output it had already written) from the pool outright: "dynamic allocation may remove an executor before the shuffle completes, in which case the shuffle files written by that executor must be recomputed unnecessarily"[^spark-job-scheduling]. So an `ExecutorLostFailure` wastes not just the running task's time but potentially prior map-output-writing time from that same executor that now has to be redone. A shuffle `FetchFailed`, by contrast, is a read-side failure on a still-alive remote executor, and Spark's exclusion policy treats it as its own category: `spark.excludeOnFailure.killExcludedExecutors`, "(Experimental) If set to true, allow Spark to automatically kill the executors when they are excluded on fetch failure or excluded for the entire application"[^spark-configuration]. Spark's scheduler explicitly distinguishes "excluded on fetch failure" from a general executor loss when deciding whether to kill an executor. That distinction in Spark's own accounting is the basis for identifying, from the retained failure information, whether a given abandoned attempt's dominant cause was the executor disappearing or a remote block fetch failing.

## Q12. What is the per-task scheduling and serialization overhead in Spark, and when does `coalesce()` (no shuffle) versus `repartition()` (full shuffle) reduce the cost of too many tiny tasks?

Spark schedules tasks around data locality rather than moving data to code: "Spark builds its scheduling around this general principle" that shipping serialized code is cheaper than shipping data, preferring `PROCESS_LOCAL` down to `ANY` locality and waiting a configurable timeout for a busy CPU to free up before shipping data to a farther executor[^spark-tuning-guide]. On top of that placement cost, every task pays a serialization cost for its closure and (if not using Kryo) for its data: Java's default `ObjectOutputStream`-based serialization "is flexible but often quite slow, and leads to large serialized formats," while Kryo is "significantly faster and more compact than Java serialization (often as much as 10x)"[^spark-tuning-guide]. Unlike MapReduce, Spark's per-task startup overhead is low enough that "it's almost always better to err on the side of a larger number of tasks (and thus partitions)... The difference stems from the fact that MapReduce has a high startup overhead for tasks, while Spark does not"[^cloudera-tuning-spark]. But that overhead is not zero, and it dominates once partitions get too small. With a default of 200 shuffle partitions applied to a dataset of only a few megabytes, "those 200 partitions will each get like ten rows. Tasks become microscopic. Most of your CPUs will just be sitting there doing nothing, wasting cluster hours"[^luminousmen-partitions]. The same small-partition penalty shows up on the shuffle-read side: production measurements found "the average shuffle block size is only 10s of KBs, which leads to delayed shuffle data fetch," and the shuffle reduce stages with the largest fetch delays (over 30 seconds per task) were consistently the ones with small block sizes[^spark-spip-magnet].

`coalesce()` and `repartition()` address this in different ways and at different costs. `repartition()` is a full reshuffle: it gives you control and rebalancing Spark won't do on its own. With `df.repartition(200)`, "you're paying for predictability"[^luminousmen-partitions]. `coalesce()` is a shuffle-free merge of existing partitions ("no data movement, no shuffle"), typically used right before a write, e.g. `df.coalesce(100).write.parquet(...)` to collapse thousands of tiny output files into a manageable number cheaply[^luminousmen-partitions]. Because it merely stacks partitions together without redistributing data, `coalesce()` doesn't fix skew: uneven input partitions stay uneven, just grouped. Pushing it too far (`coalesce(1)`) kills parallelism by funneling all work onto one executor while the rest sit idle[^luminousmen-partitions]. There is a middle option, `coalesce(N, shuffle=True)`, which "acts more like a repartition, but leaning toward reduction... not free (you pay for the shuffle cost) but you get better distribution and fewer partitions"[^luminousmen-partitions]. Use `coalesce()` when you only need fewer partitions and the existing distribution is already reasonably even, e.g. collapsing output files. Use `repartition()` when the partitioning itself needs to be fixed or rebalanced, accepting the shuffle cost to get there.

## Q13. What distinguishes whole-job abandonment (retries exhausted, e.g. `spark.task.maxFailures`) from transient task retries that succeed, and what final-stage failure reasons drive a job to fail outright?

A transient retry never threatens the job: `spark.task.maxFailures` (default 4) counts "continuous failures of any particular task before giving up on the job. The total number of failures spread across different tasks will not cause the job to fail; a particular task has to fail this number of attempts continuously. If any attempt succeeds, the failure count for the task will be reset"[^spark-configuration]. So a task that fails once and then succeeds on retry resets its counter and never counts toward abandonment. Only an unbroken run of failures on the same task, up to the configured limit (3 retries allowed by default, since allowed retries = value − 1), tips the job into failure.

Whole-job abandonment is a layered escalation. At the task level it's `spark.task.maxFailures` exhaustion as above[^spark-configuration]. At the stage level, `spark.stage.maxConsecutiveAttempts` (default 4) bounds "the number of consecutive stage attempts allowed before a stage is aborted"[^spark-configuration]. By default, `spark.stage.ignoreDecommissionFetchFailure` (true, since 3.4.0) excludes fetch failures caused by graceful executor decommission from counting toward that limit, so a decommission-triggered `FetchFailed` doesn't push a stage toward abortion the way a genuine repeated fetch failure would[^spark-configuration]. On YARN and Kubernetes there's a further application-level ceiling: `spark.executor.maxNumFailures` (default `numExecutors * 2`, minimum 3, since 3.5.0) is "the maximum number of executor failures before failing the application," while `spark.executor.failuresValidityInterval` (since 3.5.0) lets failures spaced far enough apart be "considered independent and not accumulate towards the attempt count"[^spark-configuration].

Mechanistically, the TaskScheduler owns retries at the task level, but it is "the DAGScheduler that ultimately declares the job to have failed"[^luminousmen-anatomy] once those retry budgets are exhausted. Since "a Spark job corresponds to one action" and the DAG for that action is fixed once the action is called[^high-perf-spark], an aborted stage cascades directly into failure of the job built on it. This job-level failure is itself distinct from application-attempt failure: on YARN, "each application may have multiple attempts," and the history server displays failed attempts alongside "any ongoing incomplete attempt or the final successful attempt"[^spark-history-server], a separate, higher layer of retry (driver/application restart) above the in-job task and stage retries. The final-stage failure reasons that drive a job to fail outright are a single task failing `spark.task.maxFailures` times consecutively, a stage being resubmitted until `spark.stage.maxConsecutiveAttempts` is reached and aborted, or (on YARN/Kubernetes) cumulative distinct executor failures exceeding `spark.executor.maxNumFailures`[^spark-configuration].

## For the memoryUtilization detector: what causes executor cores to sit idle while the executor is held (task parallelism below allocated cores), and what Spark guidance bounds a healthy executor-core count and dynamic-allocation idle-timeout so a whole executor's memory band is not held with little work?

An executor's core count sets its concurrency ceiling. `spark.executor.cores` controls the number of concurrent tasks an executor can run, so `--executor-cores 5` lets that executor run at most five tasks at once[^cloudera-tuning-spark]. The scheduler turns cores into task slots: the slot count is derived from `spark.executor.cores` and `spark.task.cpus` (minimum 1), where `spark.task.cpus` defaults to 1 core per task[^spark-configuration]. Cores go idle whenever there are fewer runnable tasks than slots. A stage with fewer partitions than the total slots across executors leaves slots empty; so does the tail of a stage, where only a straggler or two keep running after their peers finish; and raising `spark.task.cpus` above 1 makes each task reserve several cores, so fewer tasks run side by side. The executor JVM is still held with its whole fixed memory allocation during those gaps, because an executor is a single JVM process granted a fixed heap; on YARN that is the amount YARN allocates, and on Kubernetes it becomes the pod memory limit[^luminousmen-memory-management].

On bounding a healthy core count, the guidance is against packing every core of a node into one "fat" executor. Assigning all 16 cores of a node to a single executor hurts HDFS throughput and produces excessive garbage collection, and the recommendation is to avoid it in favor of a balance between tiny (one core per executor) and fat (one executor per node) sizing[^spark-notes-executor-sizing]. When sizing on YARN, the cluster also needs cores left for the OS and Hadoop daemons rather than handing 100% of a node to Spark containers[^cloudera-tuning-spark].

Dynamic allocation is what reclaims the memory band once the work drains. It lets an application request executors when there is a backlog of pending tasks and free them up when idle[^cloudera-tuning-spark]. Executors are requested in rounds once tasks have been pending for `spark.dynamicAllocation.schedulerBacklogTimeout` (default 1s), then again every `spark.dynamicAllocation.sustainedSchedulerBacklogTimeout` while the backlog persists[^spark-job-scheduling]. On the release side, an application removes an executor after it has been idle longer than `spark.dynamicAllocation.executorIdleTimeout`[^spark-job-scheduling]. The trap for a held memory band is cached data: by default executors holding cached blocks are never removed, governed by `spark.dynamicAllocation.cachedExecutorIdleTimeout`, whose default is infinity[^spark-configuration]. Such an executor keeps its full memory band indefinitely even with no active tasks unless that timeout is set to a finite value, or `spark.shuffle.service.fetch.rdd.enabled` is turned on so that executors holding only disk-persisted blocks are treated as idle after `spark.dynamicAllocation.executorIdleTimeout` and released[^spark-job-scheduling]. To avoid holding executors that barely work in the first place, `spark.dynamicAllocation.executorAllocationRatio` (default 1.0, maximum parallelism) can be lowered toward 0.5 to reduce the target executor count, since with small tasks full-parallelism allocation wastes resources on executors that might not even do any work[^spark-configuration].

## In Spark's executor memory model, what is the relationship between an executor's peak used memory and its total allocated memory, and why can a derived estimate of unused ('wasted') allocated memory only be a rough, low-confidence signal rather than an exact measurement?

An executor is a single JVM process inside a container, a YARN container or a Kubernetes pod, that is handed a fixed amount of memory when the application starts[^luminousmen-memory-management]. That allocated total is larger than the heap alone. Spark sizes the container as the sum of four parts, `executorMemoryMiB + memoryOverheadMiB + memoryOffHeapMiB + pysparkMemToUseMiB`[^luminousmen-memory-management]. The heap piece comes from `spark.executor.memory` (or `--executor-memory`) and becomes the JVM `-Xmx`[^luminousmen-memory-management]; overhead defaults to the greater of 10% of executor memory and 384 MB[^luminousmen-memory-management]; off-heap memory set through `spark.memory.offHeap.size` is not folded into that overhead by default[^luminousmen-memory-management]. Every executor in a given application receives the same fixed heap and core count[^cloudera-tuning-spark].

Inside the heap the allocation is layered rather than flat. Spark first reserves 300 MB for its own bookkeeping[^luminousmen-memory-management], leaving a usable pool of `executor memory - 300 MB`. User memory takes `1 - spark.memory.fraction` of that pool, 40% by default, and the remaining 60% (`spark.memory.fraction` = 0.6) forms the unified execution-and-storage region[^luminousmen-memory-management][^spark-tuning-guide]. Learning Spark frames the same layout as execution, storage, and reserved memory, split roughly 60/40 once the 300 MB reserve is set aside[^learning-spark-2e].

Peak used memory is a different kind of quantity: a high-water mark, not a ceiling. Spark's metrics system records it under `peakMemoryMetrics.*`, covering `JVMHeapMemory`, `JVMOffHeapMemory`, on- and off-heap execution and storage, the unified on- and off-heap totals, direct and mapped buffer pools, and process-tree resident and virtual memory[^spark-monitoring]. Those peak values only reach the event log when `spark.eventLog.logStageExecutorMetrics` is true[^spark-monitoring]. Since each figure is the maximum its pool ever reached, peak used memory sits at or below the allocated total by construction, and the space between the two is the executor's unused headroom.

Turning that headroom into a number for wasted allocation stays approximate, for several concrete reasons.

First, the peak heap figure counts garbage. `JVMHeapMemory` is defined as the peak used heap, where the used amount is "the amount of memory occupied by both live objects and garbage objects that have not been collected"[^spark-monitoring]. The peak therefore overstates the live footprint by whatever uncollected garbage happened to be resident at the high-water moment.

Second, the region boundaries move. Execution and storage share one unified region and borrow from each other; execution can evict storage down to a protected threshold[^spark-tuning-guide], and Spark shrinks the storage region as soon as execution asks for more[^luminousmen-memory-management]. The monitoring metrics carry the same caveat: `totalOnHeapStorageMemory` and `totalOffHeapStorageMemory` "can vary over time, depending on the MemoryManager implementation"[^spark-monitoring]. There is no single fixed "allocated to storage" value to subtract a peak from.

Third, part of the allocation is never measured. User memory has "no tracking, no boundaries", and Spark does not manage or account for what UDFs, Python wrappers, or native libraries place there[^luminousmen-memory-management]. Overhead memory, the thread stacks, metaspace, JIT buffers, and Python workers, sits outside the managed pools as well[^luminousmen-memory-management]. Memory Spark never counts cannot show up in a used-versus-allocated subtraction.

Fourth, the allocated total spans regions the heap peak does not cover. The container total bundles overhead, off-heap, and PySpark memory alongside the heap[^luminousmen-memory-management], so setting one heap high-water mark against the full allocated footprint compares quantities measured on different bases.

Each `peakMemoryMetrics` entry is also an independent maximum over the run[^spark-monitoring], so the separate pool peaks need not have occurred at the same instant. ## In a Spark physical plan, what is a ReusedExchange or repeated scan subtree, how do exchange reuse and cache()/persist() avoid recomputing an identical subtree, and why is inferring a duplicated subtree from the plan only a medium-confidence signal?

A physical plan (Spark plan) is what the engine produces after optimizing the logical plan: it "specifies how the logical plan will execute on the cluster," compiling the query down into a series of RDDs and transformations[^definitive-guide]. Within that plan, a shuffle or a broadcast is an exchange. These exchanges are the points where pipelining stops: "Spark operators are often pipelined and executed in parallel processes. However, a shuffle or broadcast exchange breaks this pipeline. We call them materialization points and use the term 'query stages' to denote subsections bounded by these materialization points"[^databricks-aqe]. A repeated scan subtree is the same source read, plus the operators above it, showing up in more than one branch of the plan. Left alone, that repetition costs real work. Put the same logic in "two different branches of your pipeline" and you are "basically signing up to recompute everything from scratch multiple times," because every action on an uncached DataFrame starts from the source and rebuilds all intermediate steps[^luminousmen-caching-mechanics]. The specific `ReusedExchange` operator label, and the exchange-reuse SQL rule that inserts it, are [UNRESOURCED]; naming that node and its planner rule would need the Spark SQL execution documentation or source.

Exchange reuse rests on the fact that a shuffle already writes its output to disk. Spark "always executes shuffles by first having the 'source' tasks ... write shuffle files to their local disks," and one consequence is that "running a new job over data that's already been shuffled does not rerun the 'source' side of the shuffle. Because the shuffle files were already written to disk earlier, Spark knows that it can use them to run the later stages of the job, and it need not redo the earlier ones. In the Spark UI and logs, you will see the pre-shuffle stages marked as 'skipped'"[^definitive-guide]. High Performance Spark makes the same point for the RDD case: "if the driver program reuses an RDD that has already been shuffled, Spark may be able to avoid recomputing that RDD up to the point of shuffle by using the shuffle files on the mapper," and the web UI shows the resulting skipped stages[^high-perf-spark]. So when the same materialized exchange output feeds two consumers, the second one reads the existing shuffle files instead of recomputing the subtree beneath it.

`cache()` and `persist()` truncate recomputation more explicitly by materializing the result and keying future lookups on it. Persisting "means materializing an RDD (usually by storing it in memory on the executors) for reuse during the current job"[^high-perf-spark]; caching is persisting with in-memory storage, and the two are "most useful to avoid recomputation during one Spark job or to break RDDs with long lineages"[^high-perf-spark]. `.cache()` is shorthand for `.persist(StorageLevel.MEMORY_AND_DISK)`[^luminousmen-caching-mechanics]. In the Structured API the mechanism is plan-keyed rather than reference-keyed: when you mark a DataFrame to be cached, Spark "modify[ies] the logical plan of your query by wrapping it in a special logical operator called InMemoryRelation," and this happens through the CacheManager after the analyzer phase[^luminousmen-caching-mechanics]. The Definitive Guide frames the lookup the same way: "caching is done based on the physical plan. This means that we effectively store the physical plan as our key ... and perform a lookup prior to the execution of a Structured job"[^definitive-guide]. On a hit, Spark returns the stored data instead of rebuilding intermediate steps from the source[^luminousmen-caching-mechanics].

Reading a duplicated subtree straight off the plan is a weaker signal than it looks, for two reasons grounded in how the cache actually matches and materializes. First, the match is exact and it happens on the wrong plan for eyeballing. The cache "is tied to the analyzed logical plan, not the final optimized one," so two queries that are semantically identical but carry different analyzed plans will miss: when they "don't match exactly," Spark "will skip the cache and recompute everything," even though "the optimizer will eventually produce the same physical plan"[^luminousmen-caching-mechanics]. A subtree that reads as shared in the printed plan may still be recomputed. Second, caching is lazy and often partial. It "is a lazy operation, meaning that things will be cached only as they are accessed"[^definitive-guide], "the only blocks that get cached are the ones Spark was forced to touch," and Spark offers "no built-in visibility into how much of your DataFrame is actually cached, or how much has already been evicted"[^luminousmen-caching-mechanics]. Whether a repeated subtree turns into avoided work comes down to runtime facts the static plan never shows: cache hits, retained shuffle files, and eviction.

## What is the small-files problem when Spark reads or writes many tiny files, what output file-size range do Spark and Parquet guidance target, and how do compaction, coalesce()/repartition(), and AQE advisoryPartitionSizeInBytes control output file size?

The small-files problem is the cost of managing a large count of tiny files. Writing lots of small files incurs significant metadata overhead, and Spark does not do well with them; many filesystems such as HDFS handle them poorly too, which is why the pattern is called the "small file problem"[^definitive-guide]. The same trap appears on the read side: driving `spark.sql.files.maxPartitionBytes` (default 128 MB) too low produces many small partition files, adding an inordinate amount of disk I/O and performance degradation from filesystem operations like opening, closing, and listing directories, which on a distributed filesystem can be slow[^learning-spark-2e]. Spark writes one file per output partition, so a job left with 200 partitions writes 200 files and one left with 3000 writes 3000, even when many hold only a handful of rows. That in turn punishes any downstream job forced to read thousands of tiny files[^luminousmen-partitions]. The opposite extreme hurts too: files that are too large make it inefficient to read whole blocks when you need only a few rows[^definitive-guide].

On target sizing, the guidance the retrieved sources give is anchored to block size rather than a single recommended output-file band. File blocks on data stores typically range from 64 MB to 128 MB, and on HDFS and S3 the default is 128 MB[^learning-spark-2e]. Spark's read-partition size, `spark.sql.files.maxPartitionBytes`, defaults to 128 MB and is deliberately aligned to the Parquet block size (`parquet.block.size`)[^spark-source-sql-conf]. Practical field guidance treats that 128 MB as the center of a healthy band: Parquet files mostly at 256 MB or larger under-parallelize reads, while 8 MB files spawn too many tasks, so the split size should match the actual file distribution rather than the default[^luminousmen-optimization-checklist]. A more explicit recommended output-file-size *range* beyond these block-aligned numbers is `[UNRESOURCED]` (a Parquet or vendor sizing guide would be needed).

Compaction, in the sense the sources describe it, is the practice of fusing many small files into fewer well-sized ones before or at write time. One direct lever is `maxRecordsPerFile`, introduced in Spark 2.2 to cap the records per file and target an optimum size; `df.write.option("maxRecordsPerFile", 5000)` guarantees at most 5,000 records per file[^definitive-guide]. The more common lever is repartitioning right before the write. `coalesce()` is a quiet merge that fuses existing partitions with no shuffle and no data movement, so `df.coalesce(100).write.parquet(...)` turns 3000 tiny files into 100 reasonably sized ones[^luminousmen-partitions]. Watch the limits, though: `coalesce()` does not rebalance data, so uneven inputs stay uneven once lumped together, and pushing it to `coalesce(1)` kills parallelism by forcing one executor to do all the work[^luminousmen-partitions]. `repartition()` is instead a full reshuffle that buys even distribution at the cost of that shuffle, and `coalesce(50, shuffle=True)` splits the difference, leaning toward reduction while still paying for a shuffle to get better balance[^luminousmen-partitions]. The same control exists in SQL through the `COALESCE`, `REPARTITION`, and `REBALANCE` hints, which reduce the number of output files just as the Dataset-API methods do[^spark-sql-perf-tuning]. Reading a directory full of small files is cushioned somewhat by `spark.sql.files.openCostInBytes` (default 4 MB), the estimated per-file open cost Spark uses when packing multiple small files into one partition; over-estimating it lets partitions of small files finish faster[^spark-configuration].

For adaptive control, Adaptive Query Execution (since Spark 3.0) can merge tiny shuffle partitions at runtime once `spark.sql.adaptive.enabled` and `spark.sql.adaptive.coalescePartitions.enabled` are set, coalescing shuffle output toward a target input size (`spark.sql.adaptive.shuffle.targetPostShuffleInputSize`, e.g. 64 MB in the cited example)[^luminousmen-partitions]. The key caveat is scope: AQE only kicks in after the first shuffle, so its coalescing fixes shuffle-output partition counts but will not repair input-side partitioning or bad file layouts[^luminousmen-optimization-checklist]. The knob that names the size directly is `spark.sql.adaptive.advisoryPartitionSizeInBytes`, the advisory size in bytes of a shuffle partition during adaptive optimization, which defaults to 64 MB (since 3.0.0) and takes effect when Spark coalesces small shuffle partitions or splits a skewed one[^spark-sql-perf-tuning]. `spark.sql.adaptive.coalescePartitions.enabled` (default true) is what drives that coalescing toward the advisory target[^spark-sql-perf-tuning].

## What does spark.sql.autoBroadcastJoinThreshold control and what is its default, when should a join broadcast the smaller side versus shuffle, and what are the failure modes of broadcasting a table that is too large (driver collection and executor memory pressure)?

`spark.sql.autoBroadcastJoinThreshold` sets the maximum table size, in bytes, that Spark will broadcast to every worker node when planning a join; setting it to `-1` turns automatic broadcasting off entirely[^spark-configuration]. It has been available since Spark 1.1.0 and defaults to 10 MB (10485760 bytes)[^spark-sql-perf-tuning]. The config source confirms the same default, stored as the string `"10MB"`, and notes an important caveat: Spark can only apply this size test when statistics exist, meaning Hive Metastore tables for which `ANALYZE TABLE <tableName> COMPUTE STATISTICS noscan` has run, or file-based data source tables whose statistics are computed directly from the files[^spark-source-sql-conf].

That threshold decides which physical join strategy Spark picks. Spark has two ways to move data for a join: the shuffle join, which forces all-to-all communication across the cluster, and the broadcast join, which ships one side out to every executor[^definitive-guide]. A broadcast hash join skips the shuffle and runs very fast when one side is small enough. It covers every join type except full outer and needs an equi-join[^high-perf-spark]. Since it is so cheap, Spark reaches for it whenever a side qualifies[^high-perf-spark]. So the rule of thumb is: if one dataset is much smaller than the other, fits the 10 MB default (or a larger threshold you can afford in memory), and you only need an equi-join, broadcast the small side. When neither side fits, Spark shuffles instead. Set the threshold to `-1` and Spark always falls back to a shuffle sort merge join[^learning-spark-2e]. A dimension table in the 10-200 MB range is a judgement call, raise the threshold or force it with `broadcast(df)`, but past roughly 200 MB the broadcast usually costs more than the shuffle it replaces[^luminousmen-optimization-checklist].

Broadcasting the small side sends a full copy of that table to every executor, which pays off only when network bandwidth and executor memory are not the bottleneck[^learning-spark-2e]. Push a table that is too large through this path and it breaks in two ways: too-large task result errors and out-of-memory failures, both because the oversized table has to be collected and shipped whole[^high-perf-spark]. The broadcast nested loop join, the non-equi variant, carries the same out-of-memory risk, so Spark keeps it as a last resort[^high-perf-spark]. The size gate exists for exactly this reason: a copy on every executor is harmless for a small table and a memory hazard for a large one[^luminousmen-optimization-checklist].

## What is the relationship between a stage's task count and the cluster's total executor cores, and what Spark guidance covers choosing the number of partitions/tasks per stage so parallelism is neither far below nor far above available cores?

The scheduling unit ties straight to partitions. A stage's task count equals the number of partitions in the last RDD of that stage, and every task processes one partition as a single thread[^cloudera-tuning-spark]. Put plainly: every partition is one task, and one task is one thread, so the partition count is what decides how much parallelism Spark can pull out of the cluster[^luminousmen-partitions]. On the resource side, each executor runs a fixed number of tasks at once, set by `spark.executor.cores`. Setting `--executor-cores 5` means an executor can run at most five tasks simultaneously[^cloudera-tuning-spark]. Each task claims `spark.task.cpus` cores, which defaults to 1[^spark-configuration]. Add the cores up across executors and you get the total pool of slots the cluster can run concurrently; the TaskScheduler is the piece that hands tasks to those slots, thinking in executors and available CPU cores rather than in RDDs[^luminousmen-anatomy]. A stage's task count measured against that pool is therefore what determines how much of the cluster is actually doing work.

Both directions hurt. When a stage has fewer tasks than there are slots to run them in, it can't put all the cluster's CPU to work, and it also piles more memory pressure onto any aggregation that runs inside each task[^cloudera-tuning-spark]. Spark itself warns that clusters stay under-used unless the level of parallelism for each operation is set high enough[^spark-tuning-guide]. Push the other way and partitions get tiny, which floods the cluster with per-task overhead[^luminousmen-partitions].

For sizing the count, the Spark tuning guide gives the standard heuristic: in general it recommends 2-3 tasks per CPU core in the cluster[^spark-tuning-guide]. Learning Spark frames the floor the same way: schedule a thread per task per core, aim for at least as many partitions as there are cores on the executor, and once there are more partitions than cores every core stays busy[^learning-spark-2e]. The data-parallel view underneath this is simply that more partitions means more parallelism, with each executor core assigned its own partition to work on[^advanced-analytics-pyspark]. When you're unsure which way to round, err high: too many partitions is usually better than too few, because Spark has low task startup overhead (unlike MapReduce, where you're told to be conservative)[^cloudera-tuning-spark]. A practical way to land on the number is experimentation: take the parent RDD's partition count and keep multiplying by 1.5 until performance stops improving[^cloudera-tuning-spark].

The knob for the default is `spark.default.parallelism`, which the tuning guide names as the way to change the default level of parallelism[^spark-tuning-guide]. It sets the partition count for transformations like `join`, `reduceByKey`, and `parallelize` when the user doesn't specify one; for distributed shuffle operations its default is the largest number of partitions among the parent RDDs[^spark-configuration]. [UNRESOURCED: the DataFrame/SQL equivalent, `spark.sql.shuffle.partitions`, and its default — would need the Spark SQL performance-tuning documentation.]

## How does Adaptive Query Execution size shuffle partitions at runtime through post-shuffle coalescing and skew-partition splitting, and how do spark.sql.shuffle.partitions and spark.sql.adaptive.advisoryPartitionSizeInBytes bound partition size when a shuffle produces partitions that are too large, too small, or skewed?

Adaptive Query Execution re-optimizes a query in the middle of its run. It first executes the leaf stages, and as each shuffle stage materializes it collects that stage's runtime statistics, feeds them back into the optimizer and physical planner, and applies adaptive-execution-specific rules such as coalescing partitions and skew join handling before launching the stages downstream[^databricks-aqe]. Because these decisions use real shuffle-file sizes rather than static estimates, AQE can correct a partition count that would otherwise be wrong for the data at hand.

The starting point is `spark.sql.shuffle.partitions`, the number of partitions Spark uses when shuffling data for joins or aggregations; it has existed since Spark 1.1.0 and defaults to 200[^spark-source-sql-conf]. That single fixed number is exactly what AQE exists to fix. Run 200 partitions over a few megabytes and each task gets a handful of rows while most CPUs sit idle; run the same 200 over hundreds of gigabytes and every executor is overloaded, often into memory errors. Push any one partition past the memory an executor has and Spark spills it to disk[^luminousmen-partitions]. The 200 default is frequently too high for smaller or streaming workloads, where dropping it toward the executor core count reduces the flood of tiny partitions crossing the network[^learning-spark-2e]. AQE's recommended pattern instead is to leave the initial count deliberately large and let it combine adjacent small partitions into bigger ones at runtime by reading the shuffle-file statistics[^databricks-aqe].

**Coalescing partitions that are too small.** `spark.sql.adaptive.coalescePartitions.enabled` (default true, since 3.0.0) merges contiguous shuffle partitions up to a target size to avoid too many small tasks[^spark-sql-perf-tuning]. The target is `spark.sql.adaptive.advisoryPartitionSizeInBytes`, the advisory size in bytes of a shuffle partition during adaptive optimization, which takes effect both when Spark coalesces small partitions and when it splits skewed ones; its default is 64 MB[^spark-sql-perf-tuning]. In the configuration reference the same property is documented as defaulting to the value of the deprecated `spark.sql.adaptive.shuffle.targetPostShuffleInputSize`[^spark-configuration], and the source defines that fallback with a default string of "64MB"[^spark-source-sql-conf]. The Databricks example makes the mechanism concrete: five post-shuffle partitions with three very small ones get coalesced into a single partition, cutting the final aggregation from five tasks to three[^databricks-aqe]. The initial partition count fed into this step is `spark.sql.adaptive.coalescePartitions.initialPartitionNum`, which when unset equals `spark.sql.shuffle.partitions`[^spark-source-sql-conf]. A floor of `spark.sql.adaptive.coalescePartitions.minPartitionSize` (default 1MB) caps how small a coalesced partition may end up, which matters when the adaptively calculated target size is too small[^spark-configuration]. By default `spark.sql.adaptive.coalescePartitions.parallelismFirst` is true, so Spark ignores the advisory target size and honors only the 1MB minimum, calculating a smaller target from cluster parallelism to keep task count high; setting it false on a busy cluster restores the advisory-size target for more efficient resource use[^spark-sql-perf-tuning].

**Splitting partitions that are too large or skewed.** `spark.sql.adaptive.skewJoin.enabled` (default true, since 3.0.0) handles skew in shuffled joins, both sort-merge and shuffled hash, by splitting the skewed partitions and replicating the matching side where needed[^spark-configuration]. A partition counts as skewed only when it exceeds both conditions: its size is larger than `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (default 5.0) times the median partition size, and larger than `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default 256MB)[^spark-configuration]. That threshold should ideally be set larger than `advisoryPartitionSizeInBytes`, since the oversized partition is split down toward the advisory size once it qualifies[^spark-configuration]. A parallel path exists for rebalance operations: `spark.sql.adaptive.optimizeSkewsInRebalancePartitions.enabled` (default true, since 3.2.0) splits skewed partitions produced by `RebalancePartitions` to smaller ones according to the same advisory target size[^spark-sql-perf-tuning], and `spark.sql.adaptive.rebalancePartitionsSmallPartitionFactor` (default 0.2, since 3.3.0) merges a fragment back if its size is below that factor times `advisoryPartitionSizeInBytes`, so splitting does not overshoot into tiny slivers[^spark-configuration].

Taken together, `spark.sql.shuffle.partitions` sets the coarse initial grid and `advisoryPartitionSizeInBytes` is the size AQE steers each partition toward from both directions: partitions below it get coalesced (subject to the 1MB minimum and the parallelism-first calculation), and skewed partitions above the 256MB / 5.0-factor bar get split down toward it.

## When a single Spark stage fails, what distinguishes a stage failure that is retried and succeeds from one that aborts the job, and what stage-level failure reasons (for example FetchFailed triggering a stage retry) does the scheduler act on?

Stage-level retry lives in the DAGScheduler, which owns the verdict on whether a job as a whole succeeds or fails. A failed stage gets resubmitted as a fresh attempt rather than abandoned on the spot; the job only dies once the stage cannot make progress after repeated attempts, and it is the DAGScheduler that then declares the job failed.[^luminousmen-anatomy] The line between "retried and succeeds" and "aborts the job" comes down to whether a later attempt of that stage completes before the attempt budget runs out.

That budget is `spark.stage.maxConsecutiveAttempts`, default 4, the number of consecutive stage attempts allowed before the stage is aborted.[^spark-configuration] Fail, resubmit, and finish within those attempts and the job stays alive; keep failing until the limit is spent and the job aborts.

This is a different mechanism from the task-level retry that sits underneath it. Individual task failures are handled by the TaskScheduler, which resubmits a failed task to another executor when an executor dies or a task throws.[^luminousmen-anatomy] The task-level giving-up threshold is `spark.task.maxFailures`, default 4: a single task has to fail that many attempts *continuously* before the job is abandoned, the count resets the moment any attempt of that task succeeds, and failures spread across different tasks do not by themselves fail the job (allowed retries = the value minus 1).[^spark-configuration] Task retries therefore absorb transient, isolated failures without ever reaching the stage-abort path.

Which reasons does the scheduler act on at stage granularity? A fetch failure counts against the stage attempt limit. `spark.stage.ignoreDecommissionFetchFailure`, default true since 3.4.0, exists precisely to *not* count a stage fetch failure toward `spark.stage.maxConsecutiveAttempts` when that failure came from an executor being decommissioned, which by implication means fetch failures otherwise do count toward the stage-abort budget.[^spark-configuration] Executor exclusion is the other stage-level lever. The `spark.excludeOnFailure.*` family, off by default via `spark.excludeOnFailure.enabled` (false), tracks how many tasks must fail on an executor within one stage before that executor is excluded for the stage, and can kill executors excluded on fetch failure.[^spark-configuration] Once exclusion leaves a TaskSet unschedulable because every executor has been excluded, `spark.scheduler.excludeOnFailure.unschedulableTaskSetTimeout`, default 120s, caps how long Spark waits to acquire a new executor before aborting that TaskSet.[^spark-configuration]

## When the same DataFrame/RDD or input is scanned multiple times across a job, how does cache()/persist() avoid recomputation, what storage-level tradeoffs apply, and when is caching not worthwhile (single use, or data larger than available storage memory)?

Spark does not remember results between actions. Transformations only build a DAG; the work happens when an action fires, and once that action finishes the intermediate results are discarded[^luminousmen-caching-mechanics]. Call a second action on the same logic and Spark re-runs the entire DAG from the original source, which can mean re-reading a terabyte from S3, re-reading Kafka, or repeating expensive decompression[^luminousmen-caching-mechanics]. Fork that logic into two branches of a pipeline and you sign up to recompute everything from scratch each time[^luminousmen-caching-mechanics]. The engine will recompute as many times as you ask it to unless you explicitly tell it not to[^luminousmen-caching-mechanics].

`cache()` and `persist()` are how you tell it not to. Persisting an RDD materializes it, usually in memory on the executors, so it can be reused during the current job; Spark keeps the persisted RDD's lineage so it can recompute a partition if one is lost[^high-perf-spark]. Caching (persisting at the in-memory level) and persisting are what you reach for to avoid recomputation within a single job or to break an RDD with a long lineage, since they keep the RDD on the executors for the duration of that job[^high-perf-spark]. In an application that reuses the same dataset repeatedly, this is one of the most useful optimizations available: it places a DataFrame, table, or RDD into temporary storage across the executors and makes subsequent reads faster[^definitive-guide].

Materialization is lazy and happens block by block. Every RDD (and therefore every DataFrame) is made of partitions, each partition maps to a block, and blocks are the actual unit of caching[^luminousmen-caching-mechanics]. Run `.cache()` followed by `.count()` and each partition is computed, then stored by that executor's local `BlockManager` according to the `StorageLevel`[^luminousmen-caching-mechanics]. Caching is local and incremental: each executor only caches the blocks it computes, and only when they are computed[^luminousmen-caching-mechanics]. Two consequences follow. If the executor holding a block dies before you reuse it, the block is gone and Spark recomputes it, unless a replicated level like `MEMORY_AND_DISK_2` kept a copy[^luminousmen-caching-mechanics]. And only blocks Spark was forced to touch get cached, so an action that scans a subset (`take(10)`, `limit(100)`, a filtered scan) leaves you with a partial cache; you need an action that touches every partition, such as `count()` or a full write, to materialize all of it[^luminousmen-caching-mechanics].

The RDD and Structured APIs key their caches differently. For an RDD, Spark caches the physical bits and returns them through the RDD reference[^definitive-guide]. In the Structured API, the cache is keyed on the physical plan, so a later query with a matching plan can transparently hit a cache someone else populated[^definitive-guide].

`cache()` is the no-argument shorthand; `persist()` takes a `StorageLevel` and lets you choose where and how blocks live[^luminousmen-caching-mechanics]. Each level is built from five attributes: `useDisk`, `useMemory`, `useOffHeap`, `deserialized`, and `replication`[^high-perf-spark]. The tradeoffs among the common levels:

- `MEMORY_ONLY` stores deserialized objects in the JVM and is the fastest to read, but if the RDD does not fit, the leftover partitions are simply not cached and get recomputed on the fly each time they are needed[^definitive-guide]. (`MEMORY_ONLY` is the default level for the RDD API, and `cache()` is equivalent to `persist("MEMORY_ONLY")` there[^definitive-guide][^high-perf-spark].)
- `MEMORY_AND_DISK` also stores deserialized objects but spills the partitions that do not fit to disk and reads them back when needed[^definitive-guide]. This is Spark's default caching strategy and is fine for most pipelines; reading a spilled block from disk is usually faster than re-evaluating it[^luminousmen-caching-tips]. For DataFrames, `.cache()` is shorthand for `persist(MEMORY_AND_DISK)`[^luminousmen-caching-mechanics].
- Serialized (`_SER`) variants store data as byte arrays instead of raw objects, trading read speed for a smaller memory footprint; use deserialized levels when you have spare memory and want fast access, serialized levels when you are short on memory and speed is secondary[^luminousmen-caching-tips].
- Replicated (`_2`) levels keep a second copy so tasks can keep running on a lost partition instead of waiting for recomputation, at the cost of twice the space; all levels are fault-tolerant by recomputation, but replication buys fast fault recovery[^spark-rdd-programming][^luminousmen-caching-tips].

Whether to spill to disk at all depends on recomputation cost. Enabling disk avoids recomputing large partitions that fall out of memory, but reading from disk is time-intensive, so it only pays off when recomputation is particularly expensive[^high-perf-spark]. The RDD guide puts it plainly: do not spill to disk unless the functions that produced the data are expensive or filter a large amount of it, because recomputing a partition can be as fast as reading it back from disk[^spark-rdd-programming].

Cached blocks do not live in the whole heap. The `BlockManager` shares a region governed by `spark.memory.fraction` between execution and storage[^luminousmen-caching-mechanics]. When that region fills, Spark evicts the least-recently-used partitions[^spark-rdd-programming]. Under the default memory-then-disk strategy, evicted blocks that would otherwise be lost can spill instead of being dropped[^luminousmen-caching-tips]. A persisted RDD that you stop using still occupies memory until the application ends or another cached RDD forces it out, so call `unpersist()` to reclaim it deliberately, which matters most on shared clusters[^luminousmen-caching-tips]. `unpersist()` does not block by default; pass `blocking=true` to wait until the resources are freed[^spark-rdd-programming].

Caching earns its keep when you reuse a dataset: iterative machine-learning training, frequent transformations during ETL, loops of joins against the same dataset, or multiple actions on one RDD[^learning-spark-2e][^high-perf-spark]. It is not free, and several situations do not warrant it:

- Processing a dataset only once. Caching adds serialization, deserialization, and storage cost, so caching data you will read a single time only slows you down[^definitive-guide].
- Data too big to fit in memory, or an inexpensive transformation that is not reused often regardless of size[^learning-spark-2e].
- Memory pressure. Memory spent on the cache is memory unavailable for processing, and under the default spill-to-disk strategy cached data can land in slower storage, so caching can cost more than simply re-reading the source[^luminousmen-caching-tips].
- Losing optimizer freedom. Once a dataset is cached, Catalyst works on the in-memory data and can no longer push filters down to the source system[^luminousmen-caching-tips].

There is no universal rule for what to cache; the payoff comes only when the data is reused, as with iterative algorithms that touch the same RDD every pass[^luminousmen-caching-tips]. Use memory caching judiciously, since it carries real serialization and deserialization costs depending on the `StorageLevel`[^learning-spark-2e].

## Absent a single slow host, what Spark-level factors (partition count, data volume per task, shuffle) explain why one stage is disproportionately slow relative to the rest of a job?

When no single machine is dragging, a stage that lags the rest of the job usually comes down to how the work was divided, not where it ran. Spark slices a stage into tasks, one per partition of that stage's output, and it can run no more tasks at once than the total executor cores allocated to the application (cores per executor times number of executors).[^high-perf-spark] More partitions, more that can run in parallel.[^definitive-guide]

**Too few partitions caps parallelism.** Wide stages (join, groupBy, aggregations) get their partition count from `spark.sql.shuffle.partitions`, which stays at its default of 200 whether you shuffle 20 MB or 500 GB unless you change it.[^luminousmen-partitions] If that count is small relative to the cluster, only a handful of tasks carry the stage while cores sit idle, so the stage stretches out even though its neighbors, with better-sized partitions, finish quickly. The first move to speed up a specific slow stage is to raise its parallelism: at least two or three tasks per CPU core when the stage processes a large amount of data, tuned through `spark.default.parallelism` and `spark.sql.shuffle.partitions`.[^definitive-guide]

**Large data volume per task makes each task run long.** That 200-partition default does not scale with input size, so a stage handling hundreds of gigabytes hands each task a large slice: fewer tasks run at a time, load on each executor climbs, and the stage often trips memory errors.[^luminousmen-partitions] Roughly 100-200 MB per task tends to work well, and tasks chewing through around 3 GB each while spilling are a sign you need more partitions.[^luminousmen-partitions] A rougher check: target 2-4 partitions per available core, and if one task runs 10x longer than the others you are looking at skew, not just volume.[^luminousmen-optimization-checklist]

**Heavy shuffle and spill inflate the stage's cost.** Shuffles are wide-transformation stages where Spark moves data across executors so rows with the same key land together, and during map and shuffle operations Spark writes to and reads from local-disk shuffle files, so there is heavy I/O activity that can become a bottleneck under the default configurations.[^learning-spark-2e] Volume per task feeds straight into this: if a partition grows larger than the memory available in an executor, Spark spills part of the data to disk, and spills are about the slowest thing a job can do because of the extra disk I/O and increased garbage collection, so the stage still finishes but runs far less efficiently than the rest.[^luminousmen-partitions]
