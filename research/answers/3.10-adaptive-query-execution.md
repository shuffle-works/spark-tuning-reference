# Adaptive Query Execution

## Q1. What does AQE re-optimize at runtime that the static optimizer cannot?

The static Catalyst optimizer plans a query once, before execution, using cost estimates derived from static statistics (row counts, min/max, NDVs, or defaults when statistics are missing)[^databricks-catalyst-optimizer]. Adaptive Query Execution (AQE), shipped in Spark 3.0, instead re-optimizes the plan mid-execution using runtime statistics gathered from completed "query stages": the sections of a plan bounded by shuffle or broadcast exchange materialization points[^databricks-aqe]. Because a shuffle or broadcast forces Spark to materialize its input before continuing, this is a natural checkpoint: once one or more leaf stages finish, AQE marks them complete, updates the logical plan with the real (not estimated) statistics, and reruns a selected set of logical and physical optimization rules (including AQE-specific rules such as partition coalescing and skew-join handling) before executing the next stages. This execute→reoptimize→execute loop repeats until the whole query finishes[^databricks-aqe].

AQE re-optimizes three things the static optimizer cannot, because none of them are knowable before execution: the number of post-shuffle partitions (coalescing small partitions produced by wide transformations)[^databricks-aqe], the join strategy (converting a statically planned sort-merge join to a broadcast join once the actual materialized size of a join side is known)[^databricks-aqe], and skewed partitions in a shuffle join (splitting oversized partitions detected from shuffle file statistics)[^databricks-aqe]. High Performance Spark frames this as AQE using "runtime information about the data it is processing along with the target output to go beyond static optimizations," with partitioning and join strategy singled out as the two biggest areas it impacts[^high-perf-spark]. Because these decisions depend on runtime statistics, they aren't visible in a static `explain()` output; you have to run the query and check the Spark UI for the finalized, adapted plan[^high-perf-spark]. AQE also performs empty-relation propagation, replacing subqueries that turn out to be empty (impossible joins, empty unions) with a dummy empty `LocalRelation`, again something only knowable once data is materialized[^high-perf-spark].

## Q2. At what point in query execution are shuffle statistics available to AQE — after all map tasks complete, or incrementally?

Shuffle statistics become available to AQE only once a query stage is fully materialized, not incrementally as individual map tasks finish. A shuffle or broadcast exchange is a "materialization point": the following stage can only proceed once all parallel processes producing that materialization have completed, and this is precisely why materialization points are the reoptimization opportunity: it's the moment when statistics on *all* partitions of a stage are available and the successor stage hasn't started yet[^databricks-aqe]. AQE's loop kicks off all leaf stages (the ones with no upstream dependency) first; as each one finishes materializing in full, the framework marks it complete, updates the plan with the collected runtime statistics, and re-optimizes before launching the next stages whose children are now all materialized[^databricks-aqe]. So the granularity is per-stage (i.e., after all map tasks belonging to that shuffle write have completed), not per-task.

## Q3. What is the exact algorithm for AQE partition coalescing — does it use a greedy bin-packing approach, and what is the target partition size (spark.sql.adaptive.advisoryPartitionSizeInBytes)?

The retrieved corpus documents the *inputs and target* of AQE's coalescing rule but does not spell out a bin-packing algorithm by name; based on what is available, coalescing works by combining **adjacent** small post-shuffle partitions into larger ones, guided by a target size, rather than an arbitrary bin-packing across non-adjacent partitions. The Databricks AQE post describes it as: set a relatively large initial number of shuffle partitions, then "combine adjacent small partitions into bigger partitions at runtime by looking at the shuffle file statistics"[^databricks-aqe]. In the worked example, five post-shuffle partitions where three are small are coalesced into one, cutting the number of final-aggregation tasks from five to three[^databricks-aqe].

The target size for this coalescing is `spark.sql.adaptive.advisoryPartitionSizeInBytes`, which defaults to 64 MB[^spark-sql-perf-tuning]. High Performance Spark describes the coalescing as happening "postevaluation" against this advisory size, and notes you can also bound the minimum resulting parallelism via `spark.sql.adaptive.coalescePartitions.minPartitionNum`[^high-perf-spark]. Two related knobs constrain the algorithm further: `spark.sql.adaptive.coalescePartitions.minPartitionSize` sets a floor (default 1 MB in Spark 3.2+) on coalesced partition size, useful when the adaptively calculated target is too small; and `spark.sql.adaptive.coalescePartitions.parallelismFirst` (default true, since 3.2) tells Spark to *ignore* the advisory target size entirely and instead calculate a (usually smaller) target based on cluster default parallelism, prioritizing task parallelism over hitting the 64 MB target. The docs recommend setting it to `false` on busy clusters to respect the configured target size and avoid many small tasks[^spark-sql-perf-tuning]. Coalescing is enabled via `spark.sql.adaptive.coalescePartitions.enabled` (default true) and only fires when `spark.sql.adaptive.enabled` is also true[^spark-sql-perf-tuning].

## Q4. What is the exact skew detection algorithm: what are spark.sql.adaptive.skewJoin.skewedPartitionFactor and spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes doing, and how does the split work?

The original SPARK-29544 design doc defines the skewed-partition condition precisely: a partition is considered skewed if its size is greater than the median partition size times a skew factor **F**, *and* greater than a preconfigured size threshold **S** (or, on the row-count side, greater than median row count times F and greater than a row-count threshold R)[^spark-spip-aqe-skew]. In the shipped Spark 3.0+ implementation, F is `spark.sql.adaptive.skewJoin.skewedPartitionFactor` (default 5.0) and S is `spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes` (default 256 MB): "a partition is considered as skewed if its size is larger than this factor multiplying the median partition size and also larger than" the threshold in bytes[^spark-configuration]. The docs recommend setting the byte threshold larger than `spark.sql.adaptive.advisoryPartitionSizeInBytes`[^spark-configuration].

For the split itself, the design doc's worked example is table A join table B where B's partition 0 is skewed: the `OptimizeSkewedJoin` rule divides B's skewed partition 0 into N smaller splits (e.g., 3 splits reading disjoint ranges of upstream map outputs: Map0–Map2, Map3–Map5, Map6–Map8) and creates N separate tasks, each joining its slice of B's partition 0 against A's corresponding partition 0; the N sub-join results are then unioned to produce the final output for that partition pair[^spark-spip-aqe-skew]. This trades off reading A's partition 0 N times (extra I/O) against eliminating the straggler task, which the design doc argues is worth it when skew is severe[^spark-spip-aqe-skew]. This whole mechanism only activates when both `spark.sql.adaptive.enabled` and `spark.sql.adaptive.skewJoin.enabled` (default true) are set, and it applies to both sort-merge and shuffled hash joins[^spark-configuration]. `spark.sql.adaptive.forceOptimizeSkewedJoin` (default false, since 3.3.0) forces the rule to fire even when it would introduce extra shuffle[^spark-sql-perf-tuning].

## Q5. When AQE promotes a sort-merge join to broadcast, does it re-materialize the build side, or does it reuse the shuffle files already written?

The corpus indicates AQE reuses the already-materialized shuffle output rather than re-running the map side from scratch. The Spark SQL performance-tuning guide states the conversion happens "when the runtime statistics of any join side are smaller than the adaptive broadcast hash join threshold," and explicitly frames the benefit as avoiding re-sorting both join sides and instead reading the shuffle files locally to save network traffic, conditional on `spark.sql.adaptive.localShuffleReader.enabled` being true[^spark-sql-perf-tuning]. The same guide calls this conversion "not as efficient as planning a broadcast hash join in the first place," which is consistent with reusing existing shuffle output rather than re-materializing an equivalent-to-fresh broadcast build side[^spark-sql-perf-tuning]. The Databricks AQE post similarly describes that once the sort-merge join is converted to broadcast hash join at runtime, "we may further optimize the regular shuffle to a localized shuffle (i.e., shuffle that reads on a per mapper basis instead of a per reducer basis) to reduce the network traffic"[^databricks-aqe], again pointing at reading the existing per-mapper shuffle output locally, not recomputing it.

## Q6. Can AQE re-optimize the same query plan multiple times (e.g., after each shuffle stage), or only once?

Yes, AQE re-optimizes repeatedly, once per completed query stage, not just once. The Databricks AQE post describes the mechanism as an explicit loop: leaf stages run first; as each stage (or set of stages) finishes materializing, the framework marks it complete, folds in the new runtime statistics, reruns the optimizer/physical planner/adaptive rules, then "search[es] for and execute[s] new query stages whose child stages have all been materialized, and repeat[s] the above execute-reoptimize-execute process until the entire query is done"[^databricks-aqe]. The config doc for `spark.sql.adaptive.enabled` describes AQE as re-optimizing "the query plan in the middle of query execution, based on accurate runtime statistics" (singular phrasing, but consistent with the iterative loop described above, since each stage boundary is a fresh mid-execution point)[^spark-source-sql-conf]. The number of reoptimizations scales with the number of shuffle/broadcast materialization boundaries in the plan, not a single fixed pass.

## Q7. Does disabling AQE affect query plan caching (spark.sql.cache.serializer)?

The corpus contains no evidence about `spark.sql.cache.serializer` specifically, so that part is **[UNRESOURCED]**; answering it properly would need the Spark config reference entry for that setting, which wasn't retrieved for this question.

What the corpus does support is a structural reason AQE and DataFrame caching are largely orthogonal: `.cache()`/`.persist()` work by wrapping the query's *analyzed* logical plan in an `InMemoryRelation` node, and this wrapping "happens after the analyzer phase, but before optimization. In other words, the cache is tied to the analyzed logical plan, not the final optimized one"[^luminousmen-caching-mechanics]. Cache lookup compares the analyzed plan of the current query against the analyzed plan that was cached, and skips the cache entirely (recomputing) if they don't match exactly, even if the two queries would ultimately produce the same optimized physical plan[^luminousmen-caching-mechanics]. Since AQE operates on the physical plan at runtime (well downstream of the analyzed-plan cache key), disabling AQE would not, per this mechanism, change whether a cached DataFrame's analyzed plan matches; it changes only how the physical/execution plan for a query is chosen after that analyzed-plan lookup. Whether AQE toggling interacts with `spark.sql.cache.serializer` (which governs the columnar serializer used for cached data) is not something this corpus documents; mark that specific claim **[UNRESOURCED]**.

## Q8. Are there known cases where AQE produces a worse plan than the static optimizer? What are the failure modes?

Yes. High Performance Spark warns: "While AQE generally does better than unoptimized code, there are cases, especially when targeting Iceberg tables, where AQE does more harm than good"[^high-perf-spark]. The specific failure mode called out is AQE's partitioning-to-target-table matching: it's "generally beneficial but sometimes can cause severe performance regressions," because if you've already done deliberate work to avoid key skew via custom partitioning, AQE's attempt to match the target table's write partitioning can undo that work, especially "when there is a large amount of key skew." The workaround given for Iceberg specifically is setting the table (or write-time) property `write.distribution-mode` to `none`, at the cost of a higher risk of many small files from unsorted/unhashed writers per partition[^high-perf-spark].

A second, more general failure mode is bad input statistics feeding AQE's runtime decisions: "If your source data has wrong stats (say, compressed JSON or Kafka streams), AQE might even make things worse. And since it adjusts plans at runtime, `explain()` might show you one thing, and the Spark UI might do something else entirely"[^luminousmen-partitions]. The same source's framing is that AQE "isn't magic... It helps polish your plan; it doesn't design it for you. You still need good partitioning fundamentals"[^luminousmen-partitions]. AQE can smooth over a reasonably-partitioned plan but doesn't reliably rescue one built on bad upstream statistics or layout.

## Q9. What is spark.sql.adaptive.localShuffleReader.enabled — when does AQE use a local shuffle reader and what does it avoid?

`spark.sql.adaptive.localShuffleReader.enabled` defaults to true (since Spark 3.0.0) and, when AQE is enabled, makes Spark "try to use local shuffle reader to read the shuffle data when the shuffle partitioning is not needed, for example, after converting sort-merge join to broadcast-hash join"[^spark-sql-perf-tuning]. Once AQE has converted a sort-merge join to a broadcast hash join at runtime, the side that no longer needs to be partitioned by join key can be read straight off the shuffle files each task's own executor already has locally, rather than going through the normal reduce-side shuffle fetch that pulls blocks from remote executors over the network. The perf-tuning guide frames this explicitly as a way to "avoid sorting both join sides and read shuffle files locally to save network traffic"[^spark-sql-perf-tuning]. The Databricks AQE announcement describes the same mechanism as optimizing "the regular shuffle to a localized shuffle (i.e., shuffle that reads on a per mapper basis instead of a per reducer basis) to reduce the network traffic"[^databricks-aqe]. So what it avoids is the remote, per-reducer shuffle-block fetch across the network (replacing it with a per-mapper, local read) once the join strategy switch has made the original shuffle partitioning unnecessary.

## Q10. Does AQE interact with Dynamic Partition Pruning (DPP)? What is the order of application — DPP first, then AQE re-optimization?

Based on the corpus, DPP and AQE are separate mechanisms that operate at different points, and (at least as of the original Spark 3.0 feature write-ups retrieved here) DPP was explicitly *not* integrated into the AQE runtime-reoptimization loop. A 2020 write-up of Spark 3.0's DPP feature notes: "Even though it's not implemented yet with the Adaptive Query Execution covered some weeks ago, it's still a good opportunity to make the queries more adapted to the real data workloads"[^waitingforcode-dpp]. At that point in Spark 3.0's development, DPP ran as its own static/logical-planning-time rule (`PartitionPruning`), independent of AQE's stage-by-stage reoptimization[^waitingforcode-dpp].

Mechanically, DPP is applied during logical optimization/physical planning, before execution starts: it inserts a `DynamicPruningSubquery`/`DynamicPruningExpression` node into the plan when an equi-join is on a partition column and the pruning is judged beneficial (using distinct-count statistics or a fallback filter ratio), reusing the join's `BroadcastExchange` where possible to avoid a redundant subquery scan[^waitingforcode-dpp]. Because DPP's benefit calculation runs at planning time off static/table statistics, and AQE's re-optimization runs later, mid-execution, off completed-stage runtime statistics, the natural ordering implied by the corpus is that DPP's pruning predicate is planned first (at physical planning time), with AQE's stage-by-stage adaptive rules (coalescing, skew handling, join-strategy switching) applying afterward, during execution, on top of whatever plan DPP has already pruned[^waitingforcode-dpp][^databricks-aqe]. The exact current-version integration between DPP and AQE's reoptimization loop is not detailed further in the retrieved corpus, so treat the ordering claim as directionally supported rather than exhaustively confirmed.
