# Caching & Persistence

## Q1. Under what circumstances does caching a DataFrame improve performance vs have no effect or hurt performance?

Caching pays off when the same DataFrame is scanned or recomputed more than once downstream: repeated queries or transformations on the same base data, iterative ML training loops, or interactive exploration where a dataset is reused across multiple branches[^learning-spark-2e][^definitive-guide]. In one book benchmark, caching a 10M-row DataFrame and materializing it with `count()` cut a subsequent `count()` from 5.11s to 0.44s, a roughly 12x speedup[^learning-spark-2e].

It has no effect, or hurts, in several cases:

- **Single-use data.** If a dataset is processed only once downstream, caching adds serialization/deserialization and storage bookkeeping cost for no reuse benefit: "if you are only going to process a dataset once... caching it will only slow you down"[^definitive-guide].
- **Data too big to fit.** DataFrames too large for available memory are poor candidates[^learning-spark-2e]. Partitions cache whole or not at all (8 partitions with room for 4.5 caches only 4), so the uncached remainder is recomputed on every access, which can make the job slower than not caching[^learning-spark-2e].
- **Partial materialization.** `cache()`/`persist()` are lazy: nothing is cached until an action forces a full pass. An action like `take(1)` materializes only the one partition Catalyst needs, not the whole DataFrame, so a later full scan still recomputes most of the data[^learning-spark-2e]. Likewise, `.take(10)`, `.limit(100)`, or any filtered/partial scan caches only the blocks Spark was forced to touch; the rest stays lazily uncomputed[^luminousmen-caching-mechanics].
- **Plan mismatch.** Caching wraps the *analyzed* (pre-optimization) logical plan in an `InMemoryRelation`. A logically-equivalent but differently-written query produces a different analyzed plan, so Spark can silently skip the cache and recompute from scratch even when the final optimized plan would have been identical[^luminousmen-caching-mechanics].
- **Optimizer limitations.** Caching freezes Catalyst's optimization opportunities at the cached point. For example, it can block predicate pushdown once data is served from the in-memory cache instead of the source[^luminousmen-caching-tips].

## Q2. What is the exact difference between df.cache() and df.persist(StorageLevel.MEMORY_AND_DISK) in Spark 3.0+? Are they identical?

For a DataFrame, `cache()` is literally shorthand for `persist(StorageLevel.MEMORY_AND_DISK)`: internally it calls persist with that storage level, so Spark tries to keep the data in RAM and spills evicted blocks to disk rather than risking an immediate OOM[^luminousmen-caching-mechanics]. There is no behavioral difference between the two calls when the level passed to `persist()` is exactly `MEMORY_AND_DISK`; they are identical.

`persist()` is the general form: it lets you pick any other `StorageLevel` (in-memory vs on-disk, serialized vs deserialized, replicated or not), while `cache()` takes no arguments and always uses that one fixed level[^learning-spark-2e]. Under `MEMORY_AND_DISK`, data is stored directly as objects in memory, and only the portion that doesn't fit is serialized and written to disk[^learning-spark-2e]. Each storage level is defined by five attributes (`useDisk`, `useMemory`, `useOffHeap`, `deserialized`, and `replication`), and `MEMORY_AND_DISK` sets `useDisk=true`, `useMemory=true`, `deserialized=true`[^high-perf-spark].

## Q4. Does calling df.cache() followed by df.count() guarantee that all partitions are cached, including those on executors that aren't currently active?

`count()` forces a full pass that materializes every partition when it runs, unlike `take(1)`, which computes and caches only the one partition it needs[^learning-spark-2e]. Caching happens locally and incrementally: each executor's BlockManager stores only the blocks it computes, as it computes them, with no centralized "cache the whole dataset" step[^luminousmen-caching-mechanics].

But "all partitions cached" after a `count()` is not a durable guarantee, for two reasons in the corpus:

- **Executor loss / dynamic allocation.** If a block was computed and cached on an executor that later goes away, the cached data goes with it unless a replicated storage level (e.g., `MEMORY_AND_DISK_2`) was used[^luminousmen-caching-mechanics]. This is explicit for dynamic allocation: Spark's `localCheckpoint()`/caching layer documentation warns that caching together with dynamic allocation "is NOT safe," because dynamic allocation removes idle executors along with their cached blocks. If you need both, set `spark.dynamicAllocation.cachedExecutorIdleTimeout` high enough that executors holding cached data aren't reclaimed before reuse[^spark-source-rdd].
- **Memory pressure eviction.** Even without executor loss, cached blocks can be evicted by memory pressure from other operations after materialization[^luminousmen-caching-mechanics].

So `cache()` + `count()` guarantees a materialization pass over every partition at that moment, but not that all partitions stay cached afterward if executors are reclaimed (dynamic allocation) or blocks are evicted under memory pressure.

## Q5. What is the eviction policy for MEMORY_AND_DISK — when does Spark decide to spill a partition to disk rather than evict it?

Spark uses Least Recently Used (LRU) eviction to decide *which* cached blocks to remove when storage memory is under pressure[^high-perf-spark][^luminousmen-caching-mechanics][^spark-notes-task-memory-management]. What happens to an evicted block depends on the storage level, not on a separate "spill" decision: `MEMORY_AND_DISK` stores data as deserialized objects in memory, and the portion that doesn't fit is serialized and written to disk instead of discarded[^learning-spark-2e][^spark-rdd-programming]. The `useDisk` flag triggers this: if set, partitions that don't fit in memory are written to disk rather than evicted and later recomputed[^high-perf-spark].

Eviction is triggered by memory contention between Spark's unified Execution and Storage regions. Under the `UnifiedMemoryManager`, Execution memory has priority over Storage: if a task needs execution memory (for a shuffle, join, aggregation, or sort) and Storage occupies that space, Spark evicts cached blocks to free it[^luminousmen-memory-management]. This can happen at any time, not only when you next access the cache: "Spark doesn't wait until your next action to evict things"[^luminousmen-caching-mechanics]. Once eviction is triggered for a block, its fate depends on the level. If it is disk-backed (`MEMORY_AND_DISK` or `MEMORY_AND_DISK_SER`), the block spills to disk and is read back on next use, at the cost of disk I/O. If it is memory-only (e.g., `MEMORY_ONLY`), the block is dropped and recomputed from source when needed again[^luminousmen-caching-mechanics][^high-perf-spark].

The memory pool sizes are configuration-driven fractions, not fixed byte counts. `spark.memory.fraction` (default 0.6) sets the fraction of (heap − 300MB reserved) used for the combined Execution+Storage region, and `spark.memory.storageFraction` (default 0.5) sets the portion of that region immune to eviction. Lowering either makes spills/evictions more frequent[^spark-configuration][^luminousmen-memory-management].

## Q6. What is the CPU/memory trade-off of MEMORY_AND_DISK_SER vs MEMORY_AND_DISK? At what data size does serialization save enough memory to be worth the CPU cost?

`MEMORY_AND_DISK_SER` behaves like `MEMORY_AND_DISK` except that data kept in memory is also serialized (data on disk is always serialized under either level)[^learning-spark-2e]. Serializing what would otherwise be full JVM objects "can save substantial space at the cost of some extra CPU time"[^spark-configuration]. Serialized byte streams use less memory than deserialized Java objects, which carry structural overhead, but reading them back requires deserialization, which costs more CPU than reading deserialized objects directly[^high-perf-spark].

The corpus gives no concrete data-size threshold or rule of thumb for when serialization's memory savings outweigh its CPU cost. That would need a benchmarking source with measured break-even points, which isn't in this reference set. This claim is [UNRESOURCED].

## Q7. Does checkpointing always truncate the lineage graph? What happens if the checkpoint directory is unavailable at job runtime?

Unlike persisting, checkpointing forgets the RDD's lineage: it writes the RDD's partitions to an external, reliable storage system (HDFS, S3) and drops the dependency chain used to recompute it[^high-perf-spark][^luminousmen-caching-tips]. It doesn't happen the moment `.checkpoint()` is called, though. Calling `.checkpoint()` only marks the RDD; the truncation happens in `doCheckpoint()`, which runs after a job using that RDD completes (so the RDD is already materialized) and which clears the RDD's dependencies and forgets its old parents[^spark-source-rdd]. `localCheckpoint()` also truncates lineage using Spark's caching layer, but trades fault tolerance for speed: the checkpointed data lives in ephemeral local executor storage rather than a reliable filesystem, so an executor failure during computation can make that data permanently unrecoverable, causing job failure rather than recomputation[^spark-source-rdd]. It also interacts badly with dynamic allocation, since executors (and their locally checkpointed blocks) can be reclaimed[^spark-source-rdd].

On directory unavailability: if no checkpoint directory has ever been set via `SparkContext.setCheckpointDir`, calling `.checkpoint()` on an RDD throws immediately (`checkpointDirectoryHasNotBeenSetInSparkContextError`) rather than silently doing nothing[^spark-source-rdd]. The corpus doesn't cover the separate case of a directory that *was* configured but becomes unreachable at write time (e.g., an HDFS outage mid-job). That runtime-failure behavior is [UNRESOURCED] here.

## Q8. Is there a limit on how many DataFrames can be cached simultaneously? What is the actual eviction trigger — absolute memory bytes or fraction?

There is no hard limit on how many DataFrames (or tables) you can cache; the constraint is aggregate storage memory, not a count of objects. Partitions stop being cacheable once available memory runs out, and caching is all-or-nothing per partition. A DataFrame can be "fractionally cached" across its partitions, but individual partitions can't be split: with room for only 4.5 of 8 partitions, exactly 4 get cached and the rest are recomputed on access[^learning-spark-2e].

The eviction trigger is fraction-based configuration translated into a live byte budget, not a fixed absolute byte constant. The BlockManager's total storage budget is carved out of the JVM heap via `spark.memory.fraction` (default 0.6, applied to heap minus a 300MB reserved region) and then split between execution and caching via `spark.memory.storageFraction` (default 0.5)[^luminousmen-caching-mechanics][^luminousmen-memory-management]. Internally Spark tracks a threshold (`onHeapStorageRegionSize`) for maximum storage usage, defaulting to the full storage region, and shrinks it whenever Execution needs memory, pushing Storage out and triggering LRU eviction[^luminousmen-memory-management]. So: no cap on the number of cached DataFrames, but a shared, dynamically-adjusted memory-fraction budget that evicts the least-recently-used blocks once exceeded.
