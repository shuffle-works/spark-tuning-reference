# Spark Config Quick-Reference

## Q1. What is the exact default of spark.sql.shuffle.partitions in Spark 3.0+ with AQE enabled — is the effective default different when coalescing is on?

The config default itself does not change: `spark.sql.shuffle.partitions` is 200, unchanged since version 1.1.0, and AQE does not override that number[^spark-sql-perf-tuning][^definitive-guide][^learning-spark-2e].

What AQE changes is the *effective* number of shuffle partitions used at runtime. `spark.sql.adaptive.enabled` defaults to true[^spark-configuration], and when it is on together with `spark.sql.adaptive.coalescePartitions.enabled` (also default true, since 3.0.0), Spark merges contiguous small post-shuffle partitions instead of running one task per configured partition[^spark-sql-perf-tuning]. The initial partition count going into that coalescing step is set by `spark.sql.adaptive.coalescePartitions.initialPartitionNum`; if unset, it equals `spark.sql.shuffle.partitions` (still 200)[^spark-sql-perf-tuning].

The coalescing target isn't simply "64MB" out of the box. `spark.sql.adaptive.coalescePartitions.parallelismFirst` defaults to true (since 3.2.0), and when true Spark *ignores* the target size set by `spark.sql.adaptive.advisoryPartitionSizeInBytes` (default 64MB) and computes an adaptive target from the cluster's default parallelism, respecting only the floor set by `spark.sql.adaptive.coalescePartitions.minPartitionSize` (default 1MB)[^spark-sql-perf-tuning][^spark-source-sql-conf]. Spark's docs recommend setting `parallelismFirst=false` on busy clusters to get stricter, size-based coalescing[^spark-sql-perf-tuning].

So with AQE and coalescing on (the 3.0+ default), 200 is just the starting point for the shuffle stage; the actual number of reduce tasks is reduced based on measured data volume, as databricks' AQE writeup shows[^databricks-aqe]. This is also why Learning Spark notes the static 200 default is "too high for smaller or streaming workloads"[^learning-spark-2e].

## Q2. What is the valid range for spark.memory.fraction? Can it be set to 0.9 safely, or are there documented failure modes above a certain threshold?

`spark.memory.fraction` sizes the unified execution/storage region (M) as a fraction of (JVM heap space − 300 MiB), default 0.6[^spark-tuning-guide]. The retrieved docs don't state a hard numeric validity range (e.g., an enforced 0–1 bound) for this config; the tuning guide treats it as a sizing knob to tune so that M "fits comfortably within the JVM's old or tenured generation"[^spark-tuning-guide].

No source in the corpus ties a failure threshold to a value like 0.9. What is documented is why high values are risky: the complement, `1 − spark.memory.fraction`, is "User Memory" (heap left over for UDFs, Python/Arrow glue, and native library buffers), and Spark doesn't track or manage this region at all. Starve it (which is what raising `spark.memory.fraction` toward 0.9 does, shrinking user memory to roughly 10% of usable heap) and the documented consequence is "GC pressure or random OOMs. Spark won't even warn you, it just dies."[^luminousmen-memory-management] So 0.9 is not documented as safe or unsafe by name ([NEEDS-REVIEW] for an authoritative numeric ceiling), but the corpus does document the failure mode (untracked user-memory starvation) that pushing the fraction that high would trigger.

## Q3. What is the interaction between spark.memory.fraction and spark.memory.storageFraction — are they independent, or does one constrains the other?

They are not independent: `spark.memory.storageFraction` is a fraction *of* M, and M is the region sized by `spark.memory.fraction`[^spark-tuning-guide]. So `storageFraction` works inside the pool that `memory.fraction` carves out of the heap, not as a separately-configured amount.

Within that shared region, Spark's UnifiedMemoryManager lets execution and storage borrow from each other: execution has priority and can evict storage down to the threshold R (governed by `storageFraction`), while storage cannot evict execution[^spark-notes-task-memory-management][^spark-tuning-guide]. With the defaults (`memory.fraction=0.6`, `storageFraction=0.5`), execution memory works out to usable-heap × 0.6 × (1 − 0.5) = 30% of usable heap, and storage memory to usable-heap × 0.6 × 0.5 = 30%[^luminousmen-memory-management]. Raising `memory.fraction` scales both execution and storage at once; `storageFraction` only re-splits the already-scaled pool between the two, it doesn't add memory from outside M[^luminousmen-memory-management].

## Q4. Does spark.sql.execution.arrow.pyspark.enabled = true have any correctness risks (e.g., type mismatches between Arrow and Spark types)?

`spark.sql.execution.arrow.pyspark.enabled` is disabled by default and controls Arrow use for `DataFrame.toPandas()` and `SparkSession.createDataFrame()` from a Pandas DataFrame/NumPy array[^pyspark-pandas-udfs]. The documented limitation is a type-coverage gap, not silent data corruption: `ArrayType` of `TimestampType` is called out as unsupported[^spark-configuration][^spark-source-sql-conf], and more generally "not all Spark data types are currently supported and an error can be raised if a column has an unsupported type"[^pyspark-pandas-udfs].

The safety net is `spark.sql.execution.arrow.pyspark.fallback.enabled`, which defaults to the value of the deprecated `arrow.fallback.enabled` (true) and automatically falls "back to non-optimized implementations if an error occurs" before the actual computation. So the failure mode is an exception plus automatic fallback, not a silently-wrong result[^pyspark-pandas-udfs][^spark-source-sql-conf][^spark-configuration]. Spark's guide states it plainly: "Using the above optimizations with Arrow will produce the same results as when Arrow is not enabled"[^pyspark-pandas-udfs].

Separately, and not specific to this Arrow config, PySpark's type system has its own coercion hazards: numeric values passed for `ByteType`/`ShortType`/`IntegerType` must fall within fixed ranges or they'll be rejected or converted unexpectedly at runtime. That risk is independent of whether Arrow conversion is enabled[^definitive-guide].

## Q5. What are the valid spark.dynamicAllocation.shuffleTracking.* configs and their defaults in Spark 3.x?

Two configs exist under this namespace, both introduced in 3.0.0:

- `spark.dynamicAllocation.shuffleTracking.enabled`: default `true`. Tracks shuffle files per executor so dynamic allocation works without an external shuffle service; Spark keeps alive executors holding shuffle data needed by active jobs[^spark-configuration].
- `spark.dynamicAllocation.shuffleTracking.timeout`: default `infinity`. When shuffle tracking is on, this is the timeout for executors holding shuffle data. The default waits for the shuffle data to be garbage collected before releasing the executor; if GC isn't cleaning up shuffles fast enough, set this to force those executors to time out anyway[^spark-configuration].

## Q6. What is the default and valid range for spark.sql.adaptive.advisoryPartitionSizeInBytes?

Default is 64MB, since version 3.0.0[^spark-sql-perf-tuning][^spark-configuration]. In the Spark SQL config source it's a `fallbackConf` pointing at the deprecated `spark.sql.adaptive.shuffle.targetPostShuffleInputSize`, version-tagged 3.0.0[^spark-source-sql-conf]; being a `bytesConf`, it accepts byte-size strings (e.g. `64MB`, `128m`)[^spark-configuration]. The retrieved source definition shows no explicit upper/lower bound (`checkValue`) beyond a positive byte size. [NEEDS-REVIEW] for a hard documented range beyond "must be a valid byte-size string."

## Q7. What is the difference between -XX:+UseG1GC and -XX:+UseZGC in terms of throughput vs pause latency trade-offs — for what Spark workload profile does ZGC win?

Since Spark 4.0.0, Spark uses JDK 17 by default, which makes G1GC the default collector; the guide notes that with large executor heaps you may also need to raise `-XX:G1HeapRegionSize`[^spark-tuning-guide]. G1 was designed as a replacement for CMS aiming at both high throughput and low latency, partitioning the heap into equal-sized regions and copying only live objects out of collected regions rather than compacting the whole heap[^databricks-memory]. Even so, a documented 88GB-heap Spark benchmark still hit "unacceptable full GC" with one job pausing nearly 100 seconds under default G1 settings; only after tuning `InitiatingHeapOccupancyPercent`, `ConcGCThreads`, and RSet-update parameters did G1 beat Parallel/CMS GC on throughput and latency[^databricks-memory].

ZGC, per the OpenJDK project page, is "a scalable low latency garbage collector" that "performs all expensive work concurrently, without stopping the execution of application threads for more than a millisecond," with pause times independent of heap size that scale from a few hundred megabytes up to 16TB[^jdk-zgc].

So the trade-off across these sources: G1 aims to balance both but keeps stop-the-world evacuation/full-GC pauses that can spike under heavy old-generation pressure on large heaps, as the ~100-second pause shows[^databricks-memory]; ZGC trades some CPU/throughput overhead for a sub-millisecond pause bound regardless of heap size[^jdk-zgc]. [NEEDS-REVIEW]: the corpus has no source that directly states "for Spark workload profile X, use ZGC over G1." Combining the two facts, ZGC's guarantee would matter most on very-large-heap, latency-sensitive workloads (e.g., structured streaming with tight micro-batch SLAs) where G1 full-GC pauses like the one above hurt most, but that pairing is inference from the two facts, not a claim either source makes.

## Q8. What is the default and behavior of spark.sql.adaptive.coalescePartitions.minPartitionSize (introduced Spark 3.2+)? How does it interact with advisoryPartitionSizeInBytes?

`spark.sql.adaptive.coalescePartitions.minPartitionSize` defaults to 1MB, introduced in 3.2.0, and is validated in the Spark source as a `bytesConf` with `checkValue(_ > 0, "minPartitionSize must be positive")`[^spark-source-sql-conf]. Its documented purpose: "The minimum size of shuffle partitions after coalescing. This is useful when the target size is ignored during partition coalescing, which is the default case"[^spark-sql-perf-tuning].

That "default case" is `spark.sql.adaptive.coalescePartitions.parallelismFirst=true` (default since 3.2.0): when true, Spark ignores the `advisoryPartitionSizeInBytes` target (default 64MB) when coalescing contiguous shuffle partitions and instead computes a (usually smaller) target size from the cluster's default parallelism[^spark-configuration][^spark-sql-perf-tuning]. In that mode `minPartitionSize` is the only thing still enforced: a floor so parallelism-driven coalescing doesn't produce tiny partitions. Set `parallelismFirst` to false and coalescing goes back to targeting `advisoryPartitionSizeInBytes` directly[^spark-sql-perf-tuning][^spark-source-sql-conf]. High Performance Spark notes a related but distinct knob for minimum parallelism after coalescing, `spark.sql.adaptive.coalescePartitions.minPartitionNum`, useful when the advisory size default is a poor fit for data that is slow to compute despite being small[^high-perf-spark].

## Q9. With dynamic allocation, why is an executor's shuffle output lost when the executor is reclaimed, and how does `spark.shuffle.service.enabled` (the external shuffle service) prevent the resulting `FetchFailed` and stage recompute?

During a shuffle, an executor first writes its map output to local disk and then acts as the file server for that data, serving fetch requests from other executors that need it[^spark-job-scheduling]. Before dynamic allocation existed, this was fine: an executor's on-disk state only had to survive until the whole application exited, and could be discarded the moment the executor itself exited. With dynamic allocation, the application keeps running after an individual executor is explicitly removed, so if a later stage tries to fetch shuffle blocks from an executor that's already gone, it has to recompute that state instead[^spark-job-scheduling]. This is especially likely with stragglers, tasks that run much longer than their peers, because dynamic allocation may reclaim an idle executor before a shuffle depending on it has fully completed, forcing an unnecessary recompute of the shuffle files that executor held[^spark-job-scheduling].

The external shuffle service fixes this by decoupling the shuffle data's lifetime from the executor's lifetime. It's a long-running process on each cluster node, independent of any particular Spark application's executors. When `spark.shuffle.service.enabled` is true, executors fetch shuffle blocks from this service rather than from each other. Shuffle output written by an executor can then continue being served after that executor is reclaimed, avoiding the `FetchFailed` error and the stage recompute it would otherwise trigger[^spark-job-scheduling][^spark-configuration]. The Spark configuration reference describes this directly: the service "preserves the shuffle files written by executors e.g. so that executors can be safely removed, or so that shuffle fetches can continue in the event of executor failure," and the service itself must be set up on the cluster before enabling it[^spark-configuration]. Setting up dynamic allocation requires enabling this external shuffle service on every worker node in addition to `spark.dynamicAllocation.enabled`[^definitive-guide].

As of Spark 3.0, `spark.dynamicAllocation.enabled` can alternatively rely on `spark.dynamicAllocation.shuffleTracking.enabled` (shuffle file tracking) instead of the external shuffle service to allow safe executor removal, though the underlying problem (shuffle output going unreachable when an executor is reclaimed) is the same one the external shuffle service was originally built to solve[^spark-configuration].

## Q10. How do `spark.dynamicAllocation.minExecutors` and `spark.dynamicAllocation.maxExecutors` behave when min is greater than max (inverted), and when maxExecutors is left unset (unbounded)?

By default, `spark.dynamicAllocation.minExecutors` is `0` and `spark.dynamicAllocation.maxExecutors` is `infinity`[^spark-configuration]. So if `maxExecutors` is left unset, dynamic allocation is effectively unbounded on the high end, limited in practice only by cluster capacity or scheduler quotas outside Spark itself. `spark.dynamicAllocation.initialExecutors` defaults to whatever `minExecutors` is set to, though if `--num-executors` (or `spark.executor.instances`) is set to a larger value, that larger value is used as the initial executor count instead[^spark-configuration]. The `executorAllocationRatio` setting also confirms that whatever target executor count dynamic allocation computes to maximize parallelism, that target can still be overridden (clamped) by the `minExecutors` and `maxExecutors` settings[^spark-configuration]. Both bounds act as hard floor/ceiling clamps around the ratio-driven target.

None of the retrieved chunks describe what happens when `minExecutors` is explicitly set higher than `maxExecutors` (an inverted configuration). That behavior (whether Spark throws a validation error at startup, silently clamps one value, or produces undefined allocation behavior) is `[UNRESOURCED]`; confirming it would require checking Spark's `SparkContext`/`ExecutorAllocationManager` source validation logic directly rather than the configuration reference page.

## Q11. How does `spark.serializer` set to `org.apache.spark.serializer.KryoSerializer` compare with the default `JavaSerializer` on performance and compactness, and why is Kryo not the default?

The default value of `spark.serializer` is `org.apache.spark.serializer.JavaSerializer`, described in the configuration reference as working with any `Serializable` Java object but "quite slow," which is why Spark recommends switching to `KryoSerializer` "when speed is necessary"[^spark-configuration]. The tuning guide is more specific: Kryo is "significantly faster and more compact than Java serialization (often as much as 10x)," though it doesn't support all `Serializable` types and requires registering the classes you'll use in advance for best performance[^spark-tuning-guide]. That registration requirement is explicitly called out as the reason Kryo isn't the default: "The only reason Kryo is not the default is because of the custom registration requirement, but we recommend trying it in any network-intensive application"[^spark-tuning-guide]. Since Spark 2.0.0, Spark internally uses the Kryo serializer regardless of this setting when shuffling RDDs of simple types, arrays of simple types, or strings, and it automatically includes Kryo serializers for common Scala classes via the Twitter chill library's `AllScalaRegistrar`[^spark-tuning-guide].

A practitioner summary puts the same tradeoff in blunter terms: Java serialization is "2-10x slower and larger on the wire," and the cost is paid on every shuffle, so Kryo is "still worth it" in production. The caveat: unregistered classes will silently fall back to Java serialization unless registered via `spark.kryo.classesToRegister` or `spark.kryo.registrator`[^luminousmen-optimization-checklist]. More generally, when RDDs are persisted in serialized form, Kryo serialization can be even more space-efficient than the standard Java serialization library used for moving objects across the network[^high-perf-spark].

## Q12. What does `spark.executor.memoryOverhead` cover (off-heap / non-JVM memory), what is its default floor, and how does setting it too low cause the container to be OOM-killed by the resource manager?

`spark.executor.memoryOverhead` covers everything an executor needs outside the JVM heap specified by `spark.executor.memory`: thread stacks, JIT buffers, metaspace, JNI, native libraries, and, if `spark.executor.pyspark.memory` isn't set separately, the memory used by PySpark's per-task Python worker processes as well[^luminousmen-memory-management]. If left unset, Spark defaults this to the greater of 10% of executor memory or 384 MB[^luminousmen-memory-management]. In the configuration reference's terms, this floor is formalized as `spark.executor.minMemoryOverhead` (default `384m`, since Spark 4.0), which is the minimum non-heap allocation applied when `spark.executor.memoryOverhead` isn't set directly, while `spark.executor.memoryOverheadFactor` (since 3.3.0) controls the percentage, defaulting to 0.10, or 0.40 for non-JVM jobs on Kubernetes, since such jobs need more non-JVM heap space and commonly fail with "Memory Overhead Exceeded" errors otherwise[^spark-configuration].

The container-killing failure mode arises because the resource manager (YARN's NodeManager, or the Kubernetes kubelet) allocates a container/pod sized to the sum of executor memory, memory overhead, off-heap size, and PySpark memory: the configuration reference states the maximum container memory for a running executor "is determined by the sum of `spark.executor.memoryOverhead`, `spark.executor.memory`, `spark.memory.offHeap.size` and `spark.executor.pyspark.memory`"[^spark-configuration]. If a workload turns on off-heap memory (`spark.memory.offHeap.size`) or relies on PySpark worker processes without correspondingly increasing `memoryOverhead`, that extra memory isn't counted in the container's requested size. It's still consumed at the process level, though: the resource manager tracks actual RSS usage, not just JVM heap. Once real usage exceeds the allocated container size, the executor gets killed by YARN or OOMKilled by the Kubernetes kubelet, with no Spark-level error, just an abrupt process death[^luminousmen-memory-management].
