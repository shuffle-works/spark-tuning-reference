# Spark Execution Model

## What are the precise responsibilities of the Driver process? What data structures live only on the Driver?

The Driver is the process "in the driver seat" of a Spark application: it controls execution and maintains all state of the cluster, including the state and tasks of the executors, and it must interface with the cluster manager to get physical resources and launch executors[^definitive-guide]. It is a single JVM process, running on the submission machine in client mode or on a dedicated cluster node in cluster mode. If it dies, the application dies with it[^luminousmen-anatomy].

As code executes, the Driver incrementally builds the logical DAG of RDD/DataFrame transformations; because Spark is lazy, no computation happens until an action is called. At that point the Driver converts the logical DAG into a physical plan, cuts it into stages at wide-dependency (shuffle) boundaries, breaks each stage into one task per partition, and then acts as scheduler: it talks to the cluster resource manager to request executors, hands out tasks, tracks their progress, and resubmits tasks whose executor died[^luminousmen-anatomy].

Internally the Driver hosts several components that exist only there:
- The **DAGScheduler**, which reads RDD lineage, decides stage boundaries at wide dependencies, emits per-partition TaskSets, tracks lineage for recomputation of lost partitions, and reacts dynamically to stage completions (it does not pre-schedule the whole DAG up front). It also declares a job failed if a stage cannot make progress[^luminousmen-anatomy].
- The **BlockManagerMaster**, which is the Driver-side counterpart to each executor's own BlockManager: it keeps the global map of block locations (RDD partitions, shuffle files, broadcast variables) across the whole cluster, so a task's local BlockManager can be told where to fetch a remote block from[^luminousmen-anatomy].
- The **SparkContext** (wrapped today by SparkSession), the entry point that lets the Driver talk to the cluster manager, request executors, create RDDs, and manage shared variables; it is instantiated once per application and lives for the application's lifetime[^luminousmen-anatomy].

The executors only run the tasks assigned to them and report back success/failure and results; they hold no cluster-wide state[^definitive-guide]. Driver-side networking is also distinct at the configuration level: `spark.driver.host`/`spark.driver.port` and `spark.driver.blockManager.port` are Driver-specific listening endpoints separate from the equivalent executor settings[^spark-configuration].

## How does a Job decompose into Stages and Tasks? What exactly is the rule for stage boundary creation?

A Spark job corresponds to one action; each job breaks down into a series of stages, and the number of stages depends on how many shuffle operations need to take place[^definitive-guide]. Each stage is a group of tasks that can be executed together to compute the same operation across machines, and a stage can be thought of as work that one executor can do without communicating with other executors or the driver. A new stage begins whenever data must move across the network, i.e. at a shuffle[^high-perf-spark]. Wide transformations (e.g. `groupByKey`, `join`, `sortByKey`) create `ShuffleDependency` objects, and it is these `ShuffleDependency`s that mark the stage boundary; several narrow transformations can be grouped into the same stage[^high-perf-spark].

Within a stage, the number of tasks equals the number of partitions in that stage's output RDD: one task per partition, each running the same code on a different slice of data[^high-perf-spark]. A worked example in the Definitive Guide shows a job that reads a range (8 partitions → stage with 8 tasks), repartitions to 6 and 5 partitions (stages with 6 and 5 tasks), and then joins, which shuffles into the default 200 shuffle partitions, giving a 200-task stage[^definitive-guide].

## Is a shuffle the only trigger for a stage boundary, or can other operations (e.g., sortBy on an RDD, checkpointing) also split stages?

The rule is still "shuffle dependency creates the boundary", but several different operations can produce that shuffle dependency, so it isn't just an explicit `.repartition()` or `.groupBy()`. Wide transformations that cause this redistribution include `sort` and `groupByKey`, among others, so `sortByKey`/`sortBy` on an RDD is itself wide, not just `groupByKey`-style aggregations[^high-perf-spark]. The example RDD program `filter → map → groupByKey → map → sortByKey → count` produces three stages, bounded by the `groupByKey` and `sortByKey` operations[^high-perf-spark]. The original Spark paper likewise defines stage boundaries generically as "the shuffle operations required for wide dependencies, or any already-computed partitions that can short-circuit the computation of a parent RDD"[^rdd-nsdi12]. A wide dependency of any kind, not a specific API call, is what matters.

A related practical trigger: reusing shuffle files. Because Spark always writes shuffle output to stable storage regardless of a `persist`/`checkpoint` call, if the driver reuses an RDD that has already been shuffled, Spark can skip recomputing everything up to that shuffle and read the shuffle files directly. The Spark UI shows this as a "skipped stage"[^high-perf-spark]. This doesn't add a boundary, it lets Spark avoid re-running stages that already produced their shuffle output.

## What is the difference between spark.default.parallelism and spark.sql.shuffle.partitions? When does each take effect — is there a priority order?

`spark.default.parallelism` is the RDD-API-level default: for distributed shuffle operations like `reduceByKey` and `join`, it defaults to the largest number of partitions in the parent RDD; for operations with no parent RDD (like `parallelize`), the default depends on the cluster manager. It governs the default number of partitions in RDDs returned by transformations such as `join`, `reduceByKey`, and `parallelize` when the user hasn't set a partition count explicitly[^spark-configuration].

`spark.sql.shuffle.partitions`, by contrast, is the Spark SQL/DataFrame-level knob: it configures the number of partitions Spark uses when shuffling data for joins or aggregations in the SQL/DataFrame engine, and it defaults to 200 regardless of data size[^spark-sql-perf-tuning]. This value applies whenever a DataFrame/SQL operation triggers a shuffle (join, groupBy, distinct, orderBy, etc.)[^luminousmen-partitions].

In practice they don't compete for priority because they scope to different APIs: `spark.default.parallelism` affects the legacy RDD API's shuffle/parallelize operations, while `spark.sql.shuffle.partitions` affects DataFrame/Dataset/SQL shuffles. There is no fixed formula for the right number of shuffle partitions; it depends on data set size, number of cores, and available executor memory, and the default of 200 is called out as too high for smaller or streaming workloads, where it's better reduced toward the number of executor cores or less[^learning-spark-2e]. Since Spark 3.0, Adaptive Query Execution (AQE) can override the static `spark.sql.shuffle.partitions` value after the fact. It can coalesce many small post-shuffle partitions and split skewed ones at runtime, but only after the first shuffle has already happened; it does not affect the initial input partitioning[^luminousmen-partitions].

## What is the DAG Scheduler exact responsibility vs the Task Scheduler? Can they be run on different threads?

The DAGScheduler is Spark's high-level scheduling layer: it takes RDD dependencies and builds a DAG of stages for each job, determines locations to run each task, and passes that information to the TaskScheduler[^high-perf-spark]. It looks at RDD lineage, identifies wide dependencies, decides where shuffles (and thus stage boundaries) occur, breaks each stage into a TaskSet (one task per partition), and hands that TaskSet to the TaskScheduler. It also tracks lineage for recomputing lost partitions on failure, and it is the component that ultimately declares a job to have failed if a stage cannot make progress after repeated retries. The DAGScheduler does not pre-schedule the whole DAG at once; it reacts to stage completions and unlocks child stages dynamically[^luminousmen-anatomy].

The TaskScheduler takes over once it receives a TaskSet: it no longer thinks in terms of RDDs, lineage, or shuffles; it thinks in terms of machines and slots. Its job is to work with the SchedulerBackend to request executors and figure out where tasks can run, assign tasks to executors while respecting data-locality preferences, and retry failed tasks (including resubmitting a task elsewhere if its executor died)[^luminousmen-anatomy]. The TaskScheduler itself does not launch tasks directly; it hands them to the SchedulerBackend, which is the layer that actually talks to the cluster manager to request/launch/kill executors[^luminousmen-anatomy].

On threading: Spark's scheduler is fully thread-safe and supports running multiple jobs concurrently if they are submitted from separate driver threads, which is common when an application serves multiple concurrent requests over the network[^spark-job-scheduling]. By default Spark schedules jobs FIFO; it also offers a fair scheduler that assigns tasks to concurrent jobs round-robin so each job gets a more even share of cluster resources[^high-perf-spark]. Job pools/weights for fine-grained sharing are configured via `spark.scheduler.mode=FAIR` and the `spark.scheduler.pool` local property set on the submitting thread[^definitive-guide]. The DAGScheduler/TaskScheduler/SchedulerBackend chain itself is exactly the mechanism that turns those concurrently-submitted jobs' logical plans into physical, thread-scheduled work.

## What does "narrow" vs "wide" transformation mean formally? Is mapPartitions always narrow? Is coalesce narrow or wide?

Conceptually, narrow transformations are those where each partition in the child RDD has simple, finite dependencies on partitions in the parent RDD, determinable at design time regardless of the values of the records. Narrow dependencies allow pipelined, one-node execution, while wide dependencies require data from all parent partitions to be shuffled across nodes[^rdd-nsdi12]. But the *formal* definition, from the original 2012 Spark paper, is stated from the parent's side rather than the child's: a transformation has a narrow dependency if "each partition of the parent RDD is used by at most one partition of the child RDD," and a wide dependency if "multiple child partitions may depend on [a given partition in the parent]"[^high-perf-spark]. This parent-centric framing is more precise because Spark's DAG scheduler builds the execution plan backward from the action to the input RDD, and it correctly rules out the case of one parent partition feeding multiple children under "narrow"[^high-perf-spark].

`mapPartitions` is a narrow transformation: each child partition depends on exactly one parent partition, so it fits the design-time-determinable, one-parent-per-child pattern alongside `map` and `filter`[^high-perf-spark].

`coalesce` is narrow, even though it changes the number of partitions and even though a child partition can depend on *multiple* parent partitions. The formal rule only requires that each parent partition be used by at most one child partition (never split or replicated across children), and which parent partitions merge into which child partition is fixed at design time, independent of the data's values[^high-perf-spark]. This holds specifically when `coalesce` reduces the number of partitions; when it increases the partition count it behaves like `repartition` (a shuffle)[^high-perf-spark]. Practically, `coalesce`-when-reducing avoids a full shuffle by merely combining existing partitions, but it forces all upstream partitions in that stage to run at the coalesced parallelism level, which can be undesirable; using `repartition` instead trades that limitation for an explicit shuffle[^high-perf-spark].

## When does Spark use pipelining within a stage? Are all narrow transformations pipelined, or are there exceptions?

Pipelining is one of the key optimizations that lets Spark act as an "in-memory computation tool": Spark performs as many steps as possible in one pass before writing data to memory or disk. Any sequence of operations that feed data directly into each other, without needing to move data across nodes, is collapsed into a single stage of tasks that execute all the operations together. For example, `map → filter → map` becomes one stage whose tasks read each record and pass it through all three operations in sequence, rather than materializing intermediate results after each step[^definitive-guide]. The same pipelining happens for a DataFrame/SQL computation doing `select → filter → select`, and it is fully transparent to the application, visible only via the Spark UI/logs, where multiple operations show up collapsed into a single stage[^definitive-guide].

Narrow dependencies are exactly what make this possible: because they don't require data to move across partitions or communication with the driver, an arbitrary number of narrow transformations can be applied to a partition using only the one set of instructions dispatched from the driver, all within the same stage[^high-perf-spark]. The original paper phrases the mechanism at the scheduler level: to run an action, Spark builds stages at wide dependencies and pipelines narrow transformations inside each stage[^rdd-nsdi12].

Wide dependencies are the exception that breaks pipelining: once a shuffle is required, downstream computation cannot proceed until the shuffle completes, because the records landing on each partition may change as a result of the shuffle, so narrow transformations following a wide one belong to a new stage and cannot be pipelined across that boundary[^high-perf-spark]. Whether pipelining happens can also depend on partitioning state Spark already knows about: because Spark tracks how an RDD is already partitioned, the same operation can land in different stage boundaries depending on whether the input RDD already has a known partitioner. No shuffle (and hence no new stage) is needed if one is already in place, so the following narrow transformations stay pipelined into the existing stage[^high-perf-spark]. This is a separate mechanism from checkpointing, which instead breaks RDD lineage and writes data to disk so later transformations start from a fresh, trimmed plan rather than being pipelined against the original computation[^luminousmen-caching-tips].
