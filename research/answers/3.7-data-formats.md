# Data Formats

## Q1. What are the main structural differences between Parquet and ORC, and when should each be preferred?

ORC is a self-describing, type-aware columnar file format designed for Hadoop workloads[^definitive-guide-1]. Parquet is likewise a columnar format, differing from ORC mainly by optimization target rather than by fundamental structure[^definitive-guide-1]; its internal row-group and footer layout, and its row-group-size guidance, are documented under Q2 and Q3, whose queries surface the Parquet format-spec chunks that state them.

*Spark: The Definitive Guide* puts the practical difference plainly: "for the most part, they're quite similar; the fundamental difference is that Parquet is further optimized for use with Spark, whereas ORC is further optimized for Hive"[^definitive-guide-1]. ORC "has no options for reading in data because Spark understands the file format quite well"[^definitive-guide-1]: Spark treats it as a native source rather than one it has extra configuration knobs for.

On the read-path side, the chunks retrieved for this question do not document Spark's ORC/Parquet vectorized-reader configuration (e.g., `spark.sql.orc.impl`, `spark.sql.orc.enableVectorizedReader`, or the Hive-SerDe-specific `spark.sql.hive.convertMetastoreOrc` gating). [UNRESOURCED within Q1's own retrieval; this vectorized-reader behavior exists elsewhere in the corpus but not among the sources Q1's query surfaces].

Guidance from the retrieved sources: default to Parquet, the format Spark's own optimizations target[^definitive-guide-1], and use ORC when the data also has to serve Hive consumers or existing Hive ORC tables, where ORC is the better-optimized target[^definitive-guide-1].

## Q2. Does Snappy compression support block-level splitting in Parquet? If not, how does Parquet achieve parallelism despite non-splittable Snappy?

No. Snappy itself has no split points. Google's format description says the Snappy stream format has "no entropy encoder backend nor framing layer -- the latter is assumed to be handled by other parts of the system"[^snappy-format]. Splittability is not a property of the raw Snappy byte stream; any container using Snappy has to provide its own way to locate independent, separately-decodable chunks.

Parquet provides exactly that mechanism at the container level, independent of which codec compresses the bytes. A Parquet file's `FileMetaData` footer records the offset and size of every row group and column chunk, and "readers are expected to first read the file metadata to find all the column chunks they are interested in. The column chunks should then be read sequentially"[^parquet-format-spec-2]. Because compression and encoding are applied within each column chunk/page rather than as one continuous stream across the whole file, a reader (or a Spark task) can seek directly to a row group's recorded offset via the footer and decode from there; it does not need to decompress the file from byte zero the way a single monolithic `.snappy` stream would require. This is why Parquet files compressed with Snappy remain splittable across row groups even though the Snappy format itself has no internal split points[^snappy-format][^parquet-format-spec-2].

## Q3. What is the difference between Parquet row group size and HDFS/S3 block size, and how do they interact for task parallelism?

Row group size is a Parquet-internal unit: the amount of data (across all columns) grouped together with its own set of column chunks. The spec recommends large row groups (512MB–1GB) because "larger row groups allow for larger column chunks which makes it possible to do larger sequential IO," at the cost of more write-path buffering[^parquet-format-spec-3]. Block size is a property of the underlying filesystem (HDFS `dfs.blocksize`, or the analogous object-size chunking on S3). The Parquet spec explicitly calls out the interaction: "since an entire row group might need to be read, we want it to completely fit on one HDFS block. Therefore, HDFS block sizes should also be set to be larger," recommending as an optimized setup "1GB row groups, 1GB HDFS block size, 1 HDFS block per HDFS file"[^parquet-format-spec-3].

For task parallelism, Spark's file-based readers inspect the file's footer/row groups and slice the file accordingly: "for structured formats like Parquet, ORC, or Avro, Spark actually reads the metadata (footers, row groups, that kind of thing) and tries to slice the file in a way that makes sense. Often you'll see one partition per row group, though Spark may merge or split depending on file sizes and configs"[^luminousmen-partitions]. A concrete example given: a single 30GB Parquet file with 300 row groups is split by Spark into exactly 300 partitions[^luminousmen-partitions]. If a row group is not aligned to fit inside one block (i.e., row group size exceeds block size, or block boundaries fall mid-row-group), the row group cannot be read from a single block, undercutting the locality benefit the spec's alignment recommendation is meant to preserve[^parquet-format-spec-3]. On the Spark-configuration side, `spark.sql.files.maxPartitionBytes` (128MB by default) and the related `spark.sql.files.maxPartitionNum`/`minPartitionNum` settings govern how many split-file partitions Spark targets for file-based sources generally[^spark-sql-perf-tuning-1], while for row-group-oriented sources like Parquet the row-group boundaries are the dominant factor in how many partitions a single file yields[^luminousmen-partitions].

## Q4. What statistics does Parquet collect per row group (min/max, null count, bloom filters)? Which are used for predicate pushdown in Spark?

Parquet records column statistics (including min/max values) per column chunk within each row group, and additionally supports an optional `ColumnIndex` structure that stores page-level min/max values (with writers permitted to truncate large values to bound index size) so that "for ordered columns, this allows a reader to find matching pages by performing a binary search in min_values and max_values. For unordered columns, a reader can find matching pages by sequentially reading min_values and max_values"[^parquet-format-spec-4]. Parquet also supports optional Bloom filters per column, motivated specifically by cases where a dictionary would be too large: "when there are too many distinct values, writers sometimes choose not to add dictionaries because of the extra space they occupy. This leaves columns with large cardinalities and widely separated min and max without support for predicate pushdown," which a compact Bloom filter (no false negatives, configurable false-positive rate) resolves[^parquet-bloom-filters].

On the Spark side, these statistics feed query planning: "Statistics that Spark reads directly from the underlying data source, like the counts and min/max values in the metadata of Parquet files. These statistics are maintained by the underlying data source"[^spark-sql-perf-tuning-2]. The mechanism is gated by `spark.sql.parquet.filterPushdown` (default `true`, since Spark 1.2.0), which "enables Parquet filter push-down optimization"[^spark-configuration-1]. A related, more aggressive feature, `spark.sql.parquet.aggregatePushdown` (default `false`, since 3.3.0), pushes `MIN`, `MAX`, and `COUNT` aggregate expressions down to Parquet's footer statistics directly, throwing an exception if the required statistics are missing from any file's footer[^spark-configuration-1]. The retrieved chunks for this question do not describe Parquet's per-row-group null-count statistic specifically. ## Q5. What statistics does ORC collect (min/max, bloom filters, row index stride)? How does ORC's predicate pushdown differ from Parquet's?

ORC's `ColumnStatistics` protobuf message records, per column, the row count and, "for most of the primitive types, ... the minimum and maximum values; and for numeric types it additionally stores the sum. From Hive 1.1.0 onwards, the column statistics will also record if there are any null values within the row group by setting the `hasNull` flag. The `hasNull` flag is used by ORC's predicate pushdown to better answer 'IS NULL' queries"[^orc-spec-1]. These statistics exist at two granularities: a `RowIndexEntry` per row group (row groups default to 10,000 rows) giving stream positions plus statistics for that row group, with the index streams "placed at the front of the stripe, because in the default case of streaming they do not need to be read. They are only loaded when either predicate push down is being used or the reader seeks to a particular row"[^orc-spec-2]; and file-level `StripeStatistics`, which "enable input split elimination based on the predicate push-down evaluated per a stripe"[^orc-spec-3].

ORC also supports Bloom filters, added "from Hive 1.2.0 onwards": a `BLOOM_FILTER` stream is recorded per row group for any column named in the `orc.bloom.filter.columns` table property, and "only the row groups that satisfy min/max row index evaluation will be evaluated against the bloom filter index"[^orc-spec-2]: ORC's Bloom filter check is a second-stage filter applied only after the min/max row-index check has already passed, rather than an independent check. In Spark, ORC predicate pushdown is controlled by `spark.sql.orc.filterPushdown` (default `true`, since 1.4.0)[^spark-configuration-2].

The high-level difference, echoing Q1: "for the most part, they're quite similar; the fundamental difference is that Parquet is further optimized for use with Spark, whereas ORC is further optimized for Hive"[^definitive-guide-2]. The two-stage min/max-then-Bloom-filter evaluation order documented for ORC[^orc-spec-2] is the one concrete sequencing difference in the retrieved material; Parquet's own Bloom filters and ColumnIndex are documented as independent pruning mechanisms, without that same two-stage ordering specified in the retrieved Parquet chunks[^parquet-bloom-filters].

## Q6. At what file size does the "too many small files" problem become measurable? Is there a task count threshold where scheduling overhead dominates?

The retrieved corpus does not give a specific file-size number at which the small-file problem becomes measurable. This implies scheduling/launch overhead becomes proportionally significant only below roughly that 200ms-per-task floor, but the corpus does not state an explicit task-count threshold at which scheduling overhead dominates total runtime. ## Q7. Does mergeSchema in spark.read.parquet handle type widening (e.g., int -> long)? What happens on a type conflict it cannot resolve?

`spark.sql.parquet.mergeSchema` (default `false`, since 1.5.0) does merge schemas collected across all data files rather than picking one arbitrarily: "when true, the Parquet data source merges schemas collected from all data files, otherwise the schema is picked from the summary file or a random data file if no summary file is available"[^spark-source-sql-conf]. The retrieved documentation for this option describes only that merging behavior at a high level and a usage example (`session.read.option("mergeSchema", "true").format("parquet").load(path)`)[^high-perf-spark-1]; it does not document the specific type-promotion rules Parquet's schema merger applies (e.g., whether an `int` column in one file and a `long` column in another are silently widened to `long`), nor what error Spark raises when it encounters a genuinely unresolvable type conflict between files. [UNRESOURCED for the exact type-widening/conflict-resolution behavior; would need Spark's `ParquetSchemaConverter`/schema-merging source, or a Spark JIRA describing `mergeSchema` type-promotion semantics.]

A related but distinct schema-evolution behavior is documented for Delta Lake's own `mergeSchema` option (not plain Parquet): adding a new column via `.option("mergeSchema", "true")` on write causes existing rows, when read back, to have the new column's value treated as `NULL`[^learning-spark-2e-2]. This is column addition, not numeric type widening, and does not directly answer the int→long question, but it's the nearest documented mergeSchema conflict-handling behavior in the retrieved corpus.

## Q8. What is Zstd's compression ratio vs speed trade-off compared to Snappy for Parquet files of typical Spark workload sizes? Are there benchmark references?

Zstandard's own manual describes it as "a fast lossless compression algorithm, targeting real-time compression scenarios at zlib-level and better compression ratios," supporting regular levels 1 through 22 (levels ≥20, labeled `--ultra`, requiring more memory), plus negative levels that "extend the range of speed vs. ratio preferences": "the lower the level, the faster the speed (at the cost of compression)"[^zstd-manual]. Spark exposes this level knob directly via `spark.io.compression.zstd.level` (default `1`), documented as: "increasing the compression level will result in better compression at the expense of more CPU and memory"[^spark-configuration-3]. Spark also exposes `spark.io.compression.zstd.workers` (default `0`, since 4.0.0) to spawn parallel compression threads, and `spark.io.compression.zstd.bufferSize` (default 32k, since 2.3.0), where "lowering this size will lower the shuffle memory usage when Zstd is used, but it might increase the compression cost because of excessive JNI call overhead"[^spark-configuration-3].

Spark's own defaults already treat Zstd and Snappy differently by format: ORC's default codec is `zstd` (since 2.3.0)[^spark-configuration-3], while Parquet's default remains `snappy`[^spark-configuration-3], and at least one optimization checklist in the corpus recommends overriding to `zstd`[^luminousmen-optimization-checklist]. The retrieved corpus does not contain a quantified ratio-vs-speed benchmark comparing Zstd against Snappy specifically on Parquet files at typical Spark workload sizes (e.g., X% smaller output at Y% more CPU time). [UNRESOURCED for a concrete benchmark; would need a dedicated Zstd-vs-Snappy Parquet benchmark, such as a vendor engineering blog or an independent codec comparison study.]

## Q9. Why is Gzip generally discouraged for Spark inputs? Is it solely the non-splittability, or are there other factors (CPU cost, codec availability)?

Non-splittability is the headline factor documented in the corpus, but specifically for large *raw* compressed source files rather than for gzip as a Parquet-internal codec: "do not use large source files in zip/gzip format, they are not splittable. It is not possible to read such files in parallel with Spark. First, Spark needs to download the whole file on one executor, unpack it on just one core, and then redistribute the partitions to the cluster nodes. As you can imagine, this becomes a huge bottleneck in your distributed processing"[^luminousmen-dont-collect]. The recommended workaround for HDFS-resident files is to unpack them before loading into Spark[^luminousmen-dont-collect].

CPU cost is the second documented factor: "uncompressed files are clearly outperforming compressed files. This is because uncompressed files are I/O bound, and compressed files are CPU bound, but I/O is good enough here"[^luminousmen-dont-collect]: once I/O is not the bottleneck, paying gzip's decompression CPU cost is a net loss. The same source draws a comparison to Bzip2, which is splittable but so aggressively compressed that "you get very few partitions and therefore they can be poorly distributed," making it suitable mainly "if there are no limits on compression time and CPU load, for example for one-time packaging of large amounts of data"[^luminousmen-dont-collect].

The non-splittability concern is about gzip as the *container-level* compression of a whole file (a `.csv.gz` or `.json.gz`), not gzip used as Parquet's internal per-page/row-group codec, where Parquet's row-group structure, not the codec, provides splittability (see Q2/Q3). *Spark: The Definitive Guide*'s discussion of splittable file types notes "not all compression schemes are splittable... We recommend Parquet with gzip compression"[^definitive-guide-4]: the same source that warns about raw gzip files elsewhere in the corpus treats gzip as an acceptable choice once it's wrapped inside Parquet's row-group container. The retrieved chunks do not discuss gzip codec-availability issues (e.g., missing native codec libraries) as a separate factor. [UNRESOURCED for codec-availability specifically].

## Q10. Parquet v1 vs v2 (parquet.writer.version) — what is the practical difference for Spark readers, and is v2 safe to enable by default?

The Parquet format spec documents Data Page V2 as an explicitly forward-*incompatible* feature: "Data Page V2 headers: a reader that only understands `DataPageHeader` cannot parse `DataPageHeaderV2` pages"[^parquet-format-spec-5]. The spec also notes that the version field in a file's `FileMetadata` "has historically been used inconsistently: writers populate 1 or 2 without a consistent relationship to the features actually used"[^parquet-format-spec-5], meaning the file-level version marker itself is not a fully reliable signal of which page-header format is actually in use.

The practical consequence for Spark readers: enabling `parquet.writer.version=2` changes the on-disk page-header encoding to `DataPageHeaderV2`, which any reader (a different, older Spark version, or a non-Spark engine like Hive/Impala) that only implements the original `DataPageHeader` cannot parse[^parquet-format-spec-5]. This is consistent with the general cross-version compatibility warning given in *Spark: The Definitive Guide*: "even though there are only two options, you can still encounter problems if you're working with incompatible Parquet files. Be careful when you write out Parquet files with different versions of Spark (especially older ones) because this can cause significant headache"[^definitive-guide-5]. So v2 is not something to flip on by default purely for its own benefits (e.g., its more compact encodings) without confirming every downstream reader of that data supports `DataPageHeaderV2`: it is a forward-incompatible, not forward-compatible, format change[^parquet-format-spec-5]. The retrieved corpus does not state what Spark's own default `parquet.writer.version` value is.
