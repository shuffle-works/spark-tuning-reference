# Join Optimization

## What join strategies does Spark SQL support, and how does the optimizer choose between them?

Spark SQL's Catalyst optimizer has five concrete physical join operators to choose from: broadcast hash join, broadcast nested loop join, shuffle hash join, shuffle sort-merge join (SMJ), and shuffle-and-replicate nested loop (cartesian) join[^high-perf-spark]. Broadcast hash avoids a shuffle entirely and is used whenever one side is small enough; it supports every join type except full outer and requires an equi-join condition[^high-perf-spark]. Broadcast nested loop join is similar but drops the equi-join restriction, supporting non-equi conditions and every join type, at the cost of scanning one side repeatedly, so it's normally a last resort because it can be slow or run out of memory[^high-perf-spark]. Shuffle-and-replicate (cartesian) joins compute every partition against every other partition and are the most likely to blow up in data size[^high-perf-spark]. Unlike hand-tuned RDD joins, where you control the partitioner directly, Spark SQL's optimizer can also push down or reorder other operations automatically to make the eventual join cheaper[^high-perf-spark].

Spark's communication strategy for a join is binary: either an all-to-all shuffle join or a broadcast join that replicates the small side once and then lets every node join locally without further communication[^definitive-guide]. The primary signal the optimizer uses to pick between broadcast and a shuffle-based join is relation size relative to `spark.sql.autoBroadcastJoinThreshold`, informed by table/column statistics (inspectable via `DESCRIBE EXTENDED`) and the cost estimates shown in `EXPLAIN COST` / `.explain(mode="cost")`[^spark-sql-perf-tuning]. Since Spark 3.2, Adaptive Query Execution (AQE, on by default) re-optimizes the plan mid-execution using accurate runtime statistics rather than only the pre-execution estimates, which is why the physical join operator can change after the shuffle stage actually runs[^spark-sql-perf-tuning].

## What is the exact default for spark.sql.autoBroadcastJoinThreshold in Spark 3.x? Is it based on compressed or uncompressed table size, and where does Spark measure it (statistics, file size, or plan estimate)?

The default is `10485760` bytes, i.e. 10 MB, unchanged since it was introduced in version 1.1.0 and still the documented default for Spark 3.5[^spark-sql-perf-tuning][^spark-configuration]. Setting it to `-1` disables automatic broadcasting[^spark-sql-perf-tuning].

Spark determines whether a table qualifies by consulting table/plan size statistics rather than re-scanning the data at broadcast time: it uses catalog statistics (collected via `ANALYZE TABLE` or exposed through `DESCRIBE EXTENDED`) and the cost estimates in the optimized plan[^spark-sql-perf-tuning]. When those statistics are missing, `spark.sql.statistics.fallBackToHdfs` (default `false`) controls whether Spark falls back to the on-disk (HDFS) file size to decide if a table is small enough for a broadcast join; for partitioned tables without statistics, Spark instead uses the `spark.sql.defaultSizeInBytes` placeholder[^spark-configuration].

Whether the size compared against the threshold is the compressed on-disk size or the uncompressed in-memory size is not stated in any retrieved chunk. ## When a broadcast hint is specified but the table exceeds the threshold, does Spark obey the hint or fall back to sort-merge?

Spark obeys the hint: when a `BROADCAST` hint is attached to a relation, that relation's broadcast join (broadcast hash join, or broadcast nested loop join if there's no equi-join key) is prioritized "even if the size of table 't1' suggested by the statistics is above the configuration `spark.sql.autoBroadcastJoinThreshold`"[^spark-sql-perf-tuning]. The hint only fails to take effect when the specific strategy structurally cannot support the join type being performed. The documentation is explicit that "there is no guarantee that Spark will choose the join strategy specified in the hint since a specific strategy may not support all join types"[^spark-sql-perf-tuning]. Join hints in Spark SQL are advisory: Spark may still choose a different operator than the one hinted[^high-perf-spark]. This is distinct from disabling the threshold outright: setting `spark.sql.autoBroadcastJoinThreshold` to `-1` forces Spark to always fall back to a shuffle sort-merge join instead[^learning-spark-2e].

## What is the driver memory cost of broadcasting a table — is the full table materialized on the driver before being sent to executors?

Yes. Building a broadcast join replicates the small-side DataFrame to every worker node, but that replication is preceded by collecting the DataFrame back to the driver first. The Definitive Guide states this plainly: broadcasting something too large "can crash your driver node (because that collect is expensive)"[^definitive-guide]. The broadcast side is materialized on the driver as part of preparing the broadcast variable before it is pushed out to executors, which is why an oversized broadcast (whether picked automatically or forced via a hint/`broadcast()` call) is a direct driver-OOM risk rather than only an executor-side risk[^definitive-guide].

## Does bucketing require both tables to have the same number of buckets? What happens if bucket counts differ — is there a partial benefit?

For the default shuffle-free bucketed join, yes: both sides need the same bucket count. The documented demos bucket both tables identically: 4 buckets on each side[^japila-bucketing] or 16 buckets on each side (`SelectedBucketsCount: 16 out of 16` on both branches of the `SortMergeJoin`)[^luminousmen-bucketing], and only then does the physical plan drop the `Exchange` nodes entirely[^taboola-bucketing-shuffle].

There is a partial-benefit path when counts differ but are related by a ratio: since Spark 3.1, `spark.sql.bucketing.coalesceBucketsInJoin.enabled` lets Spark coalesce the side with more buckets down to match the side with fewer, as long as the ratio between the two bucket counts is within `spark.sql.bucketing.coalesceBucketsInJoin.maxBucketRatio` (default `4`)[^spark-configuration]. Enabling that coalescing can still eliminate the shuffle for the join, but it does so by reducing parallelism on the finer-grained side and "could possibly cause OOM for shuffled hash join" as a tradeoff[^spark-configuration]. Outside that ratio (or with coalescing disabled), mismatched bucket counts get no free win and the join falls back to a normal shuffle.

## Does bucketing eliminate the sort phase of sort-merge join, or just the shuffle, or both?

Bucketing by itself eliminates only the shuffle (the `Exchange` step), not necessarily the sort. In the bucketed-join demo where both sides are bucketed to the same count but not additionally pre-sorted, the physical plan still shows a `Sort` operator on each branch even though the shuffle is gone: `SortMergeJoin ... :- Sort ... FileScan ... SelectedBucketsCount: 16 out of 16`[^luminousmen-bucketing]. This matches the general framing that "bucketing is an optimization technique that uses buckets ... to avoid data shuffle in join queries" and that with bucketing "the Exchanges will no longer be necessary (as the tables are already pre-shuffled)". The claim is scoped to shuffles, not sorting[^japila-bucketing]. A separate real-world account of removing bucketed shuffles likewise frames the win as "the right branch is missing an Exchange (i.e. shuffle)"[^taboola-bucketing-shuffle].

To also remove the sort phase, the bucketed tables must additionally be written pre-sorted by the join key using `sortBy` alongside `bucketBy`. When that's done, the merge phase has nothing left to do: "the joined output is sorted by `uid` and `users_id`, because we saved the tables sorted in ascending order. As such, there's no need to sort during the `SortMergeJoin`," and the Spark UI shows the query going straight to `WholeStageCodegen` with no `Exchange`[^learning-spark-2e]. So: shuffle elimination comes from bucketing (matching bucket counts), and sort elimination additionally requires the buckets to be pre-sorted via `sortBy`.

## Can the Catalyst optimizer reorder joins automatically (join reordering)? Is spark.sql.cbo.joinReorder.enabled needed?

Multi-way join reordering specifically is gated behind the cost-based optimizer and is off by default. `spark.sql.cbo.enabled` (which turns on CBO estimation of plan statistics) defaults to `false`[^spark-configuration], and even with CBO on, join reordering itself requires the separate flag `spark.sql.cbo.joinReorder.enabled`, described as "Enables join reorder in CBO," which also defaults to `false`[^spark-configuration]. Related knobs only take effect once join reordering is enabled: `spark.sql.cbo.joinReorder.dp.threshold` caps the dynamic-programming join enumeration at 12 joined nodes by default[^spark-configuration], and `spark.sql.cbo.joinReorder.dp.star.filter` applies star-join filter heuristics to that enumeration[^spark-configuration]. There's also a lighter-weight, non-CBO path: `spark.sql.cbo.starSchemaDetection` (default `false`) "enables join reordering based on star schema detection" without requiring the full CBO machinery[^spark-configuration].

Separate from that dedicated join-reorder rule, Catalyst always applies its regular rule-based optimizations regardless of these CBO flags. Spark SQL "can sometimes push down or reorder operations to make your joins more efficient" even without CBO[^high-perf-spark]. A concrete example is predicate pushdown: a filter written after a join in the DataFrame API was moved before the join (and pushed into the JDBC source) automatically by Catalyst, visible in the physical plan[^luminousmen-dataframe-api]. But that's operator reordering around a join, not reordering the join order among multiple relations. Actual join-order reordering is the capability controlled by `spark.sql.cbo.joinReorder.enabled`.

## What is the difference between BROADCAST, MERGE, SHUFFLE_HASH, and SHUFFLE_REPLICATE_NL join hints?

All four hints instruct Spark to use the named strategy for the specified relation(s) in a join[^spark-sql-perf-tuning]:

- **BROADCAST** (also accepted as `BROADCASTJOIN`/`MAPJOIN`) forces a broadcast join with the hinted relation as the build side (broadcast hash join if there's an equi-join key, otherwise broadcast nested loop join), and this is honored even above `spark.sql.autoBroadcastJoinThreshold`[^spark-sql-perf-tuning]. Broadcast hash avoids shuffling and supports all join types except full outer, but requires an equi-join[^high-perf-spark].
- **MERGE** forces a shuffle sort-merge join. This strategy requires an equi-join on sortable keys, needs high cardinality to be worthwhile, and is less likely to OOM than the hash-based alternatives since it doesn't build an in-memory hash table[^high-perf-spark].
- **SHUFFLE_HASH** forces a shuffle hash join, which supports all join types on an equi-join key but, like MERGE, requires high cardinality; it builds a hash table per partition after shuffling[^high-perf-spark].
- **SHUFFLE_REPLICATE_NL** forces a shuffle-and-replicate nested loop (cartesian-style) join, which supports inner and cartesian joins with both equi and non-equi conditions but carries a high chance of data explosion since every partition is joined against every other partition[^high-perf-spark].

When conflicting hints are specified on both sides of a join, Spark resolves the conflict with a fixed priority: BROADCAST over MERGE over SHUFFLE_HASH over SHUFFLE_REPLICATE_NL[^spark-sql-perf-tuning]. If both sides carry the same BROADCAST or SHUFFLE_HASH hint, Spark still has to pick a build side, which it does based on the join type and the relations' sizes[^spark-sql-perf-tuning]. As with any hint, none of these are guaranteed: Spark may not honor a hinted strategy if it doesn't support the actual join type being performed[^spark-sql-perf-tuning].

## In a skew join with manual salting, what is the correct way to handle the NULL key case so salted and non-salted rows join correctly?

The retrieved sources describe the general salting mechanism: adding a random "salt" column to the join key on both sides so a single hot key is spread across many partitions, e.g. exploding the dimension side into one row per salt value and assigning a random salt to the fact side, then joining on the composite `(key, salt)` pair[^luminousmen-partition-tuning], and Spark's own automated alternatives to doing this by hand: AQE's skew-join handling, which splits (and replicates if needed) oversized shuffle partitions detected at runtime[^spark-spip-aqe-skew], controlled by `spark.sql.adaptive.skewJoin.enabled`[^spark-configuration], and Databricks' declarative `SKEW` hint that lets the engine construct a skew-aware plan without manual salting at all[^databricks-skew-join].

## What is spark.sql.join.preferSortMergeJoin and when does it override broadcast threshold logic?

`spark.sql.join.preferSortMergeJoin` is the switch that governs Spark's default preference for sort-merge join over shuffle hash join once a join has already been routed to a shuffle-based strategy: "By default, the `SortMergeJoin` is enabled via `spark.sql.join.preferSortMergeJoin`"[^learning-spark-2e]. It does not interact with whether a broadcast join is chosen in the first place. Broadcast selection is governed separately by `spark.sql.autoBroadcastJoinThreshold` (or an explicit hint), and only once broadcast is ruled out does this preference decide between sort-merge and shuffle hash for the remaining large-table-to-large-table case[^definitive-guide][^spark-sql-perf-tuning].

Adaptive Query Execution can override this preference at runtime in both directions. Under AQE, `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold` (default `0`, meaning disabled) lets Spark prefer a shuffled hash join over sort-merge "regardless of the value of `spark.sql.join.preferSortMergeJoin`" whenever every post-shuffle partition's size stays under that threshold and it isn't smaller than `spark.sql.adaptive.advisoryPartitionSizeInBytes`[^spark-sql-perf-tuning]. Separately, AQE can also convert an already-planned sort-merge join into a broadcast hash join mid-execution: "AQE converts sort-merge join to broadcast hash join when the runtime statistics of any join side are smaller than the adaptive broadcast hash join threshold"[^spark-sql-perf-tuning]. This is a runtime-statistics-driven override of the original broadcast-threshold decision, distinct from (and downstream of) the `preferSortMergeJoin` setting itself.
