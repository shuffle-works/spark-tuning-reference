# Anti-Patterns

## Q1. What are the most commonly cited Spark anti-patterns in practitioner literature?

Practitioner checklists converge on a recurring set of mistakes rather than exotic ones. The most frequently cited:

- **Staying on the RDD API instead of DataFrame/Dataset.** RDDs are "lambda-driven": Spark cannot see inside the closures, so it cannot apply predicate pushdown, filter reordering, Adaptive Query Execution, or cost-based join reordering. The RDD-based MLlib API is called out as being in maintenance mode for the same reason[^luminousmen-optimization-checklist].
- **Wrong file format / schema handling.** Reading raw CSV or JSON without an explicit schema forces a full data scan just to infer types; Parquet is recommended for analytical workloads because column pruning, predicate pushdown, and stats-based file skipping work out of the box[^luminousmen-optimization-checklist].
- **Non-splittable compression.** A large GZIP file can't be split across executors, so one node must decompress the whole file alone; Snappy, LZ4, or ZSTD are recommended instead because they're splittable[^luminousmen-optimization-checklist].
- **Storing data as JSON instead of a binary columnar/row format.** JSON has to be re-parsed on every read; Avro, Parquet, Thrift, or Protobuf structs stored in a sequence file avoid the repeated parsing cost[^cloudera-tuning-spark].
- **Not registering custom Kryo classes**, which increases serialized-record size and hurts serialized cache storage levels (e.g., `MEMORY_SER`)[^cloudera-tuning-spark].

## Q2. collect() on a large DataFrame — what is the exact failure path: driver OOM, serialization buffer, or network transfer?

The failure is driver-side memory exhaustion, not a serialization-buffer limit or a network-transfer failure. `collect()` gathers every `Row` from every partition into a single in-memory `Array` that lives entirely on the driver, not the cluster[^advanced-analytics-pyspark]. Because the driver has to hold that whole result set in its own JVM heap, "for extremely large DataFrames, using these methods can be dangerous and cause an out-of-memory exception"[^advanced-analytics-pyspark][^definitive-guide][^learning-spark-2e]. High Performance Spark states the same rule plainly: "do not collect large DataFrames back to the driver," including for `toPandas()`, which does the same driver-side collection for Python users[^high-perf-spark].

Before an outright driver crash, Spark has a guardrail that fires first in most cases: `spark.driver.maxResultSize` (default 1 GB) caps the total serialized size of results shipped back to the driver across all tasks, and Spark also logs a warning once a single task's serialized size passes roughly 1 MB (`TASK_SIZE_TO_WARN_KIB = 1000`); once the accumulated result exceeds `maxResultSize` the job errors out rather than continuing to grow the heap[^luminousmen-optimization-checklist]. So the practical failure path is: task results serialize normally over the network → they accumulate on the driver → either `maxResultSize` aborts the job first, or, if that limit is raised or disabled, the driver JVM itself runs out of heap and crashes. Serialization and network transfer are the mechanism that gets the data there; the actual point of failure is driver memory.

## Q3. Does df.count() after a cache() guarantee full materialization? Is there any scenario where some partitions are computed but not persisted to the cache?

`count()` is one of the actions that forces Spark to touch every partition, so unlike `take(1)` or `limit(100)` (which only materialize the partitions needed to satisfy the request), a `.cache()` followed by `.count()` does drive computation of every partition and is the recommended way to force full materialization of the cache[^learning-spark-2e][^luminousmen-caching-mechanics].

But "materialized" and "persisted" are not the same guarantee, for two reasons:

1. **Partial caching by design, even for `count()`.** Partitions cannot be fractionally cached: if you have 8 partitions but only memory for 4.5, only 4 will actually be cached, and any partition that didn't fit has to be recomputed the next time it's accessed[^learning-spark-2e]. Caching happens locally and incrementally, block by block, as each executor computes its own partitions. There is no centralized "cache everything now" step[^luminousmen-caching-mechanics].
2. **Eviction and cache-plan mismatch after the fact.** Even a fully materialized cache is best-effort: cached blocks compete for the same memory pool as execution, and the BlockManager will evict blocks under memory pressure without warning, and there's no built-in visibility into how much of a DataFrame is still actually cached[^luminousmen-caching-mechanics]. Separately, caching is tied to the *analyzed* logical plan (before optimization), so a second query that's semantically identical but has a different analyzed plan will not hit the cache at all and Spark will silently recompute the whole DAG from source[^luminousmen-caching-mechanics].

So: `count()` after `cache()` does force every partition to be computed and attempted for caching (it is the correct way to materialize, as opposed to `take`/`limit`), but it does not guarantee those partitions stay persisted through to the next action, because of eviction under memory pressure, executor loss (a block computed on a dead executor without a replicated storage level like `MEMORY_AND_DISK_2` is gone and must be recomputed)[^luminousmen-caching-mechanics], or an analyzed-plan mismatch that bypasses the cache entirely.

## Q4. For Python row-at-a-time UDFs: is the overhead primarily serialization (pickle), context switching, or Python interpreter overhead? Are there benchmarks separating these?

The overhead the corpus attributes to row-at-a-time Python UDFs is serialization plus per-row JVM↔Python data movement, not raw Python interpreter execution speed. The original Pandas UDF announcement states it directly: "These user-defined functions operate one-row-at-a-time, and thus suffer from high serialization and invocation overhead," which is exactly why many teams historically wrote UDFs in Scala/Java and invoked them from Python instead[^databricks-pandas-udf]. Learning Spark, 2nd Edition frames the same fact in terms of the JVM/Python boundary: "PySpark UDFs required data movement between the JVM and Python, which was quite expensive," and once data is transferred via Apache Arrow "there is no longer the need to serialize/pickle the data as it is already in a format consumable by the Python process"[^learning-spark-2e]. luminousmen's DataFrame-API write-up describes the mechanism as *double* serialization for RDD-era Python UDFs (Java/Scala objects are serialized, then re-serialized to Python via `cloudpickle` and back on every call) and asserts that "most of our time is spent only on serialization of data. Actual computing is often not a big blocking part"[^luminousmen-dataframe-api]. High Performance Spark's framing is consistent: using UDFs written in non-JVM languages "you lose much of the performance benefit, as the data must still be transferred out of the JVM"[^high-perf-spark].

On benchmarks: the corpus has an aggregate before/after number, not a breakdown by cost component. The Databricks Pandas UDF benchmark (10M-row DataFrame, Int + Double columns, single-node cluster) shows vectorized Pandas UDFs beating row-at-a-time UDFs "across the board, ranging from 3x to over 100x" on three workloads (plus-one, cumulative probability, subtract-mean)[^databricks-pandas-udf]. That number bundles together the elimination of per-row pickling, the reduction in JVM↔Python round trips (batched via Arrow), and vectorized execution inside pandas. The corpus does not isolate pickle cost, process/context-switch cost, and CPython interpreter cost as separate line items. **[UNRESOURCED]** for a benchmark that decomposes those three factors individually; that would require a microbenchmark paper or profiler trace not present in this corpus.

## Q5. spark.sql.shuffle.partitions=200 fixed: observable symptom of too few partitions (spill) vs too many (scheduling overhead) in the Spark UI?

`spark.sql.shuffle.partitions` controls how many partitions Spark creates for wide transformations (`join`, `groupBy`, aggregations) and defaults to 200 regardless of data size: "it doesn't matter if you're joining 5MB or 5TB"[^luminousmen-partitions][^spark-configuration].

**Too few partitions relative to data size** (large per-partition working set): each of the 200 partitions ends up holding more data than fits comfortably in an executor's memory, which "causes fewer tasks at a time to be processed in executors, but it increases the load on each individual executor and often leads to memory errors," and once partition size exceeds available executor memory you get disk spills[^luminousmen-partitions]. In the Spark UI this shows up on the Stages tab as "Spill (Memory)" or "Spill (Disk)" entries against a stage, a direct signal that data didn't fit and Spark had to write intermediate results to disk[^luminousmen-partitions].

**Too many partitions relative to data size** (tiny per-partition working set): with a small dataset, 200 shuffle partitions can mean each task gets on the order of ten rows: "tasks become microscopic. Most of your CPUs will just be sitting there doing nothing"[^luminousmen-partitions]. The Spark UI signature here is the inverse of the spill case: a large task/stage count where each task's duration is dominated by scheduling and bookkeeping rather than actual compute, and (if that stage also writes output) a correspondingly large number of small output files, since Spark writes one file per output partition regardless of how little data it holds[^luminousmen-partitions].

The rule of thumb given for picking a number: if tasks are processing multiple GB each and spilling, increase `spark.sql.shuffle.partitions`; if tasks finish in a couple of seconds and write tiny files, decrease it; a target of roughly 100–200 MB of data per task is offered as a starting point, tuned per dataset[^luminousmen-partitions].

## Q6. Broadcasting a table that is too large — at what point does the broadcast fail: driver OOM, executor OOM, or serialization timeout?

The corpus attributes the failure to the driver, at the collection step, not to executor-side replication or a serialization timeout. Spark: The Definitive Guide states it directly for broadcast joins: "if you try to broadcast something too large, you can crash your driver node (because that collect is expensive)"[^definitive-guide]. The mechanism is that the small side of the join has to be collected onto the driver before it can be broadcast out to every executor. That collection step is the same driver-memory operation as calling `.collect()` on a DataFrame, and it is what fails first. The book's monitoring/debugging chapter lists this explicitly as a documented cause of a driver `OutOfMemoryError`: "you might be using a broadcast join where the data to be broadcast is too big. Use Spark's maximum broadcast join configuration to better control the size it will broadcast"[^definitive-guide]. The recommended treatment (raise or disable `spark.sql.autoBroadcastJoinThreshold`, or increase driver memory) targets the driver, not the executors.

## Q7. Is repartition(1) before write ever correct, or is coalesce(1) always preferable when a single output file is needed?

`coalesce(1)` is not always preferable; it depends on where in the pipeline the single-file requirement lands relative to the upstream computation. The general guidance is to prefer `coalesce` first because it avoids a shuffle by merging partitions that are already on the same node, whereas `repartition` triggers a full shuffle across the network[^definitive-guide].

The catch is what `coalesce` does to the *upstream* stage, not just the output stage. High Performance Spark is explicit about this: because `coalesce` is a narrow transformation, "coalesce causes the upstream partitions in the entire stage to execute with the level of parallelism assigned by coalesce, which may be undesirable in some cases," and the book's stated fix is to "avoid this behavior at the cost of a shuffle by using the repartition function instead"[^high-perf-spark]. Concretely: `coalesce(1)` before a write doesn't just produce one output file: because it's narrow, the scheduler can fuse the *entire preceding stage* down to a single task, so all of the upstream filtering/transformation work that would otherwise run in parallel across many executors ends up serialized onto one core, with the rest of the cluster idle[^luminousmen-partitions]. `repartition(1)` inserts an explicit shuffle boundary, so the upstream stage keeps its original parallelism and only the post-shuffle write stage is collapsed to one task.

So `repartition(1)` is the correct choice when there is meaningful upstream computation you don't want to collapse onto a single executor; `coalesce(1)` is preferable when the upstream stage is already cheap (e.g., writing a small, already-computed result) and paying for a shuffle just to merge files would be wasted cost. `high-perf-spark`'s own practical recommendation is to keep the two calls semantically distinct in code (`repartition` when you want a shuffle, `coalesce` when you don't) rather than trying to make `coalesce` behave like `repartition` via its shuffle flag[^high-perf-spark].

## Q8. For the "no predicate pushdown" anti-pattern: how can a practitioner verify pushdown is happening in the physical plan? What keywords indicate pushdown is active?

Run `.explain()` (the corpus's worked examples use the default explain mode against a JDBC source, not specifically `"formatted"`, but the same physical-plan annotation applies either way) and look at the `Scan` node for the `PushedFilters` marker. Definitive Guide shows the annotated plan directly: filtering on `DEST_COUNTRY_NAME in ('Anguilla', 'Sweden')` produces `*Scan JDBCRel... PushedFilters: [*In(DEST_COUNTRY_NAME, [Anguilla,Sweden])]` in the physical plan. The presence of `PushedFilters` next to the `Scan` operator is the keyword to look for[^definitive-guide]. Column pruning is verified the same way: a `.select()` that only needs one column shows up as a narrowed schema at the scan (`ReadSchema: ...` reflecting just the projected columns) rather than a full-table scan[^definitive-guide].

High Performance Spark frames the general debugging technique: use `explain` (paired with `printSchema`) and check "if the filters were able to be pushed down 'next to' the data source" in the final query plan; it also flags an important nuance: some data sources only *partially* handle a filter and leave Spark to re-evaluate it as a safety mechanism, and "these are still generally 'good' filter pushdowns as the amount of data being read has been reduced," so a partial pushdown is not itself a failure signature[^high-perf-spark]. On the flip side, the optimization checklist notes what does *not* push down: "Spark pushes down simple filters (column equality, IN, IS NULL) to JDBC automatically, but anything with a computed column or cast won't push and will get evaluated in Spark after the full read"[^luminousmen-optimization-checklist]. So a filter expression involving a cast or a derived/computed column is a concrete anti-pattern to look for when `PushedFilters` is absent or incomplete in the plan.
