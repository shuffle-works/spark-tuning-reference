# Memory Management

## How does the Unified Memory Manager (introduced in Spark 1.6) allocate memory between execution and storage?

Since Spark 1.6, the `UnifiedMemoryManager` replaced the earlier static split between execution and storage memory with a single shared region, referred to as M[^spark-notes-task-memory-management][^spark-tuning-guide]. M is carved out of the JVM heap after first setting aside 300 MiB of reserved system memory: `M = (JVM heap − 300 MiB) × spark.memory.fraction`, with `spark.memory.fraction` defaulting to 0.6[^spark-tuning-guide][^luminousmen-memory-management]. Within M, `spark.memory.storageFraction` (default 0.5) marks off a subregion R reserved for cached blocks that are immune to eviction; with defaults, this works out to roughly a 30%/30% on-heap split between execution and storage out of total executor memory[^luminousmen-memory-management].

Execution and storage borrow from each other dynamically rather than sitting behind a hard wall: when execution memory is unused, storage can acquire all of it, and vice versa[^spark-tuning-guide][^spark-notes-task-memory-management]. The two are not equal peers. Execution always has priority; when it needs memory, it takes it immediately, evicting cached storage blocks if necessary[^luminousmen-memory-management].

## What is the exact eviction policy when execution needs memory that storage is using? Is it LRU per block, per partition, or per RDD?

Storage eviction under memory pressure follows an LRU (least recently used) policy[^spark-notes-task-memory-management][^luminousmen-caching-mechanics]. The granularity is the block: Spark's `BlockManager` tracks cached data as per-partition blocks (one block per RDD/DataFrame partition), and LRU operates at that level rather than evicting an entire RDD or cached table in one shot[^spark-rdd-programming][^high-perf-spark]. In practice this tends to evict the oldest partitions first, those materialized in the earliest job or stage, though lazy evaluation makes it hard to predict exactly which partitions will go ahead of time[^high-perf-spark].

What happens to an evicted block depends on its `StorageLevel`. For `MEMORY_ONLY`, the block is simply dropped and recomputed from the RDD's lineage the next time it's needed. For a disk-backed level like `MEMORY_AND_DISK`, the evicted block is written to disk and read back from there instead of being recomputed[^high-perf-spark][^luminousmen-caching-mechanics]. Blocks can also be evicted well before you ever try to reuse them. `.cache()` does not guarantee a block stays resident, especially on busy clusters or long pipelines[^luminousmen-caching-mechanics].

## Does storage memory ever evict execution memory, or is eviction unidirectional (storage to execution)?

Eviction is one-directional: execution can evict storage, but storage can never evict execution. As luminousmen-memory-management puts it: "If Execution needs memory, it takes it. If Storage is using that space (cached RDDs, broadcasts), Spark starts evicting blocks. If Execution is idle, Storage can grow into that space, until Execution comes back."[^luminousmen-memory-management] That growth-then-shrink-back behavior is dynamic borrowing, not storage evicting execution. As spark-notes-task-memory-management summarizes the agreement between the two regions: "keep acquiring execution memory and evict storage as you need more execution memory"[^spark-notes-task-memory-management], never the reverse. The same asymmetric rule carries over when off-heap memory is enabled (`spark.memory.offHeap.enabled=true`): execution still has priority and storage still gets evicted first[^luminousmen-memory-management].

## What is the formula for reserved system memory? The docs mention 300 MB — is this hardcoded or configurable?

Reserved system memory is a flat 300 MB (`RESERVED_SYSTEM_MEMORY_BYTES` in the Spark source) subtracted from the executor heap before anything else is calculated: usable memory = executor memory − 300 MB[^luminousmen-memory-management]. It isn't really a formula so much as a constant, and it's hardcoded: there is no supported production configuration to change it. The only override is the internal `spark.testing.reservedMemory` property, which exists for Spark's own test suite and isn't meant for production tuning[^luminousmen-memory-management].

## What happens step-by-step when execution memory is exhausted during a sort or hash aggregation — what is the exact spill trigger and spill path?

Each task gets its own `TaskMemoryManager`, which arbitrates access to the shared execution pool across all tasks concurrently running on an executor. It enforces a soft per-task cap: with `n` tasks running concurrently, each task is allowed to allocate somewhere between `1/(2n)` and `1/n` of total execution memory, and the first task to arrive on an idle executor typically grabs more than its later-arriving neighbors[^luminousmen-memory-management]. This is a soft limit rather than a hard stop. When a task's sort or hash-aggregation operator keeps requesting execution-memory pages and can't get more, Spark doesn't fail immediately. It blocks the requesting task, triggers a spill of that task's in-memory data structure to disk, or, in the worst case, throws an `OutOfMemoryError`[^luminousmen-memory-management].

The spill path itself runs through Spark's map/shuffle I/O machinery: during map and shuffle operations Spark writes to and reads from local disk shuffle files, and shuffle partitions created by wide transformations like `groupBy()` or `join()` spill to the executors' local disks at the location set by `spark.local.directory`[^learning-spark-2e]. [NEEDS-REVIEW: the Q5-citable sources confirm that execution-memory exhaustion during sort/hash-aggregation causes the task to block, spill to local disk, or in the worst case throw an OOM (see the `TaskMemoryManager` behavior above), and that shuffle spill/merge I/O lands on `spark.local.dir`/`spark.local.directory`, but none of them describe the specific internal spill mechanics — e.g., the serialized ("Tungsten") sort path's `ShuffleExternalSorter` and its 8-byte record pointers, the `spark.shuffle.spill.compress`/`spark.shuffle.spill.diskWriteBufferSize` settings, how spilled runs are merged/concatenated at the end of the map task, or whether the legacy `spark.shuffle.spill` flag is still honored. Confirming those details would require Spark's shuffle source (`org.apache.spark.shuffle.sort.SortShuffleManager`/`ShuffleExternalSorter`) or the configuration reference, neither of which is citable for this question.]

SQL physical operators apply the same idea with their own row-count guardrails: `sortMergeJoinExec`'s in-memory buffer and the cartesian-product operator's buffer both spill once they cross a configured row threshold, which by default is set to the value of `spark.shuffle.spill.numElementsForceSpillThreshold`[^spark-source-sql-conf]. Whatever the trigger, the resulting spilled bytes are exposed on the task metrics as `memoryBytesSpilled`, visible in the Spark UI and event log[^spark-history-server].

## What is the difference between spark.executor.memoryOverhead in YARN vs Kubernetes — does the meaning or formula differ?

The formula is the same on both cluster managers: `spark.executor.memoryOverhead` defaults to `executorMemory × spark.executor.memoryOverheadFactor`, floored at `spark.executor.minMemoryOverhead` (384 MiB)[^spark-configuration]. `spark.executor.memoryOverheadFactor` itself defaults to 0.10 for ordinary JVM executors, but Spark bumps that default to 0.40 specifically for Kubernetes non-JVM jobs (e.g., executors that aren't running plain JVM tasks), since those workloads tend to need more non-JVM heap space and were commonly failing with "Memory Overhead Exceeded" errors under the 0.10 default[^spark-configuration]. Worked example: with `--executor-memory=8G`, the default 10% overhead gives `max(0.1 × 8192 MB, 384 MB) = 819 MB`, so the total memory requested from the cluster manager is `8192 + 819 = 9011 MB`[^luminousmen-memory-management]. The legacy, YARN-only `spark.yarn.executor.memoryOverhead` property was removed in Spark 3.0 in favor of the cluster-manager-agnostic `spark.executor.memoryOverhead`[^luminousmen-memory-management].

Where YARN and Kubernetes genuinely differ is in what happens with that total downstream, not in how it's computed. On YARN, the sum of executor memory, memory overhead, off-heap size, and PySpark memory is the amount requested from and allocated by the NodeManager as container memory[^luminousmen-memory-management]. On Kubernetes, each executor is a pod, and that same total becomes the pod's memory request/limit, enforced through container-level cgroups; if the process's real memory footprint (heap + off-heap + Python + native) exceeds that limit, the kubelet OOMKills the pod rather than YARN killing the container[^luminousmen-memory-management]. In both cases, off-heap memory and (if unset) PySpark memory are not automatically folded into the overhead calculation, so enabling `spark.memory.offHeap.size` without also increasing `spark.executor.memoryOverhead` (or setting `spark.executor.pyspark.memory` explicitly) can push actual usage past what either cluster manager granted, and the executor gets killed with a vague container-memory error rather than a Spark-level exception[^luminousmen-memory-management].

## Is spark.python.worker.memory a hard limit enforced by the JVM, or just a hint? What happens when a Python worker exceeds it?

It's a soft threshold, not a hard limit, and it cannot be JVM-enforced in the first place, because a PySpark worker is a separate OS process outside the JVM heap[^luminousmen-memory-management]. Per its documented behavior, `spark.python.worker.memory` (default `512m`) is "the amount of memory to use per python worker process during aggregation... If the memory used during aggregation goes above this amount, it will spill the data into disks"[^spark-configuration]. It's a spill trigger for the worker's own aggregation buffering, not a cap the JVM polices.

If a Python worker's actual memory footprint keeps growing beyond that point (for example due to code paths that don't spill, oversized single records, or native library allocations), nothing in the JVM stops it. The only related guardrail is `spark.executor.pyspark.memory`, which if set will actually try to bound PySpark's memory per executor, but that limiting depends on Python's `resource` module and inherits its platform limitations: it isn't supported on Windows, and "actual resource is not limited on MacOS" even when set[^spark-configuration]. Absent that config, PySpark memory usage is folded into `spark.executor.memoryOverhead` by default[^spark-configuration], so the practical backstop is the container limit: once the executor's combined footprint (heap + overhead, which includes PySpark memory when `spark.executor.pyspark.memory` is unset) exceeds what YARN or Kubernetes granted, the whole container/pod gets killed rather than the Python worker being throttled[^spark-configuration][^luminousmen-memory-management].

## What is off-heap memory (spark.memory.offHeap) used for exactly — Tungsten, storage, both? Does it affect GC pause frequency?

Both. When `spark.memory.offHeap.enabled=true`, Spark allocates raw off-heap buffers directly via `sun.misc.Unsafe` (routed through `jdk.internal.misc.Unsafe` on JDK 17+, which is why some Spark builds need `--add-opens` flags), and that off-heap region is split into its own Execution and Storage pools, following the same `UnifiedMemoryManager` borrowing rules as on-heap memory: execution has priority, storage gets evicted first[^luminousmen-memory-management]. Enabling it requires `spark.memory.offHeap.size` to be a positive value, and the setting "has no impact on heap memory usage": turning on off-heap memory does not shrink the JVM `-Xmx` for you, so the on-heap size has to be reduced manually if you want to keep total footprint constant[^spark-configuration].

This off-heap execution memory is what underlies Project Tungsten: Tungsten's compact binary row encoding, its explicit-memory-managed hash map for aggregations (an early benchmark showed over 1 million aggregation operations per second in a single thread versus `java.util.HashMap`, with "almost no performance degradation as memory utilization increases," unlike the JVM default which eventually thrashes on GC), and cache-aware sort/join algorithms are all built to run against this off-heap, GC-invisible memory[^databricks-tungsten][^learning-spark-2e]. Because off-heap buffers sit outside the JVM heap, they are invisible to the garbage collector. Fewer and smaller live objects need to be tracked, scanned, and copied on the heap, which reduces both the frequency and duration of GC pauses. That's the entire premise of turning it on: no GC babysitting objects it doesn't own, at the cost of no GC safety net if something goes wrong[^luminousmen-memory-management].

## Is spark.memory.fraction applied to total JVM heap or to JVM heap minus the 300 MB reserved memory?

To JVM heap minus the 300 MB reserved memory, not total heap. The Spark tuning guide is explicit that `spark.memory.fraction` "expresses the size of M as a fraction of the (JVM heap space − 300MiB)"[^spark-tuning-guide]. This matches the usable-memory formula elsewhere: usable memory = executor memory − 300 MB, and execution/storage memory are each computed as `usable memory × spark.memory.fraction × (storage/execution split)`. The 300 MB reserved region is carved out first, and `spark.memory.fraction` only ever applies to what's left[^luminousmen-memory-management].

## What is the exact behavior when spark.memory.offHeap.enabled=true but spark.memory.offHeap.size=0?

`spark.memory.offHeap.size` defaults to `0`, and the Spark configuration reference states plainly that it "must be set to a positive value when `spark.memory.offHeap.enabled=true`"[^spark-configuration], meaning enabling off-heap memory while leaving its size at the default 0 is a documented-invalid combination, not a supported way to run with off-heap "on but empty." Consistent with that, every worked example of turning it on pairs `spark.memory.offHeap.enabled=true` with an explicit positive size, e.g. `spark.memory.offHeap.size=1g`[^luminousmen-memory-management]. With size left at `0`, there is no off-heap pool for Tungsten's off-heap execution or storage regions to allocate into, which is exactly the state the documentation calls out as requiring a positive size. [UNRESOURCED: the retrieved sources state the 0-size case is disallowed by config but do not describe the exact runtime behavior — e.g., whether Spark throws a specific exception during `SparkContext`/`SparkSession` initialization versus silently leaving off-heap memory unusable. Confirming the precise failure mode would require the `MemoryManager`/`UnifiedMemoryManager` initialization source (`org/apache/spark/memory`) rather than the configuration reference.]
