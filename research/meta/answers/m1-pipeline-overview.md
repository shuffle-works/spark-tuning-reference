# Pipeline Overview

## Q1. What problem does this repository solve, and what does it produce as its build output?

This repository runs a question-granular, citation-backed answering pipeline that turns a registry of research questions into a reviewed reference site, and it does so twice: once for a Spark Tuning Reference and once for the pipeline's own architecture[^architecture]. Selection between the two happens via `--corpus {spark,meta}` on every pipeline script, defaulting to `spark`. `scripts/corpus.py` holds a `Corpus` dataclass with `SPARK`/`META` profiles, and every path a script touches (registry, per-question answers dir, section-projection dir, content-state sidecar, content manifest, references dir, Chroma path/collection, embedding model, build output, site title) comes from the selected profile rather than a hardcoded constant[^architecture]. The `spark` corpus is the Spark Tuning Reference itself, built over `references/` and indexed with the asymmetric question→passage retriever `multi-qa-mpnet-base-dot-v1`; its build output is `index.html`[^architecture]. The `meta` corpus is this project's own architecture doc (`docs/architecture.md`, `docs/runbook.md`, `docs/rules/*.md`, `AGENTS.md`, and the agent/skill files that make up the pipeline). It is indexed via symlinks under `references-meta/` with the general symmetric model `all-mpnet-base-v2` into a separate Chroma collection, and its build output is `meta.html`[^architecture]. The two corpora never share a registry, a Chroma collection, or a content manifest; each is an independent instance of the same pipeline shape[^architecture].

Within either corpus, the atomic unit of the pipeline is the question, not the section: the registry (`research/questions.yaml`, or its meta counterpart) is the single source of truth holding sections and questions, and every other artifact is a derived projection, never edited directly as a source of truth[^architecture]. Content flows one way through the pipeline: registry → per-question answer files (prose plus footnotes and their own `## Sources`) → section projections (an ordered concatenation of a section's question answers, with sources merged and deduped) → content pages (brief-driven on first generation, human-owned after that) → the built site, and a downstream artifact is never treated as a source of truth for an upstream one[^architecture]. The project's own `AGENTS.md` restates the operator-facing consequence: every content page is real cited prose, not a placeholder, and new or changed content still flows registry → answer → projection → page[^agents-md].

The build output is produced regardless of whether every content page is current. A committed hash sidecar tracks each content page against the sha256 of the section projection it was last generated or accepted from, classifying pages as ungenerated, stale, or ok; the build script checks this before rendering and prints a non-fatal warning banner listing any stale or ungenerated pages, but "the build still produces `index.html` either way"[^architecture]. Recompute never triggers regeneration on its own; it only flags a page stale, since content pages are human-owned once generated[^architecture].

On the Spark side, the resulting pages carry a further constraint tied to why the site exists: its manifest-level anchor IDs are a frozen cross-repo Integration Contract with the sibling `sparkforensics` repo, so renaming or removing one is a breaking change and content assembly must read anchors from `content/manifest.yaml` rather than deriving them from a filename or heading[^rules-content]. That contract applies only to the Spark corpus; `content/meta/manifest.yaml` and `meta.html` carry no such contract and their anchors may change freely[^rules-content]. `docs/anchor-map.md` reconciles the two, mapping each research answer file to its content file and frozen anchor[^anchor-map].

## Q2. What is the one-way derive-direction chain from research/questions.yaml down to index.html, and why does the architecture forbid editing a downstream artifact as a source of truth?

The chain runs in one direction, front to back:

`research/questions.yaml` → `research/answers/q/<id>.md` → `research/answers/<section-id>.md` → `content/*.md` (and `content/bottlenecks/*.md`) → `index.html`[^architecture].

Each stage has a role. `questions.yaml` is the registry of sections and questions with their statuses. Each per-question answer file holds that question's prose plus its own `[^id]` footnotes and `## Sources` block. The section file is a projection: an ordered concatenation of a section's question answers, with `## Sources` merged and deduped, and it is the same path the content manifest's `assembled_from:` already points at. Content pages are brief-driven and only first-generated from that projection, after which they become human-owned. The build turns the content pages into `index.html`[^architecture].

The architecture forbids treating any downstream artifact as a source of truth because `research/questions.yaml` is the single source of truth for the whole pipeline. Every other artifact (per-question answers, section projections, content pages) is a derived projection, regenerable from the registry and the per-question answer files, never edited as a source of truth itself[^architecture]. The registry rules state this directly: never edit a downstream artifact as if it were the source of truth, since per-question answers, section projections, and content pages are all derived projections regenerable from the registry, and recompute always starts at `questions.yaml` and flows forward[^rules-registry]. The derive-direction diagram states the same principle as an invariant: every arrow is one-way, and a downstream artifact (a section projection, a content page, the built site) is never a source of truth for an upstream one[^architecture]. The project's own `AGENTS.md` restates the practical consequence for operators: new or changed content still flows registry → answer → projection → page, and `questions.yaml` remains the authoritative question registry rather than any prose plan or derived array[^agents-md].

## Q3. Why is the question, not the section, the atomic unit of the answering pipeline?

`docs/architecture.md` states the design directly: "the atomic unit of the answering pipeline is the **question**, not the section." It goes on to name `research/questions.yaml` as the single source of truth, holding `sections` (id, num, title, default_k) as a grouping label and `questions` (id, section, text, version, k, status) as the working records. Every other artifact, from per-question answer files up through section projections and content pages, is a derived projection regenerable from the registry and those answer files, never a source of truth itself.[^architecture]

That per-question state (its own `version`, `k`, `status`) is what makes independent recompute possible. `add_question.py` mints an id and appends a single `pending` record without mutating any existing record, and `recompute_question.py` flips exactly one record back to `pending` and backs up only that question's old answer file, touching no other record or file.[^rules-registry] If the section were the atomic unit, recomputing one question's answer would force treating the whole section's state as dirty; scoping status and versioning to the question lets one question be re-answered, re-versioned, or given its own `k` without disturbing its siblings.

The rest of the pipeline is built around that same grain: the Draft/Verify/Redraft agents are "each now scoped to a single question," and the `answer-question` skill runs one question end to end: Draft → Verify → [Redraft → re-Verify] → Humanize → `check_prose` → `project_section` → `content_state` ... → commit.[^architecture] The meta corpus's own `answer-meta-question` skill mirrors this: its input is one question id, and it dispatches the Draft/Verify agents with "a one-item question list = the record's text."[^skill-answer-meta-question] Only after a question is answered does `project_section` roll it into the section file, by concatenating that section's question answers in registry order and merging their `## Sources` blocks[^architecture]. The section projection is assembled from finished question-level work, not answered as a unit itself.
