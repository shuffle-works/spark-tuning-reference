## Q1. What problem does this repository solve, and what does it produce as its build output?

This repository runs a question-granular, citation-backed answering pipeline that turns a registry of research questions into a reviewed reference site, and it does so twice: once for a Spark Tuning Reference and once for the pipeline's own architecture[^architecture]. Selection between the two happens via `--corpus {spark,meta}` on every pipeline script, defaulting to `spark`. `scripts/corpus.py` holds a `Corpus` dataclass with `SPARK`/`META` profiles, and every path a script touches (registry, per-question answers dir, section-projection dir, content-state sidecar, content manifest, references dir, Chroma path/collection, embedding model, build output, site title) comes from the selected profile rather than a hardcoded constant[^architecture]. The `spark` corpus is the Spark Tuning Reference itself, built over `references/` and indexed with the asymmetric question→passage retriever `multi-qa-mpnet-base-dot-v1`; its build output is `index.html`[^architecture]. The `meta` corpus is this project's own architecture doc (`docs/architecture.md`, `docs/runbook.md`, `docs/rules/*.md`, `AGENTS.md`, and the agent/skill files that make up the pipeline). It is indexed via symlinks under `references-meta/` with the general symmetric model `all-mpnet-base-v2` into a separate Chroma collection, and its build output is `meta.html`[^architecture]. The two corpora never share a registry, a Chroma collection, or a content manifest; each is an independent instance of the same pipeline shape[^architecture].

Within either corpus, the atomic unit of the pipeline is the question, not the section: the registry (`research/questions.yaml`, or its meta counterpart) is the single source of truth holding sections and questions, and every other artifact is a derived projection, never edited directly as a source of truth[^architecture]. Content flows one way through the pipeline: registry → per-question answer files (prose plus footnotes and their own `## Sources`) → section projections (an ordered concatenation of a section's question answers, with sources merged and deduped) → content pages (brief-driven on first generation, human-owned after that) → the built site, and a downstream artifact is never treated as a source of truth for an upstream one[^architecture]. The project's own `AGENTS.md` restates the operator-facing consequence: every content page is real cited prose, not a placeholder, and new or changed content still flows registry → answer → projection → page[^agents-md].

The build output is produced regardless of whether every content page is current. A committed hash sidecar tracks each content page against the sha256 of the section projection it was last generated or accepted from, classifying pages as ungenerated, stale, or ok; the build script checks this before rendering and prints a non-fatal warning banner listing any stale or ungenerated pages, but "the build still produces `index.html` either way"[^architecture]. Recompute never triggers regeneration on its own; it only flags a page stale, since content pages are human-owned once generated[^architecture].

On the Spark side, the resulting pages carry a further constraint tied to why the site exists: its manifest-level anchor IDs are a frozen cross-repo Integration Contract with the sibling `sparkforensics` repo, so renaming or removing one is a breaking change and content assembly must read anchors from `content/manifest.yaml` rather than deriving them from a filename or heading[^rules-content]. That contract applies only to the Spark corpus; `content/meta/manifest.yaml` and `meta.html` carry no such contract and their anchors may change freely[^rules-content]. `docs/anchor-map.md` reconciles the two, mapping each research answer file to its content file and frozen anchor[^anchor-map].
